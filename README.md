# Distribuidor TVBox — Admin Dashboard

Dashboard de administración para distribuidores TVBox construido con Next.js 16 (App Router, `cacheComponents`), React 19 y Tailwind 4. Las entidades de negocio se modelan con el formato **umeJSON** y se persisten en **PostgreSQL (JSONB)** siguiendo el diseño normativo de [`eortizs/ume-json-v1`](https://github.com/eortizs/ume-json-v1) (`docs/PERSISTENCE.md`).

## Características

- **Entidades umeJSON genéricas**: cualquier `entityName` con `dynamicProperties`, creado a través de un flujo *finalize* donde el servidor inyecta `id` (UUID v7), `lifecycle.createdAt/updatedAt` y valida los sentinels `RESERVED_FOR_SYSTEM`.
- **Persistencia head + journal**: tabla `entities` (documento JSONB vigente + columnas espejo) y `entity_events` (bitácora append-only con `seq` monotónico, bitemporalidad `occurred_at`/`recorded_at`), con bloqueo optimista por `version` en cada mutación.
- **Autenticación con perfiles**: `admin` (acceso total + gestión de usuarios) y `distribuidor` (solo sus propias entidades). El login siempre es una cuenta de correo. Autorregistro en `/register`: toda cuenta nueva se crea con perfil `distribuidor` y genera su propia entidad umeJSON (`entityName: "Cuenta"`, ligada vía `dynamicProperties.userId` / `distribuidorId`). Usuario y password se insertan junto a su entidad `Cuenta` en una sola transacción. Sesiones en base de datos con cookie httpOnly, contraseñas con scrypt asíncrono, gate a nivel proxy con validación de sesión contra la DB y rate limit de 10 POST/min por IP en `/login` y `/register` (en memoria, por proceso). Inicio de sesión opcional con **«Continuar con Google»** (OAuth 2.0 authorization code sobre las mismas sesiones). Ver [Autenticación con Google](#autenticación-con-google).
- **UI admin**: la pantalla **Clientes** (`/clientes`) lista los clientes del panel de FlujoTV en un **acordeón** con filas tipo **lista de chat** (composición ReUI `c-accordion-9`; `src/components/entities/clientes-accordion.tsx`), pensada para lectura cómoda en móvil: cada fila muestra **avatar grande con iniciales** (`size-12`), el **nombre de usuario** y, como subtítulo, el **nombre propio del cliente** —el de la columna **Notas** del panel, servido por `GET /client_names` (`FlujoClientName`): la API de licencias lo relaciona por usuario (búsqueda por fragmento, sin mayúsculas ni acentos; p. ej. `tv3jcambron` = *Jeanin Cambron*) y el listado lo recibe ya cruzado en `GET /api/flujotv/clients` (`clientNames`, mapa usuario→nombre acotado al perfil; si el panel no reporta nombre no se muestra nada; se muestra **completo hasta en dos líneas** (`line-clamp-2`, nunca truncado con puntos suspensivos: la fila reserva `pr-14` para el carrito de compra rápida y cortar el nombre ahí a ~25 caracteres escondía los apellidos; misma regla en las filas de *Paquetes FlujoTV*)— y, **debajo del nombre**, la **barra de progreso** (componente `progress` de shadcn) con el **conteo compacto de días restantes a su derecha** ("32d"; "—" sin dato). En el margen derecho queda solo el **punto de estado** según la licencia (verde `success` activo, rojo `destructive` vencido, ámbar `warning` pendiente, azul `info` prueba; con `role="img"` y `aria-label` para lectores de pantalla). Entre el contenido y el punto de estado, cada fila lleva el botón de **compra rápida** (`Button` ghost `size="icon"` de 36×36 `rounded-full` con icono de carrito de 20 px —`size-5` en el propio svg, porque la base del `Button` fija `size-4` para svgs sin clase de tamaño y esa regla gana a un `[&_svg]` del consumidor—, negro puro en claro y blanco puro en oscuro, feedback de pulsación `active:scale-90`): lo abre un **bottom sheet** de confirmación (`Drawer` de Base UI, `src/components/ui/drawer.tsx`: panel anclado al borde inferior con asa de arrastre, cierre deslizando hacia abajo y acción primaria a todo el ancho; ver [Convenciones de UI](#convenciones-de-ui)) con el importe y un **selector de método de pago sin selección por defecto** —Mercado Pago, Transferencia y Cupón—, donde cada opción abre su propia pantalla (la de Mercado Pago muestra el desglose del cargo: concepto + costo por procesamiento + total; ver [Selección de método y desglose del cargo](#selección-de-método-y-desglose-del-cargo-sheet)); al confirmar, crea la orden de pago y **redirige al checkout de Mercado Pago** (`purpose: "wallet_purchase"`: solo se paga con cuenta de MP, wallet a wallet; ver [Pago de licencias (Mercado Pago)](#pago-de-licencias-mercado-pago)). La renovación en el panel se aplica **solo** cuando MP confirma el pago vía webhook; al volver a `/clientes` un aviso sondea la orden y refresca la fila en vivo al verla `renewed`. La barra muestra los días restantes con una **ventana de urgencia de 30 días**: con más de 30 días va llena y se agota al acercarse el vencimiento; el indicador se pinta rojo (`destructive`) con ≤5 días o dato desconocido y ámbar (`warning`) con ≤15. La fila es el botón de expansión, **sin chevron ni anillo de foco**; al expandir aparece la **fecha de vencimiento** ("vence 27 nov 2026", movida desde la fila para no duplicarla) y, debajo, el **nombre del distribuidor asignado** al usuario («distribuidor: eortizs»; misma fuente del filtro Distribuidor — llave cruda de la fila del panel (`distributor`/`distribuidor`, nunca `reseller`) o, si falta, el mapa usuario→reseller de `/users/validity` — vía el helper `resellerOf` del propio componente; la línea se omite si el cliente no tiene distribuidor). El listado no lleva contenedor tipo Frame/Card: filas directas sobre el fondo **sin hairlines divisorias** (el ritmo lo dan el espaciado y el `hover`), hover `bg-muted`, skeletons de carga en el mismo layout, estados de error y vacío (`Empty` con reintentar) y contador de resultados. La pantalla incluye **búsqueda** por usuario, **nombre o correo en cliente** (comparación sin acentos, `foldTerm`; el campo va en píldora `rounded-full` con **icono de lupa** a la izquierda: `InputGroup` con addon inicial) y botón *Recargar* —que dispara la **sincronización real** con el panel de FlujoTV (`POST /api/flujotv/refresh`, target `list_clients` con `skip_cache=true`: login en el sitio y extracción de los datos actualizados, ~90 s, tras confirmación en `AlertDialog`; mientras tanto se siguen mostrando los datos cargados con aviso en pantalla y toast al terminar)—, más una **barra de filtros** en dos renglones: arriba, las vistas y el botón «+» en una sola fila desplazable en horizontal con el scrollbar oculto (`overflow-x-auto` sin barra visible; los elementos no se comprimen; **`pr-10`** de padding final para que, al llegar al fondo del scroll, el «+» quede fuera de la zona del chevron y no se esconda debajo de él); **flotando en el margen derecho** del renglón hay un **chevron hacia la derecha** (`ChevronRightIcon` de 16 px en `text-muted-foreground/60`) como **pista de deslizamiento**: gris, sin fondo ni borde ni hover de pulsación — deliberadamente sin aspecto de botón — y sobre un degradado `from-background` que desvanece el contenido hacia el borde para sugerir que la fila continúa; al **hover o tap** despliega un **tooltip «deslizar»** (Tooltip de Base UI, **controlado** con `swipeHintOpen` porque el hover de la librería es *solo-mouse* y sin control el tap táctil no haría nada; `closeOnClick={false}` para que el mismo tap que abre no lo cierre por el dismiss interno) y el **tap además recorre la fila con desplazamiento suave hasta el final** — y, si ya está al final, regresa al inicio — para demostrar el gesto (`runSwipeHint` sobre `filterRowRef`, con salto instantáneo si el sistema pide `prefers-reduced-motion`); el trigger es un `<button type="button">` real — enfocable por teclado, con `aria-label="Más filtros hacia la derecha"` — cuyo `onPointerDown` abre en cualquier pointer type; la capa flotante es `pointer-events-none` y solo el chevron recibe toques, así el resto de la fila sigue desplazándose con el gesto; abajo, los **filtros creados** en su propio renglón. Abre con **vistas preconfiguradas** (`ToggleGroup` outline en cápsula, radio fijo —pulsar la vista activa no la suelta—) y **contador** en cada píldora: **Todos** (el listado completo; elegirla limpia también los filtros manuales), **Por vencer** (regla fija *hardcoded* de menos de 3 días, solo clientes vigentes), **Activo** (`statusLabel` = activo) y **Vencido** (todo lo que no está activo: vencido, pendiente o prueba). La vista activa se pinta con el foreground del tema (negro en claro, blanco en oscuro) y las reglas de las vistas viven **fuera de la consulta editable**, para que el operador no pueda desconfigurarlas. La acción **Añadir filtro** es un **botón circular «+»** (36 px, `rounded-full`, mismo fondo del tema) al final del renglón superior, junto a las vistas: los filtros que crea bajan al renglón de abajo. Abre el picker de campos con el título **«Crear filtro»** y **sin buscador de atributos**. La barra es la de ReUI (`filters` en variante básica, compuesta por piezas —`children` de `Filters` con `FilterChip` + `FiltersBuilder`— para intercalar tras cada filtro aplicado un **chip independiente con el conteo en cascada de instancias**: la primera regla cuenta sobre el listado completo y cada siguiente sobre el resultado de las anteriores; los chips se redondean a **cápsula**) con tres campos: **por estado** (Activo/Vencido/Pendiente/Prueba), **por distribuidor** —la lista real de resellers del panel vía el mapa usuario→reseller de `/users/validity` (`listFlujoResellers` devuelve `userResellers`; "Sin distribuidor" para los clientes propios del distribuidor)— y **por días para vencer** (igualdad, comparaciones, rango y vacío = sin dato; cualquier regla de días excluye siempre a los clientes vencidos, aunque el operador numérico los incluyera por días negativos; el picker lista los campos como «por …» para que el chip se lea como una frase); las opciones de Estado y Distribuidor llevan además el conteo global como subtítulo. Los chips creados no viven en la fila de arriba: cada uno baja al **renglón inferior** con su contador en un paquete indivisible, y el contenedor envuelve (`flex-wrap`), de modo que al no caber el filtro salta al renglón siguiente y la pila crece hacia abajo —siempre legible, sin escaparse en el scroll horizontal—; el renglón solo existe mientras haya filtros. Los filtros creados son **persistentes**: cada cambio de consulta se guarda en `localStorage` (`clientes.filtros.v1`) y al recargar la página se restaura el árbol guardado —se validan la forma y los campos (una regla de un campo que ya no existe en la barra se suelta, p. ej. «distribuidor» bajo alcance de distribuidor) y los ids se reasignan para no chocar con la fábrica de ids del nuevo montaje—; borrarlos («Todos» o la papelera del chip) también se guarda. El matching de operadores vive en un único criterio (`matchesFilterRule` en `src/components/lab/filter-utils.ts`, compartido con el Lab) que extiende los operadores numéricos (`eq/neq/gt/gte/lt/lte/between/not_between`) tratando `null` como "sin dato". El dato viene del mismo endpoint de la pestaña *Clientes* del Lab (`GET /api/flujotv/clients`); con perfil `distribuidor` el servidor ya entrega solo los clientes de su reseller ligado y la barra omite el campo **Distribuidor** (ver [Alcance de los datos FlujoTV por perfil](#alcance-de-los-datos-flujotv-por-perfil)). El CRUD de entidades umeJSON (lista con data-grid, creación, detalle con editor de propiedades y timeline) se retiró de la UI; el modelo, la API (`/api/entities`) y las tablas siguen vivos. La app **no tiene sidebar**: la navegación es una **barra inferior fija de cinco destinos** (Inicio, Módulos, Clientes, Finanzas, Ayuda) y el chrome del panel es una **cabecera sticky** con la mascota a la izquierda (enlaza a Inicio) y, a la derecha, la campana de notificaciones y el **avatar de la cuenta** (32 px, tamaño estándar de cabecera), cuyo menú desplegable contiene *Perfil*, *Saldo en tokens* y *Saldo en cupones* —los montos disponibles en vivo, solo si el usuario ve la sección Módulos—, un divider, *Usuarios* (solo admin), *Tema* y *Cerrar sesión* —sin repetir el rol, que ya no se muestra en ninguna parte del panel. Ver [Convenciones de UI](#convenciones-de-ui).
- **Menú en español**: la navegación se rotula en español y cada entrada lleva **icono + etiqueta visible** (`src/components/dashboard/nav-config.ts`, en este orden): *Inicio* (`HouseIcon`, ruta `/`), *Módulos* (`LayersIcon`; hub en `/modulos`, antes `/herramientas` — el proxy redirige las URLs viejas—), *Clientes* (`UsersRoundIcon`, ruta `/clientes`), *Finanzas* (`ChartNoAxesCombinedIcon`; pestañas *Estado de cuenta* con `ReceiptTextIcon` y *Gastos* con `TrendingDownIcon`) y *Ayuda* (`HandHelpingIcon`; pestañas *Asistente* con `BotIcon`, *Configuración* con `SettingsIcon` y *Lab* con `FlaskConicalIcon`). Cada sección declara una **clave estable** (`key`: `inicio`, `modulos`, `clientes`, `finanzas`, `soporte`) que viaja en los permisos por usuario, de modo que renombrar o mover rutas nunca rompe la configuración guardada. El botón *Clientes* apuntaba a las entidades umeJSON (`/entities`, rotuladas "Clientes" de cara al usuario); hoy apunta a la pantalla de **clientes del panel de FlujoTV** (`/clientes`), y `/entities` redirige a `/clientes` en el proxy. El modelo umeJSON, su API (`/api/entities`) y sus tablas siguen siendo `entities`. El acceso admin a `/users` vive **fuera de la barra inferior**, en el menú de la cuenta, con `UsersRoundIcon` (grupo de personas); *Perfil* usa `CircleUserRoundIcon` (una cuenta).
- **Cabecera sin fecha**: el margen derecho de la cabecera muestra solo la campana de notificaciones y el avatar de la cuenta — la fecha informativa (componente `app-header-date.tsx`, con su calendario popover) se retiró para dar aire al rótulo, y con ella su wrapper huérfano `src/lib/date-locale.ts`; el saldo disponible vive ahora dentro del menú del avatar (ver [Abonar saldo](#abonar-saldo)). A la izquierda de la cabecera va la mascota de la marca, que enlaza a Inicio (ver [Tema y marca](#tema-y-marca)); en *Clientes* y *Módulos*, el rótulo de la sección viaja en la cabecera, a la derecha de la mascota (`titleInHeader` en `nav-config.ts`), sin título ni texto explicativo dentro de la página; dentro de la sección Módulos, el rótulo es el del **módulo activo** resuelto del catálogo (`findNavModulo` en `nav-config.ts` sobre `MODULOS`: «Animación», «Calculadora», «Abonar saldo», …; el propio hub conserva «Módulos»), así que al entrar a una herramienta la cabecera nunca se queda en el rótulo genérico; sobre esas rutas el rótulo se convierte, junto a un chevron, en un **único botón de regreso** al hub (`findNavBack` en `nav-config.ts`, dibujado por `dashboard-shell.tsx`: chevron + rótulo dentro del mismo `Button` ghost enlazado; ver el **Hub de módulos** en [Características](#características)). Ver [Convenciones de UI](#convenciones-de-ui).
- **Modo oscuro global**: tema claro/oscuro/sistema en toda la app, incluidos los módulos futuros (ver [Tema y marca](#tema-y-marca)).
- **Perfil de usuario** (`/profile`): pestañas *Detalles*, *Información* y *Seguridad* (variante `line` de ReUI). Ver [Perfil de usuario](#perfil-de-usuario).
- **Asistente LLM** (`/soporte/asistente`, pestaña *Asistente* de la sección *Ayuda* de la barra inferior): chat estilo ChatGPT. Streaming token a token vía OpenRouter (`ASISTENTE_MODEL`, `OPENROUTER_API_KEY` en `.env`), respuestas en Markdown (renderizadas al terminar cada respuesta; texto plano durante el streaming), historial efímero y rate limit de 20 mensajes/min por usuario con timeout de inactividad de 30 s hacia el proveedor. El modelo se cambia solo editando `ASISTENTE_MODEL` en `.env` y reiniciando (`pm2 restart distribuidor-tvbox`); con modelos de razonamiento (p. ej. `meta/muse-spark-1.3-contributor`) la respuesta visible llega tras la fase interna de *thinking*, que el servidor mantiene viva. El panel tiene altura fija (**alto útil − cabecera − barra inferior − pestañas de sección**, con `--shell-viewport-height` y `--shell-section-tabs-height`): el transcript hace scroll por dentro, con auto-scroll al borde durante la respuesta y botón para volver al final; funciona igual en desktop y móvil (la página nunca crece más allá del viewport). **Acceso a datos por herramientas (tool-calling)**: `registrar_gasto`, `consultar_gastos` y `resumen_gastos` (`src/server/asistente/tools.ts`) se ejecutan siempre en el servidor con el `user_id` de la sesión inyectado — el modelo nunca ve ni toca datos de otros usuarios — y los errores de herramienta se devuelven como JSON para que el asistente los explique sin romper la respuesta. Máximo 4 llamadas al proveedor por turno; el prompt de sistema incluye la fecha actual de Ciudad de México para resolver fechas relativas. Ver [Control de gastos](#control-de-gastos).
- **Gestión de usuarios** (`/users`, solo admin): listado en data-grid ReUI con búsqueda por email y filtro por rol; alta en dialog, edición (email, rol, contraseña) y baja con confirmación en `AlertDialog`. Las acciones de cada fila viven en un **menú contextual de tres puntos** (`EllipsisVerticalIcon`, `DropdownMenu` alineado a la derecha) con: **Saldo**, **Permisos** (escudo), **Editar** (lápiz) y **Eliminar** (papelera, destructiva — oculta en la fila de la propia cuenta). *Permisos* abre una **matriz de visibilidad de secciones**: un switch por entrada de la barra inferior (Inicio, Módulos, Clientes, Finanzas, Ayuda) con su descripción; guardar persiste una fila por sección en `user_section_permissions` (`db/permissions-schema.sql`) y la barra del usuario afectado se redibuja sin esas entradas (el grid ajusta sus columnas) y, vía el evento `users` del bus de tiempo real, **la sesión abierta de ese usuario refresca su navegación al instante**, esté en web o mobile (ver [Sincronización en tiempo real](#sincronización-en-tiempo-real)). Sin filas = acceso completo; las cuentas **admin siempre ven todo** (aviso visible en el diálogo); no se puede dejar al usuario sin ninguna sección. Los permisos solo ocultan la navegación: las rutas siguen servidas por URL. Protecciones en servidor: no se puede borrar la propia cuenta ni degradar/eliminar al último `admin`; el email debe ser único. Al editar una cuenta se actualiza en la misma transacción el usuario de autenticación y su entidad umeJSON `Cuenta` (espejo de `email`/`role` con evento `property.updated`); al eliminarla se archivan (soft-delete) todas sus entidades —incluida su `Cuenta`— con evento `entity.deleted`, y solo después se borra el usuario. La opción **Saldo** del menú acredita saldo **directamente, sin checkout**: diálogo con los saldos vigentes (tokens y cupones), selector de tipo y monto (ver [Abonar saldo](#abonar-saldo)); el movimiento queda como ajuste con el admin responsable en `saldo_movimientos.created_by`.
- **Almacenamiento de archivos por usuario**: cada cuenta tiene su propio folder en el servidor (`storage/users/<userId>/`, raíz configurable con `USER_FILES_DIR`) con subcarpetas `attachments/` (adjuntos subidos) y `generated/` (imágenes y archivos generados por IA). El folder se crea al registrar la cuenta, al ejecutar `node db/ensure-user-storage.mjs` (cartera de cuentas existentes) y de forma perezosa en el primer guardado; se elimina junto con la cuenta. Los archivos se indexan en la tabla `user_files` (`db/storage-schema.sql`) y se sirven solo al usuario de la sesión vía `/api/files`. Ver [Almacenamiento por usuario](#almacenamiento-por-usuario).
- **Hub de módulos** (`/modulos`, destino del botón *Módulos* de la barra inferior; antes `/herramientas` — el proxy redirige el hub y sus subrutas—): listado de herramientas sobre el mismo acordeón de `/clientes` (`c-accordion-9` de ReUI, una fila por herramienta, una sola abierta a la vez). Cada fila lleva el icono en tile (`size-12`, `bg-muted`), el nombre como título y la descripción breve como subtítulo; **la fila completa es un enlace (`Link`) que ejecuta la herramienta al pulsarla**. Al margen derecho van la **estrella de favoritos** y el botón settings-2 de lucide, que es el trigger del acordeón y despliega dos acciones maqueta sin funcionalidad: *Configurar* (fantasma) y *Eliminar* (destructive). Encima del acordeón, en el renglón de arriba, vive el **buscador con la misma composición de `/clientes`**: una píldora `InputGroup` (`h-12 max-w-xs flex-1 rounded-full bg-muted`, dentro del mismo renglón flex de `/clientes` para que `flex-1` y `h-12` resuelvan las mismas dimensiones) con **icono de lupa** a la izquierda, *placeholder* «Buscar» y **botón de limpieza (X)** que aparece solo con texto; filtra por **nombre y descripción** del módulo en comparación **sin acentos ni mayúsculas** (`foldTerm`, «calculo» encuentra «Calculadora») y **acota sobre la vista activa**: la búsqueda vive encima de la barra de vistas, de modo que «Favoritos» + «calcul…» devuelve solo los favoritos que coinciden; sin resultados muestra el aviso propio («Ningún módulo coincide con la búsqueda»). Debajo, la **barra de filtros con la misma composición de `/clientes`**: vistas en cápsulas `ToggleGroup` outline con **contador** (`Badge`) —*Todos* (3), *Favoritos* y los filtros creados—, la vista activa pintada con el foreground del tema y **radio fijo** (pulsar la vista activa no la suelta), más el botón circular **«+»** que abre *Crear filtro*: un dialog con nombre (valida vacío y duplicados) que da de alta una **categoría** nueva y la añade como vista. La **estrella** junto al nombre marca el favorito (rellena, `aria-pressed`; es hermana del enlace, nunca un botón dentro del `<a>`). El **clic sostenido (~0.5 s) sobre un módulo** abre el dialog *Asignar a filtros* (checkboxes con los filtros creados, selección múltiple; vibración háptica en móvil); el gesto cancela si hay arrastre > 10 px y suprime el click posterior para que no navegue ni expanda el acordeón; **si no hay filtros creados no hace nada**. Favoritos, filtros y asignaciones viven **en el servidor, por usuario** (tabla `user_module_prefs`, `db/module-prefs-schema.sql`; ver [Sincronización en tiempo real](#sincronización-en-tiempo-real)): se sincronizan entre web y mobile al instante y cada guardado se difunde por el bus SSE (evento `prefs`, solo-propietario). La primera visita tras el cambio migra lo que hubiera en `localStorage` (`modulos.filtros.v1`) al servidor y limpia la clave. La validación (`normalizeModulePrefs` en `src/lib/modulos.ts`, compartida por cliente y servidor) suelta favoritos/asignaciones desconocidos. El catálogo vive en `src/lib/modulos.ts` (el directorio de componentes conserva el nombre histórico `herramientas`); hover y foco con `transition-colors` + `focus-visible` ring sobre tokens semánticos, sin motion de entrada. La sección **no tiene pestañas** y el índice no redirige (el hub es la página de la sección; `/finanzas` y `/soporte` sí siguen redirigiendo a su primera pestaña): su rótulo *Módulos* viaja en la cabecera, a la derecha de la mascota (`titleInHeader` de la sección en `nav-config.ts`). Sobre las rutas de herramienta la cabecera muestra el **nombre del módulo activo** (`findNavModulo` en `nav-config.ts`, resuelto contra el catálogo `MODULOS`: «Animación», «Calculadora», «Abonar saldo», …), y el botón de regreso al hub mantiene el chevron. Agregar una herramienta nueva es añadir una entrada al catálogo (título, descripción, `href`, icono; `adminOnly: true` para las que solo ven las cuentas **admin** — el hub filtra el catálogo por rol y la ruta queda detrás de su guard de rol, como *Distribuidores*, ver [Distribuidores](#distribuidores)) y su página bajo `/modulos/<ruta>`.
- **Imágenes con IA** (`/modulos/imagenes`, pestaña *Imágenes* de la sección *Módulos* de la barra inferior): generador de imágenes vía **Vercel AI Gateway** (`AI_GATEWAY_API_KEY` en `.env`, modelos de `IMAGE_MODELS`) con prompt, relación de aspecto, **control de calidad de dos niveles** (*Media* / *Alta*, un grupo de botones alternos —toggle— con el nivel activo presionado: elige el modelo, no el nivel de render) y **hasta 4 imágenes de referencia** (botón + en una celda propia del área de texto, que el modelo recibe como parte del prompt). La página se organiza en dos pestañas, *Generar* y *Galería*, con el mismo patrón de pestañas de `/profile` (variante `line`, paneles `keepMounted`; la barra es **fija** —*sticky*— bajo la cabecera de la app; ver [Convenciones de UI](#convenciones-de-ui)). La pestaña *Generar* no lleva encabezado propio (el nombre *Imágenes* solo queda como `h1` para lectores de pantalla) y su card se titula *Descripción*. El botón principal de la card es **de dos pasos**, con una pista de progreso encima (stepper ReUI en modo display: ① investigar → ② generar): *Investigar y mejorar descripción* (paso 1) **investiga en internet** lo que pide el usuario y reescribe el prompt con los datos reales; cuando el texto ya está procesado, el mismo botón cambia a *Generar* (paso 2) y editar la descripción lo regresa al paso 1. Bajo el botón, el enlace discreto *Generar sin procesar* (visible solo con texto sin procesar) genera directamente, para prompts que no necesitan investigación (ver [Insertar detalles](#imágenes-con-ia)). Cada imagen se guarda en `storage/users/<userId>/generated/` vía `saveUserFile` (kind `generated`) y se sirve por `/api/files`; la galería es automática por usuario (tabla `image_generations`, `db/images-schema.sql`). Tarificador: cada generación registra el costo real que reporta el gateway (`providerMetadata.gateway.cost` en USD) y la UI lo presenta **en pesos mexicanos**, convertido con el tipo de cambio FIX de Banxico del día de uso (`BANXICO_TOKEN` en `.env`). Además, cada costo se **espeja automáticamente al control de gastos** del usuario (categoría *Imágenes*, `created_by: "sistema"`), por lo que también aparece en Gastos, Estado de cuenta y en los reportes del asistente. Borrar una imagen es un soft-delete: sale de la galería y libera su archivo, pero el costo permanece en el acumulado; si el binario no pudiera guardarse, el costo igualmente queda registrado (fila sin `file_id`, excluida de la galería). Cada imagen se guarda además en **dos versiones derivadas** (versión en baja resolución y miniatura, WebP, derivadas con sharp): la galería carga solo miniaturas y el visor abre la versión baja, así que con cientos de imágenes el celular no se satura; el pie del visor ofrece **dos descargas** —la versión baja y el original— y tocar la imagen en el visor la abre a **pantalla completa** (ver [Variantes de las imágenes](#variantes-de-las-imágenes)). Rate limit de 6 imágenes/min por usuario. Ver [Imágenes con IA](#imágenes-con-ia).
- **Configuración** (`/soporte/configuracion`, pestaña *Configuración* de la sección *Ayuda* de la barra inferior): página con **menú interno de secciones** —*Modelos de imagen* y *API de licencias*— y sus URLs propias. La sección de modelos define, **por nivel del control de calidad** de Imágenes (*Media* y *Alta*), el **modelo**, la **calidad de render** y el **tamaño de salida**. La selección vive en `user_settings` (`db/settings-schema.sql`, columna JSONB `image_levels`), es por usuario y el servidor la aplica al generar: lo que se manda al gateway es lo configurado para el nivel elegido. La sección **API de licencias** pide la clave de la API de FlujoTV, la comprueba contra el servicio y la guarda **cifrada** (AES-256-GCM) en `flujotv_settings` para activar el módulo de licencias del Lab. Ver [Configuración por usuario](#configuración-por-usuario).
- **Animación con agente EVE** (`/modulos/animacion`, pestaña *Animación* de la sección *Módulos* de la barra inferior): chat con un agente [EVE](https://eve.dev) montado same-origin en `/eve/v1/*` vía `withEve()` en `next.config.ts`. El área de texto incluye un **ícono de papel clip** para adjuntar archivos al turno (eve los deja en el sandbox de la sesión y el agente los lee con `read_file`/`bash`). El agente **produce video real** con el toolkit claude-motion (skills de motion design, review loop, sonido y sims) en un sandbox Docker con ffmpeg, Python y Chromium, y entrega los archivos por chat con `guardar_archivo` → `/api/files/<id>` con reproductor inline. La página usa el patrón de dos pestañas *Agente* / *Galería*: todos los entregables se indexan en `animation_deliverables` (`db/animation-schema.sql`) y aparecen en la galería con su **costo en MXN** (tarificador por turno con FIX de Banxico, espejado al control de Gastos con categoría *Animación*) y su **tiempo de trabajo** (cronómetro en vivo durante el turno y total persistido por conversación). El control **Presupuesto** (arriba del área de texto) elige el modelo **por turno** con un slider de tres pasos (**bajo**, **medio**, **alto**): cada paso corresponde, en el orden de `ANIMATION_MODELS`, a un modelo del catálogo, así que el usuario elige cuánto gasta y no el nombre del modelo. La elección viaja como `clientContext` y un resolver dinámico de eve la aplica antes de cada llamada, con el **nivel de razonamiento máximo que reporta el AI Gateway para ese modelo** fijado explícitamente en cada request. Junto al cronómetro, el **tarificador en vivo** muestra el costo acumulado de la conversación en MXN mientras el agente trabaja. Las herramientas por defecto de EVE están desactivadas (`defaultTools: false`); se habilitan `bash`, `read_file` y `write_file`. El agente vive en `agent/` (`instructions.md`, `agent.ts` con el modelo dinámico de Vercel AI Gateway, `agent/skills/`, `agent/sandbox/` con el Dockerfile y la semilla del toolkit, `agent/tools/`, `agent/hooks/tarificador.ts` y `agent/channels/eve.ts`, que valida la misma cookie de sesión del panel contra Postgres, liga cada sesión EVE a su creador en `eve_sessions` y limita a 20 mensajes/min por usuario) y su estado durable se guarda en `.eve/.workflow-data`. Requiere `AI_GATEWAY_API_KEY` y `ANIMATION_MODELS` en `.env`; el middleware excluye `/eve/` y `/.well-known` del redirect a `/login` para que la API responda 401 en lugar de redirigir. Ver [Animación con agente EVE](#animación-con-agente-eve).
- **Calculadora** (`/modulos/calculadora`, herramienta *Calculadora* del hub de Módulos): cálculos rápidos con porcentaje comercial, desde botones circulares o teclado físico, **a pantalla completa** (regreso en la cabecera al hub): durante la operación la línea grande muestra lo tecleado (`25+2,500`) con el **resultado previo** debajo en gris (`2,525`), y al pulsar `=` queda solo el resultado en grande con **miles con coma**. Todo el cálculo ocurre en el navegador con una máquina de estados pura y probada (`scripts/test-calculadora.mjs`), sin `eval` ni parser de expresiones: las operaciones se encadenan en orden de pulsación (`2 + 3 × 4 = 20`). Ver [Calculadora](#calculadora).
- **Lista de compras con IA** (`/modulos/lista-de-compras`, herramienta *Lista de compras* del hub de Módulos): una sola lista persistente por usuario que se alimenta **escribiendo o dictando** en un área de texto con micrófono integrado; la IA interpreta la instrucción (`agrega 2 kg de tomate, leche y 12 huevos`, `cambia a 3`, `ya compré el pan`, `nueva lista para desayunar`, `limpia la lista`) y la convierte en operaciones acotadas sobre la lista real. Productos agrupados por categoría de supermercado, casillas circulares de comprado, barra de progreso que celebra el 100 % con confeti, y botón *Nueva* para empezar de cero con confirmación. Fiel al pedido: sin cantidades ni productos inventados, y las operaciones destructivas **siempre piden confirmación** derivada en servidor. Ver [Lista de compras con IA](#lista-de-compras-con-ia).
- **Alta de tickets con IA** (`/modulos/alta-de-tickets`, herramienta *Alta de tickets* del hub de Módulos): registra tickets de compra/gasto **subiendo la foto** —dos vías de captura: *Tomar foto* (abre la cámara del celular vía `capture="environment"`; en escritorio cae al selector) o *Elegir archivo*— y la IA extrae los datos en un documento umeJSON estructurado (comercio, fecha/hora, folio, moneda, partidas, impuestos, totales y forma de pago) que el propietario **revisa, corrige y confirma**. Fiel a la foto: lo ilegible queda `null` (nunca un cero inventado), la moneda solo si está impresa, la fecha ambigua se descarta con aviso y la conciliación aritmética (partidas↔subtotal, total↔desglose, cantidad×precio) avisa en vez de corregir. La foto es privada del propietario (ni un admin la ve) y no caduca con el sweep de adjuntos. Ver [Alta de tickets con IA](#alta-de-tickets-con-ia).
- **Lab** (`/soporte/lab`, pestaña *Lab* de la sección *Ayuda* de la barra inferior): **página vacía**, lista para alojar contenido nuevo; ya no redirige (su guard de admin —que enviaba a `/clientes` a quien no lo era— se retiró) y el índice de módulos en prueba se dio de baja junto con su catálogo (`src/lib/lab.ts`, eliminado). La consola *API FlujoTV* sigue viva en `/soporte/lab/flujotv` (**solo admin**: permite operar la API de licencias sin pasar por el cobro) y hoy se alcanza desde *Configuración → API de licencias* con el botón *Abrir API FlujoTV*. La renovación se cobra con Mercado Pago desde `/clientes`; el Lab no tiene herramienta de renovación directa. Ver [Lab](#lab).
- **Finanzas** (`/finanzas/estado-de-cuenta`, sección *Finanzas* de la barra inferior): **Gastos** y **Estado de cuenta** como pestañas de la sección; **Ganancias** y **Método de pago** siguen como páginas de estructura. La navegación vive en `navSections` (`src/components/dashboard/nav-config.ts`). Ver [Control de gastos](#control-de-gastos).
- **Sincronización en tiempo real (web + mobile)**: la misma app abierta en dos dispositivos refleja los cambios del uno en el otro al instante — clientes, gastos, órdenes de Mercado Pago (incluida la renovación que aplica el webhook), usuarios/permisos y favoritos/filtros de Módulos. Server-Sent Events + `LISTEN/NOTIFY` de Postgres; el otro dispositivo no espera a recargar. Ver [Sincronización en tiempo real](#sincronización-en-tiempo-real).
- **Reembolsos de Mercado Pago** (sección **Reembolsos** de `/clientes`, solo admin): devolución **total** del cobro vía la API de pagos de MP cuando la renovación de la licencia falló con el pago confirmado (`renewal_failed`) — nunca de una orden ya renovada. Reclamo atómico a `refunding` que bloquea reintentos de renovación en paralelo, auditoría en `mp_refunds` y conciliación de reembolsos interrumpidos contra la API de MP. Ver [Reembolsos](#reembolsos).
- **Paquetes FlujoTV** (`/modulos/paquetes-flujotv`, herramienta del hub de Módulos): renovaciones en paquete de **3, 6 y 12 meses con meses de regalo** (3 sin regalo, 6 +1 gratis, 12 +2 gratis) sobre la misma estructura de compra de `/clientes` (listado de clientes, carrito y bottom sheet con los tres métodos de pago; el cupón **1010** lo asigna el sistema). La orden paga solo los meses del paquete y la renovación aplica el total (pagados + gratis) como plan de renovaciones idempotentes; el canje de paquete por cupón responde al instante y renueva desacoplado. Ver [Paquetes FlujoTV](#paquetes-flujotv).
- **Abonar saldo** (`/modulos/abonar-saldo`, herramienta del hub de Módulos, `PiggyBankIcon`): el **mismo checkout de siempre** (Mercado Pago, transferencia o cupón) pero el comprador **define el monto y el tipo de saldo** y el crédito se acredita en **su propia cuenta del panel** (dos billeteras: `users.saldo_tokens` para herramientas con APIs externas y `users.saldo_cupones` para licencias FlujoTV, más el libro mayor `saldo_movimientos`; alcance de esta entrega: solo acumular — aún no hay gasto con saldo). Con Mercado Pago el cargo se engrosa para que depositen exactamente los pesos definidos; la transferencia acredita el importe transferido tras concepto+comprobante; el cupón QA acredita al instante. Toda orden de abono vive en `mp_orders` con `months = 0`, guarda su billetera destino en `saldo_tipo` y termina en el estado nuevo `applied`. Ver [Abonar saldo](#abonar-saldo).
- **Revisión automática del comprobante de transferencia** (carrito de renovación de `/clientes`): flujo de **dos pasos** — primero el **concepto de pago**, un código de 4 caracteres ligado al comprador + usuario + mes (`POST /api/transferencias/concepto`: idempotente en el mes, TTL mensual, se anula al aprobarse o rechazarse la transferencia; el comprador escribe **solo el código** como concepto) — y después la subida del ticket, que un modelo de visión (`RECEIPT_SCAN_MODEL` vía AI Gateway) escanea y el servidor verifica en código —estricto solo en **fecha del mes actual, concepto con el código de pago e importe**; el beneficiario es tolerante (iniciales «E. Ortiz»/«Enrique O», origen/destino implícito, sin beneficiario legible no bloquea)— con dedup por sha256 y tope de 3 escaneos/min por comprador. Todo pasa → orden `paid` y renovación lanzada sola; algo falla → orden `pending` para la revisión manual del admin, con el aviso al comprador de contactarlo. La app queda **bloqueada por etapas** (comprobante → renovación → resultado, timeline vertical) hasta el 100% del proceso: solo el panel final libera, y el bloqueo sobrevive a una recarga. Ver [Concepto de pago de la transferencia](#concepto-de-pago-de-la-transferencia-paso-1) y [Revisión automática del comprobante](#revisión-automática-del-comprobante-transferencia).
- **Notificaciones de renovación** (campana de la cabecera, a la izquierda del avatar): feed **persistente** por comprador con el resultado de cada renovación — **éxito** (con el vencimiento nuevo verificado en el panel) o **fallo** (con el motivo y la sugerencia de reintento), el usuario FlujoTV renovado y el tiempo relativo de creación — para las compras de `/clientes` y los paquetes de `/modulos/paquetes-flujotv` (Mercado Pago, transferencia aprobada o rechazada, cupón, reintentos y conciliación). Cuando la validación automática rechaza un comprobante de transferencia, además del aviso al comprador se inserta una **copia en la campana de cada admin** con los motivos en detalle para agilizar la revisión manual. Insignia con el contador de no leídas, refresco en vivo por el evento SSE `notifications` (solo-propietario) y acciones estándar: *Marcar leídas* (una fila o todas) y *Borrar* (una fila o todas, con confirmación). Ver [Notificaciones de renovación](#notificaciones-de-renovación).
- **Conectores** (`/modulos/conectores`, herramienta del hub de Módulos, `PlugZapIcon`): catálogo de integraciones **por proveedor** con conexiones OAuth **por usuario** — Google Calendar disponible y Google Drive / Outlook Calendar como *Próximamente* para marcar la estructura. Tokens cifrados AES-256-GCM en reposo, flujo OAuth propio con estado anti-CSRF y revocación en Google al desconectar. Ver [Conectores](#conectores).
- **Distribuidores** (`/modulos/distribuidores`, herramienta del hub de Módulos, `UserCogIcon`, **solo admin**): las cuentas con rol `distribuidor` de `/users` listadas con las filas de `/clientes` (avatar pastel de iniciales, panel FlujoTV ligado con punto de estado, clientes asignados, saldos al expandir) y gestionadas con el mismo menú contextual de `/users` (Saldo, Permisos, Editar, Eliminar) tras el botón settings-2 que ocupa el lugar del carrito de compra. Primera entrada `adminOnly` del catálogo de módulos: el hub la oculta a cuentas no admin y la ruta redirige. Ver [Distribuidores](#distribuidores).

## Requisitos

- Node.js 24+ (requisito de EVE; `package.json` declara `engines.node: 24.x`)
- PostgreSQL 16

```bash
psql "$DATABASE_URL" -f db/saldo-tipos-schema.sql       # Dos billeteras de saldo (users.saldo→saldo_cupones renombrada + users.saldo_tokens, mp_orders.saldo_tipo y saldo_movimientos.tipo; requiere saldo)
psql "$DATABASE_URL" -f db/notifications-schema.sql   # Notificaciones de renovación de la campana (una fila por evento dirigida al comprador; los rechazos automáticos de transferencia copian además una fila a cada admin; solo depende de auth)
psql "$DATABASE_URL" -f db/coupon-limit-schema.sql        # Tope diario de cupones por usuario (users.coupon_daily_limit; requiere auth)
psql "$DATABASE_URL" -f db/coupon-monthly-limit-schema.sql # Tope mensual (acumulado 30 días) de cupones por usuario (users.coupon_monthly_limit; requiere auth)
psql "$DATABASE_URL" -f db/module-prefs-schema.sql # Preferencias del hub Módulos (favoritos/filtros; solo depende de auth)
psql "$DATABASE_URL" -f db/shopping-list-schema.sql # Lista de compras con IA (una lista por usuario + log de mutaciones idempotentes; solo depende de auth)
psql "$DATABASE_URL" -f db/tickets-schema.sql      # Alta de tickets (control de TicketCompra: vínculo con la foto, idempotencia request_id, sha256 y lease del análisis; requiere entities, auth y storage)

# 5. Desarrollo o producción
npm run dev            # http://localhost:3000
npm run build && npm run start   # compila el agente EVE y luego Next.js; respeta PORT (default 3000)
```

El login vive en `/login` y siempre es una cuenta de correo; desde ahí se enlaza a `/register` para crear cuenta. Toda cuenta nueva nace con perfil `distribuidor` y su entidad umeJSON `Cuenta`; el resto de rutas redirigen a `/login` si no hay sesión. La página está **íntegramente en español** —títulos, labels, botón, enlace a registro y también los **errores del server action** (`loginAction` en `src/app/actions/auth.ts`: *"Credenciales incorrectas"*, *"Ingresa un correo electrónico válido"*, etc.), que son los textos que se pintan bajo el formulario.

## Roles

| Rol | Alcance |
|---|---|
| `admin` | Ve y edita todas las entidades; gestiona usuarios en `/users` (crear, editar y eliminar) y las cuentas distribuidoras en `/modulos/distribuidores` (el menú de `/users` sobre filas de `/clientes`) |
| `distribuidor` | Solo ve y edita las entidades que él crea (el servidor estampa `dynamicProperties.distribuidorId` al crear y filtra con el índice GIN). El scoping se aplica tanto en la API como en la página SSR de detalle y su timeline de eventos |

El autorregistro (`/register`) crea cuentas únicamente como `distribuidor`; solo un `admin` puede elevar el perfil después.

### Ligazón usuario ↔ distribuidor (reseller FlujoTV)

En `/users`, el diálogo **Edit user** incluye un campo **Distributor**: un dropdown con los resellers reales del panel FlujoTV (`GET /api/flujotv/resellers`, que la app consulta al abrir el diálogo, con estados de carga/error y el valor actual siempre presente aunque la lista falle). La opción **Not linked** desliga la cuenta. La tabla muestra el vínculo vigente en la columna **Distributor** (`—` si no hay).

Reglas de la ligazón:

- **Persistencia**: el nombre elegido vive en `dynamicProperties.distribuidorName` de la entidad umeJSON `Cuenta` del usuario (vacío = sin ligar). Lo escribe `updateAccount` (`src/server/auth/accounts.ts`) con el mismo protocolo de lock optimista y evento `property.updated` que email/role; `listUsers` (`src/server/auth/users.ts`) lo lee con un JOIN contra la entidad Cuenta y lo expone en `/users`.
- **Entidad canónica**: las tres rutas de lectura/escritura del vínculo (`listUsers`, `getAccountDistribuidorName`, `findAccountEntityId`) exigen que la entidad Cuenta cumpla `userId = distribuidorId = usuario`, como siempre deja `buildAccountDraft`, de modo que documentos ajenos no puedan hacerse pasar por la cuenta de otro.
- **Nombre reservado**: `Cuenta` solo lo crea el flujo interno de cuentas (`createAccount`). Un no-admin que lo intente vía `POST /api/v1/ume-json/finalize` o que parche una entidad `Cuenta` vía `PATCH /api/entities/[id]` recibe `403 reserved_entity_name` (documentado en la tabla de API).
- **Errores explícitos**: si el usuario no tiene entidad Cuenta viva (p. ej. cuentas de semilla), ligar un distribuidor devuelve error en el formulario (`account_entity_missing`) en lugar de reportar éxito sin persistir; cambiar solo email/role/password mantiene el comportamiento de siempre.
- **Contrato cliente/servidor**: el valor "sin distribuidor" viaja con el sentinel compartido `DISTRIBUTOR_LINK_NONE` (`src/lib/distributor-link.ts`), usado a la vez por el formulario (`users-list.tsx`) y el server action (`updateUserAction`), y nunca se persiste.

### Alcance de los datos FlujoTV por perfil

Los datos del panel de FlujoTV (clientes, licencias, resellers y renovaciones) se **filtran en el servidor** según el perfil de la sesión (`resolveClientScope` en `src/server/flujotv/scope.ts`): el navegador nunca recibe datos fuera de alcance, aunque llame a la API directamente.

- **`admin`**: sin restricción; ve el panel completo.
- **`distribuidor` ligado a un reseller** (`dynamicProperties.distribuidorName` de su entidad Cuenta, p. ej. `dist01@tvbox.network` → `eortizs`): solo ve los **clientes asignados a su distribuidor**. La atribución cliente→reseller se resuelve con la llave cruda de la fila del panel (`distributor`/`distribuidor`; nunca `reseller`, que es la cuenta padre) y, si la fila no la trae, con el mapa usuario→reseller de `/users/validity` (`getFlujoUserResellers` en `service.ts`, una sola lectura tolerante a fallos: sin mapa solo cuentan las llaves crudas). La comparación es insensible a mayúsculas.
- **`distribuidor` sin ligar**: no ve ningún cliente — mostrar el panel completo filtraría datos de otros distribuidores.

Aplicación por ruta:

| Ruta | Efecto del alcance |
|---|---|
| `GET /api/flujotv/clients` | Lista filtrada; el `total` reportado pasa al conteo filtrado. El mapa de nombres propios `clientNames` (columna Notas vía `/client_names`) se acota a los usuarios del alcance: un distribuidor no recibe nombres de clientes fuera de su cartera |
| `GET /api/flujotv/clients/[userName]` | Un cliente fuera de alcance responde como inexistente (`client: null`), sin revelar si existe |
| `POST /api/mercadopago/orders` | `403` si el cliente no pertenece al distribuidor (o sin atribución posible); se comprueba antes de crear la orden y la preferencia de pago |
| `GET /api/flujotv/resellers` | Solo la fila del reseller ligado y su subconjunto del mapa `userResellers` (sin exponer otros resellers ni asignaciones ajenas) |
| `GET /api/flujotv/licenses` | Solo las licencias de usuarios del distribuidor, con el mismo criterio de atribución |

En la pantalla **Clientes** (`/clientes`) la página resuelve el alcance en el servidor y pasa el nombre del distribuidor al acordeón (`distribuidorName`): con perfil distribuidor la barra omite el filtro **Distribuidor** —todas las filas comparten el mismo— y no consulta `GET /api/flujotv/resellers`, cuyo listado completo no le compete al perfil; sin clientes ligados muestra el estado vacío «Sin clientes asignados». El admin no nota ningún cambio.

## Perfil de usuario

Página `/profile` (enlace **Perfil** en el menú de la cuenta, en la cabecera), organizada en tres pestañas (patrón ReUI `c-tabs-2`, variante `line`). Es el patrón de pestañas **canónico de la app**: todas las vistas con pestañas lo replican (ver [Convenciones de UI](#convenciones-de-ui)):

| Pestaña | Contenido |
|---|---|
| **Detalles** (por defecto) | Lectura sola: email, rol (badge), fecha de alta y última actualización de la entidad Cuenta |
| **Información** | Email (solo lectura: es el identificador de login), nombre completo y teléfono, editables |
| **Seguridad** | Cambio de contraseña: actual + nueva (mín. 8, distinta de la actual) + confirmación |

Persistencia y reglas:

- Los datos de perfil (`fullName`, `phone`) viven en `dynamicProperties` de la entidad umeJSON `Cuenta` del usuario (localizada por `dynamicProperties.userId`); no requieren migración de esquema.
- Cada guardado pasa por `updateProperties` del repositorio: bloqueo optimista por `version` (conflicto → error al usuario) y evento `property.updated` con diff `from`/`to` en `entity_events`, con `actor` = email de la sesión y `reason: "Profile updated"`. Si la entidad Cuenta no existe, se crea con el mismo draft que el registro.
- La contraseña se cambia solo tras verificar la actual contra el hash scrypt; el nuevo hash se escribe con `updatePassword` (`src/server/auth/users.ts`). Las sesiones activas no se invalidan.
- Validación en el server action (`src/app/actions/profile.ts`): nombre ≤ 100 caracteres, teléfono opcional con formato flexible (`+`, dígitos, espacios, paréntesis, guiones; 7–20), y ninguna mutación sin sesión (`requireUser`).
- Formularios cliente con `useActionState`, estado pendiente, error inline (`role="alert"`) y toast de éxito con `router.refresh()` para recargar los datos; los paneles usan `keepMounted` para no perder lo tecleado al cambiar de pestaña.
- Iniciando sesión con Google, el **nombre completo** (`fullName` de la entidad Cuenta) y la **foto** (`users.google_picture`, avatar del menú de la cabecera) se capturan del perfil de Google: el nombre solo se rellena si el campo está vacío — nunca pisa una edición manual, y cada llenado queda en el historial (`reason: "Nombre completo desde Google"`)— y la foto se refresca en cada inicio si cambió. Ver [Autenticación con Google](#autenticación-con-google).

## Autenticación con Google

Botón **«Continuar con Google»** en `/login` y `/register`, sobre las sesiones existentes (OAuth 2.0 *authorization code* implementado a mano en `src/server/auth/google.ts`, sin dependencias de terceros). Requiere `GOOGLE_CLIENT_ID` y `GOOGLE_CLIENT_SECRET` en `.env` (Google Cloud Console → Credenciales → ID de cliente OAuth tipo «Aplicación web», con la URI de redirección autorizada `SITE_URL + /api/auth/google/callback`); sin las dos variables el botón se oculta y `GET /api/auth/google/start` redirige a `/login?error=google_disabled`.

- **Flujo** (`src/app/api/auth/google/start/route.ts` + `callback/route.ts`): el inicio fija el estado anti-CSRF en una cookie httpOnly de 10 minutos (comparación timing-safe, un solo uso) y manda al consentimiento de Google con `prompt=select_account`; el callback valida el estado, canjea el código y verifica los claims del `id_token` (iss, aud, exp y **correo verificado obligatorio**). Ambos handlers llaman `await connection()`: con `cacheComponents` activo, sin una API de request-time se prerenderizarían en el build y servirían para siempre la respuesta congelada (p. ej. el guard `google_disabled` si las credenciales no existían al compilar); `export const dynamic` no es compatible con este proyecto.
- **Resolución de la cuenta**, en orden: 1) por `users.google_sub`; 2) cuenta local con el mismo correo → **vínculo con prueba de propiedad** (ver abajo); 3) cuenta nueva con perfil `distribuidor` y sin contraseña local. Carrera de creación (otra petición registró el correo entre la consulta y el INSERT): se reintenta la resolución sobre la fila existente en vez de fallar.
- **Vínculo con prueba de propiedad**: el vínculo automático por correo sin verificar permitiría que una cuenta autoregistrada se adelantara a la cuenta real de su dueño. Cuando el correo de Google coincide con una cuenta local sin `google_sub`, el callback deja la identidad pendiente firmada en una cookie (HMAC-SHA256 con `GOOGLE_CLIENT_SECRET`, 10 minutos; **falla cerrado** si el secreto falta) y redirige a `/login?error=google_link_required`; al iniciar sesión con la contraseña correcta, `loginAction` verifica la firma y el correo del token y enlaza `google_sub`. Cuentas ya ligadas a otro sub devuelven `google_linked_other`.
- **Foto y nombre**: `users.google_picture` alimenta el avatar del menú de la cabecera (Base UI `Avatar`, iniciales como fallback mientras carga o si falla) y se refresca en cada inicio si difiere. El `id_token` a veces omite `picture` (típico en re-consentimientos con sesión activa), así que el canje completa con el endpoint OpenID **userinfo** usando el `access_token` del mismo canje. El nombre completo precarga `fullName` de la entidad Cuenta solo si está vacío (ver [Perfil de usuario](#perfil-de-usuario)). El token de vínculo firmado lleva `sub|email|exp|picture|name` para que el camino por contraseña capture ambos al primer vínculo.
- **Cuentas solo-Google** (`password_hash` NULL): no pueden iniciar sesión con contraseña ni cambiarla en Perfil → Seguridad; el admin las distingue con insignia «Google» en `/users`.
- **Migración**: `db/auth-google-schema.sql` + `db/apply-auth-google.mjs` (ya en la cadena de despliegue de AGENTS.md): columna `google_sub` con índice único parcial, columna `google_picture` y `password_hash` nullable. El archivo de credenciales descargado de Google (`client_secret_*.json`) está en `.gitignore` — nunca se sube al repo.

## Conectores

`/modulos/conectores`, herramienta del hub de Módulos (`PlugZapIcon`): catálogo de integraciones **por proveedor** y conexiones OAuth **por usuario**. El catálogo vive en `src/lib/conectores.ts` —una sola fuente (compartida cliente/servidor) para ids válidos, scopes y estado—; hoy **Google Calendar** está disponible (scope `https://www.googleapis.com/auth/calendar.events`, solo eventos: privilegio mínimo; cambiar el scope si el consent screen aprobó otro es una línea del catálogo) y **Google Drive** y **Outlook Calendar** se listan como *Próximamente*. Un conector nuevo se agrega con una entrada del catálogo; el flujo OAuth vive por proveedor (`providerId`), así que otro proveedor solo necesita su módulo de tokens en `src/server/conectores/` y su ruta de callback.

- **UI** (`src/components/conectores/conectores-view.tsx`): secciones *Tus conexiones* (badge de estado, correo de la cuenta conectada, fecha de conexión y *Desconectar* con confirmación en `AlertDialog`), *Disponibles* (acción primaria *Conectar*) y *Próximamente*. La conexión en `error` muestra «Reconectar»; el resultado del flujo OAuth llega por query y se pinta como Alert superior. Los botones de inicio del flujo son **anclas planas** (no `<Link>`): la navegación debe ser de documento completo, porque el fetch RSC de Link sigue el 307 hacia el proveedor y el navegador lo bloquea por CORS.
- **Flujo OAuth propio, separado del login**: `GET /api/conectores/conectar/<connectorId>` valida sesión y catálogo, fija el estado anti-CSRF (`<connectorId>.<aleatorio>` en cookie httpOnly de 10 min; el callback compara el valor completo en tiempo constante y toma el conector de la cookie) y redirige al consentimiento con `access_type=offline` + `prompt=consent` (garantiza refresh_token). El callback (`/api/conectores/google/callback`) canjea el código y guarda los tokens; *Desconectar* (`DELETE /api/conectores/<connectorId>`) revoca el token en Google (best effort, sin bloquear la respuesta) y borra la fila. **URI de redirección autorizada en Google Cloud Console**: `SITE_URL + /api/conectores/google/callback` (distinta a la del login). Ambos handlers llaman `await connection()` por la misma razón que los del login.
- **Tokens cifrados en reposo**: AES-256-GCM (`src/server/conectores/crypto.ts`) con clave derivada por scrypt de `CONECTORES_SECRET` (o `GOOGLE_CLIENT_SECRET` si falta; ver [Puesta en marcha](#puesta-en-marcha)) y memoizada por proceso. Nunca salen al cliente: la pantalla solo ve estado, correo de la cuenta y fecha. Reconectar conserva el refresh_token anterior si el nuevo canje no lo trajo y revoca el viejo si cambió.
- **Consumo por módulos**: `accesoValido(userId, connectorId)` (`src/server/conectores/repository.ts`) devuelve un access_token vigente y lo renueva en frío con el refresh_token a menos de un minuto de expirar. Solo `google_grant_invalid` (token muerto: revocado o caducado) o la ausencia de refresh marca la conexión en `error`; los fallos transitorios (red, 5xx) dejan el estado intacto y quedan en el log para que el siguiente consumo reintente.
- **Persistencia**: tabla `connector_connections` (`db/conectores-schema.sql` + `db/apply-conectores.mjs`, en la cadena de despliegue de AGENTS.md): una conexión por usuario y conector (índice único `(user_id, connector_id)`; reconectar reemplaza la fila), FK a `users` con borrado en cascada.

## Distribuidores

`/modulos/distribuidores`, herramienta del hub de Módulos (`UserCogIcon`, **solo admin**): la gestión de las cuentas con rol `distribuidor` con las mismas filas de `/clientes` y el mismo menú contextual de `/users`. Es la primera entrada `adminOnly` del catálogo `MODULOS` (`src/lib/modulos.ts`): el hub filtra el catálogo por rol (prop `isAdmin` que la página `/modulos` resuelve con `user.role`), así que las cuentas distribuidoras ni siquiera ven la tarjeta, y la ruta queda protegida con `requireRole("admin")` (no admin → redirect a `/clientes`; sin sesión → `/login`).

- **Dato filtrado en el servidor**: la página (`src/app/(dashboard)/modulos/distribuidores/page.tsx`) llama `listUsers()` (`src/server/auth/users.ts`) y pasa solo las filas con `role === "distribuidor"` — el mismo listado de `/users`, con sus dos saldos (tokens/cupones), su reseller FlujoTV ligado (`distribuidorName`), el conteo de entidades y las secciones denegadas para el diálogo Permisos; más los topes globales de cupón (`couponQaDailyLimit` / `couponQaMonthlyLimit`), exactamente igual que la página de Usuarios.
- **Filas estilo `/clientes`** (`src/components/herramientas/distribuidores/distribuidores-view.tsx`): acordeón con avatar `size-12` de iniciales pastel —misma paleta y helpers de `/clientes`, extraídos a `src/lib/avatar.ts` (`initials` + `pastelAvatarStyle`) para que ambas pantallas compartan una sola fuente—, título con el correo de la cuenta y badge «Google» si está ligada a OAuth, subtítulo con el panel ligado («Panel FlujoTV: …» o «Sin panel de FlujoTV ligado»), conteo de clientes asignados como dato compacto y punto de estado en el margen derecho (verde `success` con panel ligado, ámbar `warning` sin ligar; `role="img"` + `aria-label`). Al expandir: fecha de alta (formato `es`) y los dos saldos vigentes de la cuenta, lo que el admin necesita a la vista antes de abonar o editar.
- **Botón de gestión settings-2**: ocupa la posición del carrito de compra rápida de `/clientes` (capa absoluta `right-8`, táctil 36×36 `rounded-full`, negro puro en claro y blanco puro en oscuro, feedback `active:scale-90` con la curva de la casa y `motion-reduce` a solo color) pero abre el `UserActionsMenu` de `/users` (`src/components/auth/users-list.tsx`, ahora exportado con trigger configurable — `triggerIcon` + `triggerClassName`; sin props, `/users` se comporta igual que siempre): Saldo (abono directo), Permisos (matriz de secciones + topes de cupón), Editar (email, rol, distribuidor, contraseña) y Eliminar (oculto en la fila propia), con sus diálogos intactos y `router.refresh()` tras cada acción.
- **Buscador**: la misma píldora de `/clientes` (`InputGroup` `rounded-full` con lupa y X de limpieza visible solo con texto); filtra por correo o panel ligado sin acentos ni mayúsculas (`foldTerm`). Contador de resultados bajo el listado y estado vacío («Sin cuentas distribuidoras») con acceso directo a *Usuarios* para crear la primera cuenta.

## Almacenamiento por usuario

Cada cuenta dispone de un folder propio en el servidor para sus archivos: adjuntos subidos e imágenes/archivos generados por IA.

```
storage/users/<userId>/
  attachments/   # adjuntos subidos vía POST /api/files
  generated/     # imágenes y archivos generados por IA (p. ej. el asistente)
    variants/    # versiones derivadas de las imágenes (baja + miniatura, WebP)
```

- **Raíz configurable**: `USER_FILES_DIR` (por defecto `<proyecto>/storage/users`); `USER_FILES_MAX_BYTES` fija el tamaño máximo por archivo (10 MB por defecto). El folder está en `.gitignore` y no forma parte del build.
- **Ciclo de vida**: `createAccount` crea el folder al registrar una cuenta (con reintentos perezosos en el primer guardado si fallara); `node db/ensure-user-storage.mjs` lo aprovisiona para cuentas existentes; al eliminar una cuenta se elimina su folder completo.
- **Índice**: cada archivo se registra en la tabla `user_files` (`db/storage-schema.sql`): nombre original saneado, nombre en disco (`<ts>-<rand>-<nombre>`), MIME, tamaño y fecha. Borrar un archivo elimina la fila y el fichero.
- **Aislamiento**: las rutas `/api/files*` operan siempre sobre el `userId` de la sesión (nunca sobre un id del cliente); la descarga hace streaming con `Content-Disposition` y `X-Content-Type-Options: nosniff`.
- **Variantes**: además del original, el servidor guarda dos versiones derivadas de cada imagen (`low`, la que se ve en el celular, y `thumb`, la miniatura de la galería) en `<kind>/variants/<storedName>.<variante>.webp`, indexadas en `user_file_variants` (`db/variants-schema.sql`). Se derivan con **sharp** (redimensión a 1280 px / 400 px de lado mayor y recodificado a WebP) al generar la imagen y, si faltan, **bajo demanda** al pedirlas (`ensureFileVariant`). Las variantes son inmutables, así que se sirven con `Cache-Control: private, max-age=31536000, immutable`; el original se sirve sin caché. Borrar un archivo borra también sus variantes (fichero y fila).
- **Uso futuro**: el asistente (o cualquier módulo) guarda lo que genere con `saveUserFile({ userId, kind: "generated", ... })` de `src/server/storage/user-files.ts`, de modo que todo queda dentro del folder del usuario.
- **Adjuntos de las herramientas**: las imágenes de referencia de `/modulos/imagenes` se suben con `POST /api/files` (kind `attachment`) y quedan en `attachments/`; el chat de `/modulos/animacion` **no** las sube: manda los bytes al agente, que los deja en el sandbox de la sesión Eve.
- **Barrido de adjuntos**: `node db/sweep-attachments.mjs` borra los adjuntos (kind `attachment`) con más de `ATTACHMENT_TTL_DAYS` días (7 por defecto) —fila y fichero— para que el disco no crezca sin límite; conviene correrlo a diario (cron). Los archivos `generated` (la galería del usuario) nunca se tocan.

## Imágenes con IA

Generador en `/modulos/imagenes` (sección *Módulos* de la barra inferior); backend en `src/server/images/service.ts` (catálogo y opciones en `src/server/images/models.ts`, investigación deportiva en `src/server/images/sports.ts`) y rutas `/api/images*`.

- **Pestañas**: la página se organiza en dos pestañas —*Crear* (card *Descripción*, con el área de texto del prompt) y *Galería* (grid de resultados)— con el patrón canónico de pestañas de `/profile` (`Tabs` variante `line`, paneles `keepMounted`; ver [Convenciones de UI](#convenciones-de-ui)). La barra de pestañas es **fija** (`sticky` bajo la cabecera de la app): al recorrer la galería, las pestañas siguen a la vista para cambiar de vista sin volver arriba (ver [Convenciones de UI](#convenciones-de-ui)). Ambas pestañas comparten estado en `ImageStudio`: una imagen recién generada aparece en la galería sin recargar, y el botón *Escribir prompt* del estado vacío cambia a la pestaña *Crear* y enfoca el prompt. La página **no lleva encabezado propio** (ni título ni descripción): el nombre *Imágenes* no se muestra y el `<h1>` queda solo para lectores de pantalla (`sr-only`).
- **Proveedor**: **Vercel AI Gateway** vía AI SDK (`AI_GATEWAY_API_KEY` en `.env`). Los modelos de imagen se llaman con `generateImage` + `gateway.imageModel(<id>)`; los LLM multimodales que devuelven imágenes (Gemini) usan `generateText` + `gateway.languageModel(<id>)` y la imagen se toma de `result.files`. El modelo lo determina la configuración del usuario (ver [Configuración por usuario](#configuración-por-usuario)) y, sin selección propia, el orden de `IMAGE_MODELS` (`.env`). La **calidad y el tamaño** salen de la configuración del usuario para el nivel elegido (ver [Configuración por usuario](#configuración-por-usuario)); por omisión, la máxima que admite cada modelo y su tamaño estándar (`1024x1024` en OpenAI, `1K` en Gemini). La relación de aspecto elegida en la herramienta (`auto`, `1:1`, `16:9`, `9:16`, `4:3`, `3:4`, `3:2`, `2:3`) se aplica según la familia del modelo: en OpenAI se traduce a `size` con lados múltiplos de 16 (`1:1`→`1024x1024`, `16:9`→`1792x1008`, `9:16`→`1008x1792`, `4:3`→`1024x768`, `3:4`→`768x1024`, `3:2`→`1536x1024`, `2:3`→`1024x1536`), porque esos modelos no aceptan `aspectRatio`; en Gemini y Grok viaja como `aspectRatio`. El selector ofrece **la misma lista completa en todos los niveles** (`1:1 · Cuadrada`, `16:9 · Panorámica`, `9:16 · Póster`, `4:3 · Clásica`, `3:4 · Retrato`, `3:2 · Foto`, `2:3 · Foto vertical` y `Automático`), y abre por omisión en **`9:16 · Póster`**, la relación que más usa el panel. El selector pasa el catálogo como `items` al *Select* de Base UI, así que el trigger refleja la etiqueta de la opción elegida (`9:16 · Póster`) y no el valor crudo; si el modelo configurado no admite la relación elegida, el servidor la recorta a la más cercana que sí admite (`closestAspect`), para que la imagen no salga con otra forma sin avisar. En `Automático` manda el tamaño configurado para ese nivel —único caso en que el aviso de tamaño bajo el selector se muestra; con una relación elegida no se imprime nada, porque el propio trigger ya refleja la opción—, y la galería guarda el aspecto realmente aplicado. `n = 1`. Timeout de 180 s hacia el gateway y rate limit de 6 imágenes/min por usuario (en memoria, por proceso). El catálogo de modelos verificables (con su etiqueta, proveedor y capacidades) vive en `src/server/images/models.ts`. Cada familia expone los controles de forma distinta, y el catálogo lo declara: **OpenAI** (`gpt-image-2.5-sunburst`) usa `size` en píxeles (lados múltiplos de 16) y `providerOptions.openai.quality`; **Gemini** (`gemini-3.1-flash-image`, `gemini-3.1-flash-lite-image`) es un LLM multimodal y usa `providerOptions.google.imageConfig` con `aspectRatio` e `imageSize` (512, 1K, 2K, 4K), sin calidad; **Grok Imagine 2.0** usa `aspectRatio` y `providerOptions.xai.quality` (solo `low`, `medium`, `auto`) y no admite `size`. Todo verificado en vivo contra el gateway (2026-10-21).
- **Control de calidad**: la fila de *Calidad* es un `ToggleGroup` (Base UI, variante `default` —sin borde; el nivel activo se distingue por el tono `muted` del estado presionado, coherente con la celda de adjuntos) con un botón por nivel del catálogo de calidad —*Media* y *Alta*—, con el nivel activo presionado; el estado vive en `qualityIndex` y se traduce al `level.id` (`media` / `alta`) que viaja al servidor en `POST /api/images`. Antes era un `Slider` de dos pasos con las etiquetas de los niveles debajo; el toggle comunica el estado con el propio botón (`aria-pressed`), se opera con el teclado (flechas entre opciones, Enter para elegir) y expone el grupo a lectores de pantalla con `aria-labelledby` sobre la etiqueta *Calidad*. Por omisión el control abre en ***Alta*** (el nivel `alta` del catálogo; si el usuario no tiene ese nivel configurado, abre en el primero disponible). El resto del control (qué modelo, calidad y tamaño usa cada nivel) no cambia: lo define `/soporte/configuracion` (ver [Configuración por usuario](#configuración-por-usuario)).
- **Fila de controles (mobile first)**: la fila de *Formato* / *Calidad* / botón es un `grid`. En móvil compone un **renglón compacto** de dos columnas —*Formato* (select flexible, `minmax(0,1fr)`) y *Calidad* (toggles al ancho de su contenido) comparten línea, con sus etiquetas encima y el botón debajo a todo el ancho— y pasa a una fila alineada en ≥1024px (`lg:contents` + `col-start`/`row-start`): la etiqueta *Formato* y la etiqueta *Calidad* en su propia línea, sus controles justo debajo y el botón a la derecha, sobre la misma línea que los controles. Las dos etiquetas usan el mismo estilo (`text-muted-foreground text-xs`) y la de *Calidad* es la que nombra al grupo de toggles (`aria-labelledby`). El botón de la fila es **un solo botón de dos pasos** con la pista de progreso encima (stepper no interactivo de ReUI: ① investigar · ② crear, con spinner en el paso activo): *Investigar y mejorar descripción* mientras el texto no se ha procesado y *Crear* cuando ya lo está (editar la descripción lo regresa al paso 1); debajo, el enlace *Crear sin investigar* (variante `link`, visible solo con texto sin procesar) genera directamente.
- **Botones bajo el prompt (mobile first)**: bajo el área de texto, alineados a la derecha y uno junto al otro (`flex justify-end gap-2`), viven **Regenerar** (`secondary`, `size="sm"`, ícono de refresco) y **Limpiar** (`ghost`, `size="sm"`, ícono de papelera). *Regenerar* solo aparece cuando hay una investigación que repetir: repite la búsqueda **desde la descripción original** que el usuario escribió (la UI la guarda al investigar), no desde el texto ya reescrito, para que el modelo haga un intento en limpio cuando la búsqueda no devolvió los valores esperados (el servidor no cachea: cada intento vuelve a buscar; el límite es de 10 mejoras por minuto). *Limpiar* borra la descripción (y con ella el texto procesado y sus fuentes) y devuelve el foco al área para escribir un prompt nuevo desde cero; los adjuntos se conservan (quitarlos es la acción de cada chip). Editar la descripción a mano descarta la original guardada y *Regenerar* desaparece (el flujo regresa al paso 1), pero *Limpiar* sigue disponible.
- **Imágenes de referencia**: un botón con el **símbolo + grande** vive en una **celda propia bitono** al costado izquierdo del área de texto (fondo `muted/50` dentro del `InputGroup`, sin borde: solo cambio de tono), para que se distinga como botón y no como decoración del prompt; permite adjuntar hasta **4 imágenes** (10 MB cada una, 20 MB en total por generación) que se envían al modelo como parte del prompt (`generateImage` con `prompt: { images: [...], text }`), de modo que la generación sigue la paleta, el estilo o el sujeto de la referencia. Cada adjunto se sube primero a `POST /api/files` (kind `attachment`, queda en `storage/users/<userId>/attachments/`) y la UI manda solo su id (`referenceIds`) en `POST /api/images`; el servidor valida que cada id sea un UUID con el formato 8-4-4-4-12 (`UUID_RE` en `src/server/images/service.ts`) y lo resuelve con `getUserFile` (solo archivos del propio usuario), **verifica la firma de bytes** (solo PNG, JPEG, GIF o WebP: el MIME que declara el cliente no se usa como prueba) y lo entrega como bytes al gateway — un adjunto inválido devuelve 422 **sin gastar** y superar el tope de bytes devuelve 413. Las mismas referencias viajan a *Insertar detalles* (partes `file` con la imagen) para que la propuesta del modelo tenga en cuenta la imagen. Quitar un chip aborta la subida en vuelo y borra el adjunto del almacenamiento (`DELETE /api/files/<id>`); una referencia que falló al subir bloquea la generación hasta que se quite, para que lo enviado y lo visible coincidan. Los límites viven en `src/lib/attachments.ts` y los comparten cliente y servidor.
- **Dictado por voz**: un botón de **micrófono** vive a la derecha de la etiqueta *Descripción* (`CardAction`, a su misma altura): es la otra forma de escribir el prompt. Usa la **Web Speech API** del navegador (reconocedor en `src/hooks/use-speech-recognition.ts`, idioma `es-MX`, `continuous` + resultados provisionales, así que las palabras aparecen en el área mientras se hablan); el audio lo procesa el propio navegador (Chromium lo manda a sus servidores de voz). Un toque abre el micrófono y otro lo cierra; lo dictado **se agrega** a lo que ya estaba escrito y, al cerrar, el texto queda consolidado y el foco vuelve al área. Mientras escucha, el botón pasa a variante `destructive` con una línea de estado (*Escuchando…*, `role="status"`) bajo el área. **Detección y permisos**: solo Chromium y Safari exponen el reconocedor y exige contexto seguro —en Firefox o fuera de HTTPS el botón queda inactivo (`aria-disabled`) y el toast/tooltip explican por qué—; el permiso de micrófono lo pide el navegador en el primer toque. **Robustez ante los móviles**: los reconocedores móviles reenvían la lista completa de resultados en cada evento (con `resultIndex` siempre en 0), devuelven la misma frase dos o tres veces seguidas como finales (Chrome de Android), retranscriben de forma acumulada sustituyendo la primera entrada por una versión más larga, y vuelven a transcribir la frase tras una pausa (iOS 18). El hook acumula **por índice** (no por evento) y colapsa al juntar las copias consecutivas de lo mismo —comparando sin puntuación ni mayúsculas— y lo acumulado que el navegador reenvía, de modo que el texto nunca sale duplicado (cada resultado guarda su hora de llegada cuando conviene distinguir la repetición deliberada del usuario). Chrome de Android ignora `continuous`: la sesión se cierra sola al terminar cada frase y basta tocar el micrófono de nuevo para continuar (lo dictado se acumula sin duplicarse). **Límites y convivencia**: el dictado respeta el tope de 2000 caracteres del área (aviso visible al llegar) y entra por la misma puerta que una edición manual —reinicia el paso del botón principal a *Investigar y mejorar descripción*—; escribir a mano mientras se dicta cancela la sesión (lo escrito manda); y mientras vuela una investigación o una generación el micrófono se deshabilita, para que ninguna respuesta pise el texto dictado.
- **Persistencia**: la imagen se decodifica (base64 → binario) y se guarda con `saveUserFile` (kind `generated`), por lo que vive en `storage/users/<userId>/generated/` y se sirve vía `/api/files/<fileId>`; cada generación se registra en `image_generations` (`db/images-schema.sql`) con prompt, modelo, parámetros y costo. Al guardarse se derivan sus **variantes** (`low` y `thumb`) con sharp, de modo que la galería y el visor nunca arrastran los 2-3 MB del original (ver [Variantes de las imágenes](#variantes-de-las-imágenes)).
- **Insertar detalles** (investigación con LLM + búsqueda web): el paso 1 del botón principal (*Investigar y mejorar descripción*) envía el prompt, el aspecto seleccionado y las imágenes de referencia al modelo y devuelve **un único prompt final** en el que ya están integrados los datos del tema; tras aplicarlo, el botón pasa a *Generar*. **Ruta rápida (grounding)**: con `GEMINI_API_KEY` (o `GOOGLE_GENERATIVE_AI_API_KEY`) configurada, el botón resuelve en **una sola llamada** a Gemini —salvo en el tema deportivo, que va en dos fases (ver abajo)— (`IMAGE_DETAILS_GROUNDING_MODEL`, default `gemini-3.8-flash`) con **Google Search grounding** (`src/server/images/grounding.ts`): la búsqueda corre dentro del modelo en la infraestructura de Google, sin planificador ni Tavily, con presupuesto de razonamiento configurable (`IMAGE_DETAILS_GROUNDING_THINKING`, default 0 = máxima velocidad) y timeout de 45 s. En esta ruta el metadata de grounding no trae `groundingChunks` (con el contrato de JSON el modelo no llega a buscar: ver la ruta deportiva más abajo), así que las fuentes son las URLs que cita el propio modelo tras buscar y el servidor les aplica la regla de dos familias editoriales distintas (la verificación contra un índice de resultados reales ya no es posible por esta vía). El grounding tampoco entrega fechas de publicación: la frescura de los datos volátiles queda declarativa (el corte temporal que cita el modelo) y, ante cifras vivas con fuentes discrepantes, el modelo prefiere no confirmar el dato y lo avisa en `note`. Si la llamada falla (timeout, JSON inválido, error del proveedor), el service cae al pipeline de respaldo sin que el usuario note nada (Tavily quedó retirado el 2026-10-22 al eliminarse `TAVILY_API_KEY` del `.env`: sin esa key el respaldo redacta sin investigación web); cada uso queda registrado en el log (`images: details grounding` con ms, tokens, `searched` y el costo estimado `costUsd`). **Tema deportivo (búsqueda forzada, dos fases)**: las peticiones de temática deportiva (cualquier deporte o competición; la detección es determinista en `src/server/images/sports.ts`, no depende del modelo) **nunca** se responden con el conocimiento del LLM: ganadores, campeones, resultados, marcadores, clasificaciones, récords y fechas tienen que salir de la web. La razón es técnica: en Gemini, pedirle a la misma llamada que devuelva JSON **suprime** la llamada a `google_search` (medido: 0 llamadas a la herramienta, `groundingMetadata` vacío y respuesta con la temporada vieja), de modo que la ruta deportiva se parte en dos fases. **(1) Investigación**: una llamada cuyo único trabajo es buscar y reportar los datos en texto plano (`DATO: <dato> | CORTE: <fecha o jornada> | VOLATIL: <sí/no> | FUENTES: <url>, <url>`), con la búsqueda forzosa en el *system prompt* (tu memoria no es una fuente; usa el año de la fecha de referencia en las consultas). El servidor comprueba que la búsqueda **ocurrió** (los `groundingChunks` de la respuesta) y que cada dato quede respaldado por **dos páginas de dominios distintos que la búsqueda realmente abrió** —los *chunks* traen los dominios consultados, así que una URL inventada por el modelo se descarta—. **(2) Síntesis**: una segunda llamada (la misma API directa de Google, ya sin la herramienta de búsqueda) que redacta el JSON final **solo** con esa evidencia y pasa la misma validación del resto del pipeline (cada dato cita dos dominios de la evidencia). Si la búsqueda no ocurre o ningún dato alcanza dos páginas independientes, se reintenta una vez con una instrucción más exigente; si tampoco, el prompt se redacta **sin datos deportivos** (la regla prohíbe completarlos con la memoria del modelo) y el usuario recibe el aviso en `note`. El *system prompt* de síntesis también exige, para el tema deportivo, que los datos salgan únicamente de la evidencia y que no se completen los que la búsqueda no confirmó. Medido el 2026-10-22: **~17 s** de extremo a extremo para el caso F1 (investigación ~11 s + síntesis ~6 s) y **~$0.02** por consulta (tarifa de búsqueda + tokens), con los datos confirmados y sus dos enlaces en pantalla; el resto de las peticiones conserva la ruta de una sola llamada (~3-5 s). **Prorrateo del costo de búsqueda**: cuando la búsqueda corrió, su costo estimado (tarifa de grounding $14/1,000 más tokens, según el catálogo del gateway) se acumula por usuario (`src/server/images/details-cost.ts`, ventana de 30 minutos) y se carga a la **primera generación posterior**, sumándose al costo del gateway en `image_generations.cost_usd` y en su espejo del control de gastos; si el usuario nunca genera, el costo se absorbe al expirar la ventana. La **ruta completa** (sin esa key o como respaldo) investiga en internet antes de escribir, con un pipeline de cuatro pasos (`src/server/images/details.ts` + `src/server/images/tavily.ts`): **(1) planificación** —el LLM decide si la petición necesita datos externos verificables y genera hasta 3 búsquedas en es-MX, con tema `news` para eventos en vivo o de últimos días—; **(2) investigación** —las búsquedas se ejecutan en paralelo contra **Tavily** (`TAVILY_API_KEY` en `.env`; profundidad avanzada, `language: es`, `country: mexico` en búsquedas generales, hasta 8 resultados con fecha de publicación por búsqueda)—; **(3) síntesis** —el LLM redacta solo con esa evidencia real como material externo—; y **(4) validación del servidor** —cada dato citado debe existir en los resultados reales de Tavily (las URLs inventadas se descartan) y quedar respaldado por **al menos dos familias editoriales distintas** (ESPN México y ESPN Deportes son una sola: la corroboración debe venir de medios independientes); un dato con una sola fuente no entra al prompt (la respuesta sintetizada de Tavily cuenta solo como referencia, nunca como fuente). Los **datos volátiles** (tablas de posiciones, puntos, marcadores, clasificaciones) se protegen contra la corroboración obsoleta —dos medios con la jornada anterior pasan la regla de dos fuentes—: el planificador los marca como tales, su búsqueda se acota con `time_range: "week"` y se restringe primero a **medios verificados** (`ligamx.net`, ESPN, Mediotiempo, TUDN, Récord, Azteca Deportes; la web abierta queda de respaldo), el modelo debe citar el corte temporal del dato (jornada o fecha), resolver contradicciones a favor de la fuente más reciente que declare el corte, puede combinar un estado parcial confirmado con resultados finales confirmados si la aritmética es trivial (la tabla previa + el resultado del partido pendiente, citando ambas piezas) y el servidor descarta el dato volátil si todas sus fuentes fechadas tienen más de 7 días. Si la síntesis no confirma nada —o la evidencia fechada más fresca ya tiene más de 3 horas, señal de que la fecha está en curso—, se ejecuta **una ronda de refinamiento**: el LLM genera búsquedas dirigidas a lo que faltó (típicamente el resultado final de los partidos pendientes, que se publica antes que la tabla consolidada) y se re-sintetiza con la evidencia fusionada. Si el validador rechaza todas las citas de un intento (dos páginas del mismo medio, URLs fuera de la evidencia), se ejecuta **una re-síntesis correctiva**: el modelo recibe la causa exacta de cada rechazo y corrige sus citas con otras páginas de la evidencia. La UI muestra la fecha de publicación de cada fuente de respaldo para que la frescura sea visible. **Todo lo que devuelve el modelo está siempre en español de México (es-MX)**, aunque el usuario escriba en otro idioma (el modelo traduce la petición), y usa el léxico mexicano ("El Tri", "la Selección Mexicana", "liga MX"): las **búsquedas también se hacen en es-MX** y la búsqueda va anclada a México (`language: "es"` y `country: "mexico"` en las búsquedas generales de Tavily) para que las fuentes sean las de aquí. El *system prompt* incluye la **fecha y hora de referencia de Ciudad de México** (con su desfase, p. ej. `GMT-06:00`) para resolver referencias relativas ("hoy", "esta noche", "el próximo partido") y le exige al modelo que **no invente**: si ese día no hay evento, el prompt lo dice en vez de inventar uno. Todos los horarios se manejan **exclusivamente en hora del centro de México**: el prompt le prohíbe al modelo traducir la hora local de origen ("no agregues la zona ni la hora local de origen; escribe solo la hora de Ciudad de México"), de modo que en el texto final no aparezcan horarios ambiguos ni la ciudad de origen. El servidor **valida esa referencia** antes de llamar al modelo (`mexicoCityNow` en `src/server/images/details.ts`): la fecha, la hora y el día de la semana se calculan por dos caminos independientes —el formateador de ICU con `America/Mexico_City` y el cálculo manual sobre el desfase que reporta la zona— y, si no coinciden (o si el día de la semana no corresponde a la fecha), la operación falla con un error claro en vez de pasarle al modelo una fecha equivocada. El modelo es el de `IMAGE_DETAILS_MODEL` en `.env` (por defecto `deepseek/deepseek-v4.1-flash-1017`, ~$0.001 USD por consulta: $0.075 por millón de tokens de entrada y $0.30 por millón de salida en el catálogo del AI Gateway del 2026-10-22; el gateway multiplica x2 el precio en las ventanas de tarifa pico y varía según el proveedor que route la llamada); el texto que devuelve es un párrafo descriptivo en español de México (es-MX, máx. 120 palabras) más el aspecto sugerido cuando el texto es ambiguo (p. ej. "banner" → 16:9, "retrato" → 9:16). El prompt final **contiene solo lo que el usuario pidió**: el *system prompt* prohíbe añadir elementos, escenas, rótulos, textos para representar, datos o afirmaciones que no estén en la petición, **aunque sean reales o los haya encontrado la búsqueda** —la búsqueda solo completa los datos del tema pedido (fecha, hora, cifra, nombre, sede)—. Si la petición se apoya en un hecho que **no ocurrió o no existe** (por ejemplo, "el partido de hoy" y hoy no hay partido), el modelo no lo inventa ni lo anuncia dentro del prompt: lo devuelve en el campo `note`, que la UI muestra **fuera del área de texto** (debajo de ella), de modo que el prompt queda limpio y el usuario sigue viendo la corrección. El resultado **reemplaza el contenido del área de texto** para que el usuario lo revise antes de generar, y debajo del botón se muestran los **datos confirmados** (cada dato con el ícono de verificación y los enlaces a los dominios que lo respaldan —mínimo dos—) para que la verificación sea trazable; si hubo investigación pero ningún dato alcanzó las dos fuentes, un aviso estándar lo dice. Si el usuario edita el texto a mano, la lista de datos, las fuentes y el aviso se limpian. Degradación por pasos: la investigación (plan + Tavily) se intenta una sola vez y, si falla (sin `TAVILY_API_KEY`, timeout, JSON inválido), el servidor degrada a redacción sin investigación; la síntesis conserva sus reintentos (sin imágenes de referencia, sin evidencia), de modo que el botón nunca deja al usuario sin resultado (`src/server/images/details.ts`). El límite es de 10 consultas por minuto y usuario. **Tiempos típicos** (medidos el 2026-10-22, extremo a extremo): la **ruta grounding** resuelve en **~5 s** tanto los prompts creativos como los que requieren búsqueda, y la **ruta deportiva** (investigación + síntesis) en **~17 s**; la ruta completa (Tavily, hoy retirada) con `deepseek/deepseek-v4.1-flash-1017` medía ~5 s cuando el tema no requería investigación, ~30-40 s con búsqueda confirmada y ~55 s en el caso volátil con refinamiento (con `meta/muse-spark-1.3-contributor`: ~18 s, ~90 s y ~120 s).
- **Tarificador**: el costo es el que reporta el gateway (`providerMetadata.gateway.cost`, USD, `numeric(12,6)`; `NULL` si no viene dato), más el **costo de búsqueda prorrateado** de *Insertar detalles* cuando la búsqueda con grounding corrió antes de generar; ambos se suman en el mismo `cost_usd`. El **costo acumulado** suma *todas* las generaciones del usuario: borrar una imagen (soft-delete, `deleted_at`) la saca de la galería y borra su binario, pero el costo permanece en el total para que refleje el gasto real facturado. Si el archivo no pudiera persistirse tras una generación exitosa, el costo igualmente queda registrado en una fila sin `file_id` (excluida de la galería, incluida en el total). Además, cada costo facturado se **espeja al control de gastos** del usuario mediante `createSystemExpense` (`src/server/finanzas/gastos.ts`): una fila en `expenses` con categoría *Imágenes*, moneda USD, tipo de cambio FIX del día, `created_by: "sistema"` y `source_image_id` apuntando a la generación (índice único que hace idempotente la operación). El espejo es *best effort* por diseño: un fallo ahí nunca falla la generación; solo se registra en el log. Las generaciones previas al espejo se importaron con `node db/backfill-image-expenses.mjs` (idempotente: los reintentos se saltan vía `source_image_id`).
- **Conversión a pesos mexicanos (Banxico)**: el USD se guarda como fuente de verdad para facturación y la UI presenta los costos **en MXN**, cada uno convertido con el tipo de cambio **FIX de Banxico** (serie `SF43718`) publicado para el **día de uso** de la generación en zona horaria `America/Mexico_City` (fin de semana y feriados heredan el último día hábil publicado). El módulo `src/server/banxico.ts` consulta el API de Banxico (`BANXICO_TOKEN` en `.env`) por rango de fechas con ventana ampliada 10 días atrás (un rango caído íntegramente en día inhábil devuelve la serie sin `datos`) y mantiene en memoria un cache por día calendario con TTL de 1 h, relleno hacia adelante y cooldown de 60 s ante fallos del proveedor. Si Banxico no responde (o falta `BANXICO_TOKEN`), la conversión degrada con gracia: costos y total se muestran en USD etiquetado (`US$…`) o `s/d`, sin romper ninguna petición. La fila `image_generations` no cambia: la conversión se calcula al leer (`cost_usd` → `costMxn`) usando `created_at`.
- **Galería**: `GET /api/images` devuelve las generaciones vivas (con `file_id`), el total y el costo acumulado en USD (`costUsd`/`totalCostUsd`) junto con su equivalente en MXN (`costMxn`/`totalCostMxn`, `null` si algún día carece de tipo de cambio); `DELETE /api/images/[id]` hace el soft-delete y libera el archivo; el id de la generación se valida con el mismo `UUID_RE` 8-4-4-4-12 y, si no encaja o no pertenece al usuario, la ruta responde 404. La UI (`src/components/herramientas/imagenes/image-studio.tsx`) muestra el costo por imagen en cada tile (badge); si el MXN no está disponible cae a `US$…` etiquetado. **El encabezado de la galería no muestra el costo acumulado** (ni la etiqueta *Costo acumulado* ni el monto): el acumulado vive en otra parte de la app, así que la UI ya no lo pide ni lo guarda en estado; el API sigue devolviéndolo (`totalCostUsd`/`totalCostMxn`) para quien lo necesite. Las miniaturas **respetan la proporción de la imagen**: el grid usa `items-start` y el `aspect-ratio` sale de las dimensiones reales de la miniatura derivada (y, si aún no existe, del `aspect_ratio` guardado), para que ninguna miniatura se recorte al cuadrado ni se deforme.
- **Selección múltiple y borrado por lote**: la galería admite selección múltiple. El gesto de entrada es la **pulsación larga** sobre una miniatura (tap sostenido en móvil, clic sostenido en escritorio): marca esa imagen y enciende el modo selección; a partir de ahí un toque normal marca o desmarca en vez de abrir el visor. La marca vive en el propio botón (`aria-pressed`), con un indicador circular en la esquina de la miniatura, y el botón cambia de *Ver imagen…* a *Seleccionar imagen…*. El gesto se apoya en eventos de puntero (`src/hooks/use-long-press.ts`), con tres detalles que lo reconcilian con el navegador: el **clic que cierra la pulsación larga se descarta** (marcar una imagen no puede abrir el visor), el **menú nativo** (guardar, copiar) se cancela mientras el gesto está en curso (en escritorio aparece solo al mantener pulsado el botón) y el gesto se **cancela si el puntero se mueve**, porque entonces el usuario está desplazando la galería. Como el gesto es invisible, el encabezado de la galería trae además un botón *Seleccionar* (variante *ghost*, sin contorno) que enciende el modo desde el teclado. En modo selección aparece una **barra pegajosa** en la cabecera de la pestaña (debajo de las pestañas, con el mismo fondo opaco) con el número de imágenes marcadas, el enlace *Seleccionar todas*, la salida *Cancelar* y la acción destructiva *Eliminar* a la derecha; `Escape` sale del modo. El botón *Eliminar* (como el del diálogo de confirmación) lleva `dark:bg-primary dark:text-primary-foreground`: la variante `destructive` pinta un rojo diluido que en el **tema oscuro se pierde contra el fondo**, y en ese tema el botón pasa a blanco —igual que los botones primarios, que el tema oscuro invierte—, sin tocar el tema claro. El borrado pide **confirmación** (`AlertDialog`, con el número de imágenes que van a desaparecer) y va al servidor en una sola llamada: `DELETE /api/images` con `{ ids: string[] }` (hasta 200 ids, UUID 8-4-4-4-12), que hace el mismo soft-delete que el borrado de a una (`deleteImageGenerations` en `src/server/images/service.ts`: una sola consulta resuelve las filas y libera los binarios) y devuelve `{ deleted, missing }`; los ids que no encajan o no son del usuario se ignoran en silencio. El costo de las imágenes borradas permanece en el acumulado.
- **Visor de imagen** (`src/components/herramientas/imagenes/image-studio.tsx`): al tocar una miniatura se abre el diálogo del visor **sin título visible** (el nombre accesible *Imagen generada* queda solo para lectores de pantalla) con la versión `low` de la imagen y los datos de la generación. Los datos van en badges —costo en MXN (sin el prefijo "Costo", que queda en el `title` y en el `aria-label`), relación de aspecto y calidad—; **no** se muestran ni el nombre del modelo ni los tamaños de archivo. La **fecha (sin hora)** va en el mismo renglón de los datos (costo, aspecto y calidad), pegada al margen derecho (`ml-auto`), sin alterar la fila de acciones. La **X de cerrar** se dibuja en el diálogo (no con el botón por defecto de `DialogContent`) porque ese es *ghost* y su fondo solo aparece al pasar el mouse: en móvil la X quedaba invisible sobre la imagen; el sustituto lleva un **círculo translúcido siempre visible** (`bg-black/55 text-white`, `rounded-full`, `size="icon"`). Las acciones se reparten por jerarquía: *Copiar descripción* (secundaria) y *Eliminar* (destructiva, con `AlertDialog` de confirmación) en una fila aparte bajo la imagen, y las **dos acciones del pie** del diálogo —*Descargar original* como acción primaria (a la derecha en escritorio y al alcance del pulgar en móvil) y *Compartir* secundaria—, de modo que la acción principal domine y la destructiva quede aislada de ella. El botón *Compartir* manda la **versión baja** de la imagen (el WebP de 1280 px que se está viendo, no el original) con la Web Share API (`navigator.share` con `files`), que abre la hoja del sistema (WhatsApp, Telegram, lo que haya); si el navegador no sabe compartir archivos, la imagen se copia al portapapeles (en PNG, lo único que el portapapeles acepta) y se avisa con un toast. El archivo se deja preparado al abrir el visor (`fetchShareTarget` en `image-studio.tsx`, helpers en `src/lib/share.ts`), para que compartir no espere una descarga ni pierda el gesto del usuario (Safari exige que la llamada salga del clic). Sobre el visor, **tocar la imagen** abre un **lightbox a pantalla completa** con solo la imagen (ver [Convenciones de UI](#convenciones-de-ui)). **El prompt no se imprime**: antes se mostraba recortado (`line-clamp-3`), así que el texto no se leía completo ni se podía reusar. En su lugar el botón **Copiar descripción** (`outline`, `size="sm"`) copia el **prompt íntegro** al portapapeles (`navigator.clipboard.writeText`) para poder reutilizarlo tal cual. Al copiar, el botón cambia a *Copiado* (ícono de palomita) durante 2 s y se avisa con un toast; si el portapapeles no está disponible o la escritura falla, sale un toast de error. El estado *Copiado* se reinicia al abrir otra imagen o al cerrar el diálogo, y el temporizador se limpia al desmontar el componente. El prompt sigue en el `alt` de la imagen, así que no se pierde para lectores de pantalla.
- **Dibujar sobre imágenes** (`src/components/herramientas/imagenes/draw-editor.tsx`, `POST /api/images/[id]/annotations` en `src/app/api/images/[id]/annotations/route.ts`): el botón *Dibujar* del visor (junto a *Copiar descripción*, solo cuando la imagen tiene archivo) abre un **editor a pantalla completa** con tres herramientas en grupo alterno —**Lápiz** (trazo libre), **Flecha** y **Números**—, el **color** (picker ReUI con muestras contrastantes: rojo, amarillo, verde, azul, negro y blanco; el rótulo del panel cambia con la herramienta: *Color del trazo* o *Color del sticker*) y **Deshacer** por trazo. La **flecha** se dibuja tocando primero el **punto al que apunta** (la punta) y arrastrando hasta la cola, donde se suelta, con vista previa en vivo (línea + punta triangular) y arrastre mínimo de 8 px (un tap sin arrastre no crea nada). El modo **Números** coloca con un toque el siguiente **sticker numerado en secuencia** (1, 2, 3…; *Deshacer* libera el número y el siguiente toque lo reutiliza): un círculo del **color elegido** al **50 % de opacidad** con el número impreso en el **color contrastante** que decide el brillo del fondo elegido (`contrastingTextColor`: negro sobre claro, blanco sobre oscuro), diámetro fijo (7 % del ancho, letra escalada por dígitos con `numberStickerFontSize`) y **confirmación al soltar el toque**, de modo que un pellizco que empiece a mitad nunca deja un sticker accidental. La imagen admite **zoom por pellizco**: **un dedo dibuja, dos dedos hacen zoom y paneo** (ancla fija en el punto inicial del gesto, 1×–4×, con paneo acotado para que la imagen nunca se separe del lienzo) y también **rueda o trackpad** (zoom anclado al cursor, incluido el pinch del trackpad, que llega como `ctrl+wheel`); al hacer zoom aparece el chip **«N %»**, que devuelve al ajuste original, y los umbrales mínimos de arrastre (flecha) y de puntos (lápiz) escalan con el zoom para sentirse iguales en pantalla. Los botones no primarios del ratón no dibujan ni participan en gestos. Los trazos se guardan como **puntos normalizados (0..1)** respecto a la imagen, con color y grosor proporcional fijo (1% del ancho, sin controles de grosor ni capas), de modo que rotar o redimensionar el editor no los desplaza; el canvas se alinea al rectángulo exacto de la imagen (sin bandas de letterboxing), con `touch-action: none` solo en la zona de dibujo, captura de punteros con registro de dedos (1 dibuja, 2 pellizcan: el trazo a medio hacer se cancela al entrar el segundo dedo), repintado imperativo (sin render de React por movimiento) y zoom escrito directo en el `transform` del contenedor (la etiqueta de porcentaje solo se sincroniza cuando cambia el número mostrado). **Aceptar** (deshabilitado sin trazos) envía los trazos validados al servidor, que **compone el mismo dibujo sobre el original a su resolución completa** con sharp (`annotateImageGeneration` en `src/server/images/service.ts`: decodificación con tope de píxeles, `rotate()` EXIF y overlay SVG construido solo desde números y colores validados, con la misma geometría compartida `arrowGeometry` de `src/server/images/annotations.ts` que pinta el canvas; el sticker numérico comparte además la decisión de contraste, la pila tipográfica, el centrado del dígito y la opacidad por elemento (`fill-opacity="0.5"`, en el mismo orden secuencial que el canvas: círculo sobre la imagen y número sobre el círculo), así que el preview es idéntico a la copia guardada) y guarda una **copia nueva de Galería** con nombre `nombre (copia).ext` (`copyFileName`, reservando espacio para conservar sufijo y extensión al truncar), conservando PNG/JPEG/WebP (los demás formatos compatibles se rasterizan a PNG), registrando la fila en `image_generations` con **costo NULL** —sin llamada a IA ni gasto: no mueve los totales— y derivando sus variantes; el original queda intacto y la copia **sobrevive al borrado posterior del original** (revalidación de la fuente justo antes del INSERT y limpieza de archivo/variantes si el registro falla). **Cancelar**, la X o Escape con trazos sin guardar piden confirmación de descarte (`AlertDialog`; tocar fuera nunca guarda); un fallo de guardado conserva los trazos para reintentar, y el éxito inserta la copia en la galería en local —un fallo de refresco posterior no repite el POST—, abre la copia en el visor y avisa con toast. El endpoint valida sesión y propiedad (404 si la fuente no está disponible para esa sesión), rechaza JSON malformado, colores no HEX opacos, coordenadas no finitas o fuera de rango y grosores inválidos (el sticker usa su propio tope de diámetro, 12 % del ancho), además de stickers sin su etiqueta entera (1–9999) o sin su único punto, con límites de **500 trazos y 50 000 puntos**, lectura del cuerpo cortada de verdad a **2 MiB** (`readJsonBody` con tope en `src/server/http.ts`) y bucket de frecuencia propio (`checkAnnotationRateLimit`, 20/min, independiente del de generación). Pruebas de la lógica pura en `scripts/test-annotations.mjs` (`node scripts/test-annotations.mjs`).

### Variantes de las imágenes

Las imágenes que genera el modelo pesan 2-3 MB cada una (PNG a resolución alta). Con más de 20 imágenes, la galería arrastra decenas de megabytes y el celular se vuelve inservible. El servidor guarda **tres versiones** de cada imagen:

| Versión | Contenido | Uso |
|---|---|---|
| `thumb` | WebP, lado mayor **400 px** (≈20 KB) | la miniatura de la galería |
| `low` | WebP, lado mayor **1280 px** (≈120-180 KB) | la imagen que se ve al tocar el tile |
| original | tal como la generó el proveedor (2-3 MB) | la descarga en calidad completa |

- **Derivación**: sharp (`src/server/storage/file-variants.ts`), con corrección de orientación EXIF, `fit: inside` sin ampliar y calidad WebP 78 (`low`) / 72 (`thumb`). Las variantes se derivan **al generar la imagen** y, si faltan (imágenes anteriores al despliegue o un fallo puntual), **bajo demanda** al pedirlas: `ensureFileVariant` las genera del original y las guarda, de modo que la galería nunca depende de un backfill previo.
- **Servidor**: `GET /api/files/<id>?variant=low|thumb` sirve la variante (`422` si el nombre no existe, `404` si no se puede derivar) y `?download=1` fuerza la descarga; el `Content-Disposition` lleva el nombre `-baja.webp` / `-miniatura.webp`. Las variantes son inmutables → `Cache-Control: private, max-age=31536000, immutable`.
- **UI**: la galería carga solo miniaturas (`loading="lazy"`) y el visor abre la versión `low`. El pie del visor separa la acción principal del resto: **compartir o descargar** (pie del diálogo, a la derecha en escritorio y apiladas en móvil) con dos botones —*Compartir* (secundario, manda la versión `low`) y *Descargar original* (primario)—; **copiar la descripción** (secundaria) y **eliminar** (destructiva, con confirmación) en una fila aparte bajo la imagen; los datos de la imagen (costo en MXN, proporción y calidad) van en badges, sin el nombre del modelo ni los tamaños de archivo. Si una variante no se puede cargar, la UI cae al original en lugar de dejar un hueco. La imagen se abre en dos niveles: el tile de la galería abre el visor con su información y, sobre él, tocar la imagen abre un **lightbox a pantalla completa** (un segundo `Dialog` que cubre la vista con la imagen sola sobre fondo negro; se cierra con un toque en cualquier parte, la X o Escape, que solo cierra el lightbox y devuelve el foco al visor). Los `<img>` van con `pointer-events-none` (igual que el `<video>` del visor de animación) para que en móvil el toque nunca dispare el visor nativo de imagen a pantalla completa: en la galería lo captura el botón del tile y en el visor el botón que abre el lightbox.
- **Backfill**: `node db/backfill-image-variants.mjs` deriva las que falten de lo que ya está en la galería (idempotente; `LIMIT=n` acota el lote).

## Configuración por usuario

Página en `/soporte/configuracion` (pestaña *Configuración* de la sección *Ayuda* de la barra inferior); UI en `src/components/configuracion/configuracion-view.tsx`, acción en `src/app/actions/configuracion.ts` y persistencia en `src/server/images/settings.ts`.

- **Menú interno**: `/soporte/configuracion` es el punto de entrada y lleva un **menú de secciones** (`src/components/configuracion/configuracion-menu.tsx`) con enlaces reales: *Modelos de imagen* (`/soporte/configuracion`) y *API de licencias* (`/soporte/configuracion/api-licencias`). Cada sección tiene su URL (se puede abrir en pestaña nueva) y la activa se marca con `aria-current="page"` y un subrayado primario. Comparte el mismo riel de pestañas (`sectionTabClass` en `nav-layout.ts`) que las secciones de la barra inferior.
- **Qué define**: por cada nivel del control **Calidad** de la herramienta Imágenes —*Media* y *Alta*— el **modelo**, la **calidad de render** y el **tamaño de salida**. Los selectores se adaptan al modelo elegido: solo se ofrecen las calidades y los tamaños que ese modelo admite (Gemini no expone calidad; Grok no expone tamaño; el tamaño de Gemini es un nivel de resolución y el de OpenAI, píxeles). La pestaña *Configuración* del riel de Soporte apunta a `/soporte/configuracion`; las pestañas de cada sección viven en `children` de `navSections` (`src/components/dashboard/nav-config.ts`) y las dibuja `SectionTabs` con `usePathname`.
- **Calidad y tamaño**: la calidad va al gateway como `providerOptions.<proveedor>.quality` y el tamaño según la familia del modelo (píxeles `size` en OpenAI, nivel de resolución `imageConfig.imageSize` en Gemini, ninguno en Grok). La omisión es la **máxima calidad** que cada modelo admite (`high` en OpenAI, `medium` en Grok) y el tamaño estándar de su familia (`1024x1024` en OpenAI, `1K` en Gemini). Cambiar de modelo en la UI reajusta la calidad y el tamaño a los que ese modelo admite. El costo depende de ambos: `gpt-image-2.5-sunburst` a 1024×1024 va de ~US$0.04 (`auto`) a ~US$0.05 (`high`); `gemini-3.1-flash-image` cuesta ~US$0.045 (512), ~US$0.067 (1K), ~US$0.101 (2K) y ~US$0.151 (4K); `grok-imagine-image-2.0` ~US$0.04 (`low`) o ~US$0.06.
- **Alcance**: la selección es **por usuario** (tabla `user_settings`, `db/settings-schema.sql`, una fila por `user_id` con modelo, calidad y tamaño de cada nivel), no global: cada cuenta elige sus modelos y el servidor los aplica al generar. La página y la acción exigen sesión (`requireUser`).
- **Omisión**: mientras un usuario no guarde nada, la selección es la de `.env` — `IMAGE_MODELS`, un modelo por nivel: el primero es *Media* y el segundo *Alta*. Un modelo, una calidad o un tamaño configurados que ya no son válidos caen de vuelta a la omisión de ese nivel, para que la herramienta nunca apunte a algo inexistente.
- **Aplicación en el servidor**: la UI manda el **nivel** (`media` / `alta`) y el aspecto, nunca el modelo ni la calidad: `generateImage` resuelve contra la selección del usuario y, si el nivel no existe, usa el primero configurado. La columna `quality` de `image_generations` guarda la calidad realmente usada.
- **Cambio por variables de entorno**: `IMAGE_MODELS` (`.env`) deja de ser el mecanismo principal —la UI lo reemplaza— y queda como la omisión y como el orden de fábrica. Editarla exige **reiniciar el proceso** (`pm2 restart distribuidor-tvbox`): Next carga el `.env` al arrancar el server, y el valor se lee en cada request. Si además se agrega un modelo nuevo al catálogo, hay que recompilar (`npm run build`) porque el registro vive en el código.

### API de licencias

Sección `/soporte/configuracion/api-licencias` (misma página, segunda pestaña del menú interno); UI en `src/components/configuracion/licencias-api-view.tsx`, acciones en `src/app/actions/licencias.ts` y persistencia en `src/server/flujotv/settings.ts`.

- **Qué hace**: pide la **clave de la API de licencias (FlujoTV)** y activa el módulo del Lab (`/soporte/lab/flujotv`) sin tocar el servidor. Antes de guardarla la **comprueba contra el servicio**: un `200` confirma la clave, un `401` la descarta, un `403` avisa de que falta un scope y un `429` recuerda respetar el `Retry-After`.
- **Guardado**: la clave se cifra con **AES-256-GCM** (`src/server/flujotv/crypto.ts`) y se guarda en `flujotv_settings` (`db/flujotv-settings-schema.sql`, una fila). El material de cifrado sale de `FLUJO_ENCRYPTION_SECRET` y, si no existe, de `DATABASE_URL`: rotarlo invalida las claves guardadas y hay que volver a introducirlas.
- **Prioridad**: la clave guardada en el panel manda sobre la del entorno (`FLUJO_API_KEY` o `FLUJO_API_KEY_FILE`), que queda como respaldo. *Desactivar* borra la fila y el módulo vuelve a la del entorno.
- **Permisos**: solo un **admin** guarda, prueba o desactiva la clave; el resto ve el estado. El navegador nunca recibe la clave en claro: solo un identificador parcial (`fltv1_••••••0000`).
- **Cifrado en tránsito**: la clave viaja únicamente en el header `X-API-Key`; nunca en la URL, la cookie ni el fragmento, y nunca se registra (en los logs solo queda el identificador parcial).

### API FlujoTV

Consola en `/soporte/lab/flujotv` (**solo admin**; hoy se alcanza desde *Configuración → API de licencias* con el botón *Abrir API FlujoTV*); UI en `src/components/lab/` (`flujo-lab.tsx` con las pestañas, `clientes-panel.tsx`, `resellers-panel.tsx`, `licencias-panel.tsx`, `consola-panel.tsx`, `flujo-status-card.tsx`), servidor en `src/server/flujotv/` y proxy autenticado en `src/app/api/flujotv/`. La consola permite operar la API de licencias sin pasar por el cobro de Mercado Pago.

- **Autenticación**: la clave se resuelve **solo en el servidor**, con `FLUJO_API_KEY` o con el fichero que apunte `FLUJO_API_KEY_FILE` (`config.ts`); viaja únicamente en el header `X-API-Key` (`client.ts`) y la interfaz solo muestra un identificador parcial (`fltv1_••••••0000`). La base por defecto es `https://api.eortizs.people-negocios.com` (`FLUJO_API_BASE`).
- **Endpoints**: `GET /health` (público, para el estado), `GET /get_clients`, `GET /search_clients`, `GET /find_user`, `GET /users/validity`, `GET /resellers` (disponibilidad de resellers; el desglose activo/inactivo por reseller se cuenta desde `/users/validity` con el campo `distributor`, que también alimenta el mapa `userResellers` usuario→reseller que expone `GET /api/flujotv/resellers` —solo la llave del sub-reseller `distributor`/`distribuidor`: la llave `reseller` es la cuenta padre y es constante en todas las filas—) y `GET /licencias` (historial). `POST /licenses/{user_name}/renewals` (renovación upstream) solo lo invoca el servidor, desde el webhook de Mercado Pago y el reintento admin (ver [Pago de licencias (Mercado Pago)](#pago-de-licencias-mercado-pago)). El refresco real (`GET /list_clients`, `GET /cache`, ~90 s) solo se dispara desde una acción explícita con confirmación: el botón *Recargar* de la pantalla Clientes y de la pestaña Clientes del Lab (target `list_clients`) y *Refrescar panel* en la tarjeta de estado del Lab.
- **Normalización**: la API devuelve formas heterogéneas; `service.ts` las lleva a un modelo estable (estado *activo* / *vencido* / *pendiente*, vencimiento y días restantes) y reintenta con otra firma de parámetros solo si el servicio responde 400/422. El vencimiento del cliente se lee del campo **`end_date`** que devuelven `/get_clients` y `/find_user` (formato `YYYY-MM-DD HH:mm:ss`), de donde salen la columna *Vence* y los días restantes; los estados `Válido` e `Inválido` del panel se mapean a *activo* y *vencido*. Otros alias de fecha (`expires_at`, `fecha_expiracion`, …) se aceptan por si el servicio cambia de forma. El cliente individual de **`/find_user`** llega como **objeto único** (`{ success, message, user: {...} }`) y no como arreglo: `getFlujoClient` desenvuelve primero colecciones (`findArray`) y luego el registro único (`findRecord`, llaves `client`/`user`/`cliente`/`data`), porque normalizar el sobre entero producía un cliente degenerado (`userName: "#1"`, sin llave de distribuidor) y el guardia de alcance del cobro de Mercado Pago rechazaba con `403` a los propios clientes del distribuidor — el perfil admin no lo sufría porque su alcance `all` se salta ese guardia.
- **Alcance por perfil**: los mismos endpoints alimentan la pantalla Clientes y el Lab, de modo que el alcance del distribuidor (ver [Alcance de los datos FlujoTV por perfil](#alcance-de-los-datos-flujotv-por-perfil)) también recorta lo que este módulo muestra a un perfil distribuidor; la consola cruda (`/api/flujotv/raw`) queda como herramienta de diagnóstico del admin.
- **Sin renovación directa**: el Lab ya no renueva licencias — toda renovación pasa por el cobro de Mercado Pago (ver [Pago de licencias (Mercado Pago)](#pago-de-licencias-mercado-pago)). La renovación upstream exige el header `Idempotency-Key` (1 a 200 caracteres imprimibles); el webhook la usa con la clave determinista `mp-<orderId>` para que los reintentos nunca sumen meses dos veces. La consola cruda (solo admin) sigue permitiendo operar la API a mano como herramienta de diagnóstico.
- **Datos sensibles**: por defecto las respuestas omiten `password` y `notes`; `include_credentials=true` solo se pide cuando el operador marca la casilla, y la consola del laboratorio oculta los campos sensibles de la respuesta.
- **Errores**: 401 (clave ausente/expirada/revocada), 403 (falta de scope), 409 (conflicto de idempotencia), 429 (límite por clave, con `Retry-After`), 503 (base de claves no disponible; `renewal_timeout` avisa de reconciliar antes de reintentar) y 504 (timeout) llegan al navegador como mensajes accionables.

## Animación con agente EVE

Chat en `/modulos/animacion` (sección *Módulos*, debajo de *Imágenes*); agente en `agent/`, UI en `src/components/herramientas/animacion/` (`animacion-studio.tsx` con las pestañas y la galería, `animacion-agent.tsx` con el chat y el cronómetro) y montaje same-origin en `/eve/v1/*` con `withEve()` (`next.config.ts`). El agente **produce video real** (mp4 con imagen y sonido) con el toolkit [claude-motion](https://github.com/whaleyxbt/claude-motion) ejecutándose en un sandbox Docker.

- **Agente**: `agent/agent.ts` define el modelo de forma **dinámica** (Vercel AI Gateway): `defineDynamic` con resolvers en `session.started`, `turn.started` y `step.started`, de modo que cada llamada al modelo puede usar uno distinto (ver [Presupuesto por turno](#presupuesto-por-turno)). Desactiva las herramientas por defecto (`defaultTools: false`); `agent/instructions.md` fija el rol de productor de video en español (storyboard → `timeline.json` → escenas → review loop → cue sheet de sonido → render/mux) y `agent/channels/eve.ts` implementa el canal HTTP.
- **Adjuntos al agente**: el ícono de papel clip del área de texto permite adjuntar hasta **6 archivos** (10 MB cada uno, 15 MB en total por turno) al turno. La UI los manda como partes de archivo del `UserContent` de AI SDK (`createDataUrlFilePart` de `eve/client`: data URL + `mediaType` + `filename`), de modo que eve los deja en el sandbox de la sesión (`/workspace/.eve/attachments/`): el modelo **ve los bytes** de PNG/JPEG/GIF/WebP ≤ 3 MiB y PDF ≤ 20 MiB, y cualquier otro formato llega como etiqueta con su ruta para que el agente lo abra con `read_file` o `bash`. Los chips sobre el área de texto muestran nombre y tamaño y permiten quitar un adjunto antes de enviar; ya en el chat, los adjuntos enviados se vuelven a mostrar en la burbuja del usuario (eve los proyecta como partes `file` con `filename`, `mediaType` y `size`). **Tope del body**: los adjuntos viajan dentro del JSON del POST a `/eve/v1/session` y Next.js proxya ese body con `experimental.proxyClientMaxBodySize` (10 MB por defecto): sin subirlo, un turno grande se trunca y falla con un 500. `next.config.ts` lo fija en 64 MB y la UI limita el turno a 15 MB de adjuntos (≈ 21 MB de body en base64) para quedar holgadamente por debajo.
- **Presupuesto por turno**: la UI (`animacion-agent.tsx`, control *Presupuesto* encima del área de texto) deja elegir el **presupuesto** del turno con un slider de tres pasos (**bajo**, **medio**, **alto**) en vez del nombre del modelo. Cada paso corresponde al modelo que ocupa la **misma posición en `ANIMATION_MODELS`** (`.env`, separados por coma; el primero es el default): con `ANIMATION_MODELS=deepseek/deepseek-v4.1-flash-1017,anthropic/claude-haiku-5.5,openai/gpt-6.1-sol`, **bajo** = DeepSeek V4.1 Flash, **medio** = Claude Haiku 5.5 y **alto** = GPT-6.1 Sol. El modelo del paso elegido viaja como `clientContext` (`modelo-seleccionado: <id>`), que eve expone al resolver dinámico como mensaje `user-role` **efímero** (no se persiste en el historial durable). Los IDs válidos y su orden salen de `ANIMATION_MODELS` y el catálogo vive en `src/server/animaciones/models.ts` (que además expone `BUDGET_LABELS` y `animationBudgetSteps` para el mapeo presupuesto → modelo), que declara por modelo —según lo que reporta el catálogo del AI Gateway (`GET https://ai-gateway.vercel.sh/v1/models`, campo `reasoning_options`, consultado el 2026-10-20)— los niveles de razonamiento disponibles, el **nivel máximo**, la ventana de contexto y el tope de salida:

  | Modelo | Niveles que reporta el gateway | Máximo | Contexto |
  |---|---|---|---|
  | `minimax/minimax-m3.1-flash` | low, medium, high, xhigh, max | `max` | 1,000,000 |
  | `xiaomi/mimo-v2.6-pro` | none, minimal, low, medium, high | `high` | 1,048,576 |
  | `anthropic/claude-haiku-5.5` | none, low, medium, high, xhigh, max | `max` | 1,000,000 |
  | `deepseek/deepseek-v4.1-flash-1017` | none, low, high, max | `max` | 1,048,576 |
  | `openai/gpt-6.1-sol` | low, medium, high, xhigh, max | `max` | 1,050,000 |

  El **razonamiento máximo se fija explícitamente en cada request**: el envoltura de `agent/agent.ts` inyecta `reasoning` (nivel nativo del proveedor, incluido `max`, que la unión de eve no admite a nivel de agente) y `maxOutputTokens` en cada llamada. Un ID desconocido o ausente cae al default; la selección se reevalúa **antes de cada paso del turno**, así que escribir código, renderizar o entregar archivos usa el modelo elegido.
- **Skills** (`agent/skills/{motion-design,review-loop,sound-design,web-sims}/SKILL.md`): las cuatro skills de claude-motion, que el modelo carga bajo demanda con `eve__skill`. Procedencia: vendidas del upstream (commit `e627941543d9988b155dc610bb9cc0115a5e365e`), licencia [MIT](https://github.com/whaleyxbt/claude-motion/blob/main/LICENSE).
- **Toolkit y sandbox**: el código del toolkit vive como semilla en `agent/sandbox/workspace/` (raíz de `/workspace` en el sandbox; ver `agent/sandbox/workspace/PROVENANCE.md`) y `agent/sandbox/Dockerfile` construye la imagen base (`node:20-bookworm-slim` + `ffmpeg`, `python3`, `chromium`, `ca-certificates`, `fonts-liberation`). `agent/sandbox/sandbox.ts` corre `prepare` una vez por generación durante `npm run build` (dentro de un contenedor temporal): `npm ci`, Chromium de Playwright para el pipeline `sims/` y verificaciones de ffmpeg/python3/node; el resultado se comitea como **imagen template** (eve-sandbox-template, ~2.5–3 GB en disco) y las sesiones nuevas arrancan de ahí en segundos. Remotion usa `/usr/bin/chromium` (via `REMOTION_BROWSER`) y los renders consumen CPU del host: piezas cortas y drafts a `--scale 0.5`.
- **Red del sandbox**: `allow-all` (el contenedor sale a internet; necesario para depencias externas de build y renders que las pidan). Para endurecerlo, cambiar a `networkPolicy: "deny-all"` en `agent/sandbox/sandbox.ts` y re-ejecutar `npm run build`.
- **Herramientas**: `bash`, `read_file` y `write_file` re-exportadas de eve (`agent/tools/`), más la propia **`guardar_archivo`**: copia un archivo del sandbox al almacenamiento del usuario (`kind: generated`, límite de 250 MB por archivo vía `maxBytes` en `saveUserFile`), lo indexa en `animation_deliverables` (best effort: un fallo de indexado solo se registra y nunca rompe la entrega) y devuelve `/api/files/<id>`, que el chat reproduce inline (`<video>`/`<audio>` en el render Markdown de `animacion-agent.tsx`). Las entregas quedan listables en `/api/files?kind=generated` (ver [API](#api)); el `/workspace` del sandbox persiste durante la conversación, no entre conversaciones.
- **Galería de entregables**: `GET /api/animaciones` devuelve los entregables vivos (con `file_id`), el total, el costo acumulado (`totalCostUsd`/`totalCostMxn`, este último `null` si algún día carece de FIX) y el `totalTimeMs` de trabajo; `DELETE /api/animaciones/[id]` hace soft-delete y libera el archivo, pero conserva costo y tiempo en los acumulados. La UI (`src/components/herramientas/animacion/animacion-studio.tsx`) agrega la pestaña *Galería* con tiles por tipo (video con primer frame, audio, imagen, PDF), badge de costo MXN por entregable (costo acumulado de la conversación que lo produjo), tiempo de trabajo por conversación, visor con reproductor/descarga y borrado con confirmación. La lista se refresca al cambiar de pestaña y cuando un turno del agente termina.
- **Tarificador por turno**: el hook `agent/hooks/tarificador.ts` observa el stream de EVE. Cada `step.completed` registra costo/tokens en `animation_costs` (`UPSERT` por `session_id, turn_id, step_index`: un step reintentado se sobrescribe, sin doble conteo) junto con el **modelo real** que ejecutó ese paso (el `modelId` que reporta `step.started`, que con el selector de presupuesto puede cambiar dentro del turno); al cerrar el turno (`turn.completed`/`turn.failed`/`turn.cancelled`) el costo sumado del turno se **espeja al control de gastos** con categoría *Animación*, `created_by: "sistema"`, el modelo usado anotado en las notas y ancla única `(source_animation_session_id, source_animation_turn_id)` (idempotente). Los fallos del hook se registran y nunca afectan el turno.
- **Tarificador en vivo en el chat**: junto al cronómetro, el margen derecho de la fila de estado muestra el **costo acumulado de la conversación en MXN** (tarificador de `animation_costs`, al TC FIX del día). Lo alimenta `GET /api/animaciones/costo?sessionId=…` (`getAnimationSessionCost` en `src/server/animaciones/service.ts`): el chat lo lee al montar, cada 4 s mientras el agente trabaja y al cerrar el turno; si no hay tipo de cambio disponible degrada a `US$…` etiquetado. El costo se muestra con 4 decimales porque los montos por paso son fracciones de centavo.
- **Contador de tiempo**: además del cronómetro en vivo del chat (`ClockIcon`, ticks de 1 s mientras el turno está en vuelo, acumula turnos y se reinicia con *Nueva conversación*), el hook abre un turno en `animation_turns` (`turn.started`) y lo cierra computando `duration_ms = (ended_at − started_at) − wait_input_ms`: las ventanas `turn.waiting` con `on: "input"` (espera de respuesta humana) se descuentan; las esperas `on: "tasks"` cuentan como trabajo del agente. Cada tarjeta y el visor muestran el tiempo de trabajo acumulado de su conversación (`SUM(duration_ms)` por sesión) y el header de la galería el total del usuario.
- **Autenticación**: el canal valida la misma cookie `reseller_session` del panel contra Postgres mediante `src/server/auth/session-lookup.ts` (compartido con `src/server/auth/session.ts` y `src/proxy.ts`). Cada sesión EVE se liga a su creador en la tabla `eve_sessions` (`db/eve-sessions-schema.sql`, FK a `users`): otro usuario autenticado recibe 401 al intentar continuar, leer o resetear una sesión ajena. El middleware excluye `/eve/` y `/.well-known` del redirect a `/login` (la API responde 401, no HTML) y `GET /eve/v1/health` es pública.
- **Rate limit**: 20 mensajes/min por usuario (en memoria, por proceso) aplicado en `onMessage`; los streams y las creaciones de sesión no cuentan.
- **Modelo y rebuild**: `AI_GATEWAY_API_KEY` y `ANIMATION_MODELS` viven en `.env`. **Tope de salida obligatorio**: el AI Gateway recorta `maxOutputTokens` a 4096 en modelos que no figuran en su registro; con reasoning alto el modelo agota ese presupuesto solo en razonar y eve recibe pasos vacíos (`empty model response` → reintento → turno estacionado). Por eso `agent/agent.ts` envuelve el modelo del gateway inyectando `maxOutputTokens` en cada llamada (`ANIMATION_MAX_OUTPUT_TOKENS`, default 65536, acotado al tope que declara el catálogo de cada modelo) y el **nivel máximo de razonamiento** del modelo, y declara `modelContextWindowTokens` por selección (eve lo exige con modelos-objeto para planear la compactación; hoy sale del catálogo del gateway). Las instrucciones, las tools y la imagen template se congelan al compilar: tras cambiarlas hay que ejecutar `npm run build` (que corre `eve build` —incluida la preparación del sandbox si cambió el Dockerfile, la semilla o `prepare`— antes de `next build`) y luego `pm2 restart distribuidor-tvbox`. `ANIMATION_MODELS` se lee al arrancar el proceso, así que un cambio de lista solo necesita `pm2 restart distribuidor-tvbox`. Tras deploys, limpiar templates viejos con `docker image prune`.
- **Runtime y estado**: `next start` levanta el agente compilado (`.output/server/index.mjs`) en loopback (4274) y Next proxya `/eve/v1/*` por el mismo origen; el estado durable de las sesiones vive en `.eve/.workflow-data` (incluir en backups y no versionar).
- **UI**: pestañas *Agente* / *Galería* (variante `line`, paneles `keepMounted`) sobre el patrón de `/imagenes`. El chat usa `useEveAgent` de `eve/react` sobre los componentes ReUI del chat (`message`, `bubble`, `message-scroller`, `input-group`), con composer multilínea, detener respuesta, nueva conversación, sugerencias iniciales, render Markdown de las respuestas, línea de actividad por llamada a herramienta (`text-xs`), cronómetro de tiempo de trabajo, selector de presupuesto (slider de `src/components/ui/slider`, patrón ReUI `c-slider-9`) y reproductor inline para los enlaces `/api/files/*.mp4|webm|mov|wav|mp3`. La UI no persiste la conversación entre visitas; el servidor sí conserva las sesiones (y la galería persiste los entregables globalmente).
- **Uso y prueba**: pide el video por chat; el agente pregunta formato/duración/marca solo si faltan datos clave (máximo dos preguntas). Prompt de prueba completo del pipeline (timeline → escenas → review loop → sonido → render → entrega): *"Produce un video de presentación del TVBox Togu: 8 segundos, 9:16, colores azul oscuro y blanco, tipografía Inter; 3 escenas (logo, 3 beneficios, llamado a la acción), revisa con review-loop, sonido mínimo con sfx, draft a --scale 0.5 antes del render final, y entrégalo con guardar_archivo."* Smoke rápido del sandbox (sub-minuto): *"Renderiza un draft de 2 segundos a 320×180 de EffortVideo con --scale 0.3 y entrégalo con guardar_archivo."* Para probar el selector de presupuesto: elige un nivel (bajo/medio/alto), pide una tarea de código (*"crea con write_file el archivo /workspace/src/demo.tsx con el contenido export function Demo() { return <div>hola</div> }"*) y revisa que el `step.started` reporte el modelo que corresponde a ese nivel y que el archivo exista en el sandbox. Un render real tarda minutos y consume CPU del host; los archivos entregados quedan en `/api/files?kind=generated`.

## Calculadora

Herramienta de cálculo rápida en `/modulos/calculadora` (herramienta *Calculadora* del hub de Módulos): lógica pura en `src/lib/calculadora.ts`, UI cliente en `src/components/herramientas/calculadora/` (`calculadora.tsx` con pantalla y teclado; el regreso al hub viaja en la cabecera del shell) y página en `src/app/(dashboard)/modulos/calculadora/page.tsx`. Todo el cálculo ocurre **en el navegador** (sin servidor ni persistencia) con una máquina de estados por reducer — sin `eval`, `Function` ni parser de expresiones: las operaciones se encadenan **en orden de pulsación** (`2 + 3 × 4 = 20`), según lo acordado para un uso comercial rápido.

- **Pantalla estilo iOS**: durante la operación, la línea grande muestra la operación en construcción (`25+2,500`) y debajo el **resultado previo** en gris (`2,525`) recalculado en vivo con cada tecla; al pulsar `=` la operación desaparece y el resultado queda solo en grande. En reposo, la línea grande muestra la entrada o el resultado. El texto para la vista lo producen los helpers de render de `src/lib/calculadora.ts` (`calculatorExpression`, `calculatorPreview`, `formatCalculatorEntryText`): el estado guarda los números **sin comas** para que `Number()` siga parseándolos, el agrupado de millares ocurre solo al renderizar.
- **Comportamiento** (contrato probado): **porcentaje comercial** — aislado divide entre 100 (`10 %` → `0.1`), con `+`/`−` pendiente es relativo al acumulador (`200 + 10 % = 220`) y con `×`/`÷` usa la fracción (`200 × 10 % = 20`); pulsaciones consecutivas de `%` sin escribir nada nuevo no se re-aplican (editar la entrada lo permite). Un segundo operador sin operando reemplaza al anterior (`8 + × 2 = 16`); `=` sin segundo operando deja el valor actual; `=` repetido repite la última operación (`2 + 3 = =` muestra `8`; `C` reinicia esa memoria); un dígito tras el resultado abre entrada nueva y un operador continúa desde el resultado; el cambio de signo (`±`) invierte la entrada activa y también un resultado ya calculado; el retroceso solo edita la entrada activa (nunca un resultado).
- **Formato y límites**: miles con coma al renderizar (`2,500`, `1,234.5`), entrada limitada a **15 caracteres de cifra** (un solo punto decimal), resultados normalizados a 15 cifras significativas (sin residuos tipo `0.30000000000000004`) con **notación científica** cuando el número no cabe en la pantalla (`1.5e+18`, `1e-7`), `-0` normalizado a `0`, y errores legibles (`No se puede dividir entre cero`, `Resultado fuera de rango`): los operadores y `%` en estado de error no propagan valores inválidos, y un dígito, el punto o `C` permiten empezar otra operación.
- **Teclado físico**, limitado al área de la calculadora (`onKeyDown` en el contenedor): cifras, `.`/`,`, `+ - * /`, `%`, `Enter`/`=`, Retroceso y `Esc`/Supr. Ignora atajos con Ctrl/Meta/Alt y, con un botón enfocado, solo salta Enter/Espacio (que ya activan el botón por sí mismos): sin dobles ejecuciones.
- **Pantalla a todo lo alto**: la página mide exactamente el espacio entre cabecera y barra inferior (`--shell-viewport-height` − `--shell-header-height` − `--shell-bottom-nav-space`) y el tamaño de las teclas circulares se resuelve con **container queries** (`container-type: size` y unidades `cqw`/`cqh` en clases arbitrarias de Tailwind — el proyecto redirige `*.css` al loader de Tailwind en Turbopack, así que **no** se usan CSS modules) entre 2.75 y 6 rem: crecen con la pantalla y se encogen si el teclado virtual la reduce. La línea grande escala por longitud (`text-6xl/7xl` para valores cortos, bajando hasta `text-xl` en los largos) con desplazamiento horizontal sin scrollbar visible.
- **Pestañas fuera, rótulo y regreso en la cabecera**: Módulos ya no tiene riel de pestañas (la sección no declara `children` en `nav-config.ts`); el rótulo *Módulos* viaja en la cabecera, a la derecha de la mascota (`titleInHeader` de la sección, resuelto por `findNavHeaderTitle`); en las rutas de herramienta (más profundas que el hub) la sección publica `backHref` y `findNavBack` (`nav-config.ts`) hace que `dashboard-shell.tsx` dibuje el regreso como **un solo botón que une chevron y rótulo** (ghost con `Link` real: `ChevronLeftIcon` en `text-foreground` —negro puro en tema claro, blanco puro en oscuro— seguido del rótulo del módulo activo («Calculadora», resuelto por `findNavModulo` sobre el catálogo `MODULOS`), todo dentro del mismo `Button` que navega al hub y envuelto por el `<h1>` de la página); sobre el propio hub el botón no aparece (el rótulo queda como texto simple). Como parte del mismo ajuste de espacio, la cabecera y la barra inferior del shell quedaron **sin bordes** (sin `border-b` en `dashboard-shell.tsx` ni `border-t` en `bottomNavClass.bar`), y la Card de la calculadora sin su anillo (`ring-0`).
- **Accesibilidad**: nombres accesibles en español para iconos y símbolos (`aria-label="Suma"`, `"Borrar último dígito"`, etc.), pantalla como `role="region"` enfocable con el teclado y con `aria-describedby` hacia una descripción oculta del uso del teclado, y una región viva moderada (`role="status"`) que anuncia **solo resultados y errores** — nunca cada dígito — mediante el campo `announce` del estado. La jerarquía de botones usa una sola acción primaria (`=`, variante `default`), cifras en `secondary`, operaciones y utilidades en `outline`.
- **Verificación y despliegue**: `node scripts/test-calculadora.mjs` (34 pruebas de la lógica pura con `node:assert/strict`, patrón de `scripts/test-annotations.mjs`; Node 24 elimina los tipos al importar el `.ts`) más `npm run lint`, `npx tsc --noEmit` y `npm run build`. La UI y la integración se verificaron con capturas y pruebas de interacción sobre el DOM (clics por `aria-label`) en un servidor de desarrollo local con una ruta de preview temporal que **nunca se publica**. El despliegue es el estándar (ver [Deployment](#deployment)): `npm run build` + `pm2 restart distribuidor-tvbox`.

## Lista de compras con IA

Herramienta en `/modulos/lista-de-compras` (hub de Módulos): una **única lista persistente por usuario** que se alimenta con lenguaje natural escrito o dictado. Dominio puro en `src/lib/lista-compras.ts` (compartido por cliente, servidor y pruebas), intérprete LLM en `src/server/lista-compras/llm.ts`, repositorio transaccional en `src/server/lista-compras/repository.ts`, rutas `/api/lista-compras*`, UI en `src/components/herramientas/lista-compras/lista-compras.tsx` y página en `src/app/(dashboard)/modulos/lista-de-compras/page.tsx`. Registrada en el catálogo del hub (`MODULOS` en `src/lib/modulos.ts`, icono `ShoppingBasketIcon`).

- **Un área de texto, sin formularios**: el campo (`InputGroup` con `InputGroupTextarea`, card sin anillo exterior) es la única entrada; el **micrófono** (Web Speech API, mismo hook y robustez móviles del módulo Imágenes: acumulación por índice sin duplicados, `es-MX`) vive dentro de la caja, abajo a la derecha, como botón outline circular solo-icono que pasa a cuadrado destructivo mientras dicta. *Agregar* (media anchura) envía la instrucción; *Nueva* (la otra mitad) abre el diálogo de confirmación y, al aceptar, **vacía la lista sin pasar por el LLM** (reemplazo por lista vacía). Enter envía; Shift+Enter salta de línea. Las casillas circulares marcan comprado sin pasar por la IA, la cantidad y unidad van debajo del nombre (`2 kg`, `12 pzas`; sin cantidad no se inventa un 1), los productos **estimados** por pedido explícito del usuario llevan badge, y una **barra de progreso** sobre las categorías celebra el 100 % con **confeti** (`canvas-confetti`, solo en la transición al 100 % — no al cargar una lista ya completa — y respeta `prefers-reduced-motion`). Cada fila lleva una **X** (destructiva silenciosa) para borrar: el clic es la confirmación explícita y el PATCH llega ya confirmado. La card no tiene textos explicativos: el placeholder orienta (`Agregar a la lista...`) y el estado vacío queda en el icono y el título.
- **Interpretación con LLM (solo lectura)**: `POST /api/lista-compras/interpretar` envía la instrucción y un snapshot compacto de la lista (IDs estables para referencias) a **OpenRouter** con la clave del asistente (`OPENROUTER_API_KEY`; modelo `LISTA_COMPRAS_MODEL` o, por omisión, `ASISTENTE_MODEL`), sin streaming, con `response_format: json_object` y razonamiento excluido (`reasoning: { exclude: true }`: el modelo del panel razona y agota presupuestos cortos sin emitir contenido). Devuelve **operaciones acotadas** (agregar, actualizar, eliminar, marcar, reemplazar, vaciar) o una aclaración; **nunca escribe la base** ni recibe credenciales, identidad o historial de otros módulos. Reglas del intérprete: fiel al pedido (sin inventar productos ni cantidades), categorías cerradas de supermercado con *Otros* de respaldo, unidades canónicas con conversión previa (`500 ml` + `1 l` → `1.5 l`), referencias por ID contra el snapshot real (una referencia inexistente descarta la operación y se avisa en lugar de adivinar), duplicados que no se duplican (volver a pedir un producto lo regresa a pendiente), sumas solo con unidades compatibles (`agrega otros 2`) y `cambia a 3` como establecer. La salida se valida con Zod y con los validadores estrictos del dominio antes de proponer nada; rate limit propio de 20/min por usuario y timeout de 30 s. El texto enviado solo se limpia del borrador tras la persistencia exitosa.
- **Persistencia y concurrencia** (`db/shopping-list-schema.sql` + `db/apply-shopping-list.mjs`, idempotente): `shopping_lists` (una fila por usuario, productos en JSONB validado por el servidor, `revision` incremental como compare-and-swap) y `shopping_list_mutations` (log por `(user_id, request_id)` que hace **idempotentes los reintentos**: mismo `request_id` + mismo payload devuelve el snapshot actual sin reaplicar; mismo id con payload distinto se rechaza). El `PATCH` es transaccional con `FOR UPDATE`: revisión distinta → **409 con el snapshot actual** (la UI refresca, conserva el borrador y pide volver a agregar, nunca sobrescribe a ciegas); operaciones destructivas sin `confirmar: true` → 422 `confirmacion_requerida`. La necesidad de confirmación (vaciar, reemplazar —aun con lista vacía resultante— o eliminar productos) **se deriva en servidor** de las operaciones contra la lista real; nunca se confía en un indicador del LLM ni del cliente. El diálogo de confirmación (`AlertDialog`) lo presenta el cliente, pero el servidor es quien lo exige. Los IDs de productos nuevos los genera el servidor (`randomUUID`).
- **Dominio puro y probado**: `src/lib/lista-compras.ts` concentra categorías cerradas (11, de *Frutas y verduras* a *Otros*), unidades canónicas con alias de dictado (litros → `l`, piezas → `pza`), límites (nombre ≤ 80, ≤ 200 productos, cantidad > 0 y ≤ 9999 con 2 decimales, ≤ 50 operaciones por tanda, texto ≤ 4000 caracteres) y la aplicación determinista de operaciones: una operación con ID desconocido **rechaza la tanda completa** (casi siempre significa que la lista cambió en otro lado) y los productos comprados se conservan salvo que el pedido los afecte. `scripts/test-lista-compras.mjs` (25 pruebas con `node:assert/strict`) cubre normalización, duplicados, sumas compatibles/incompatibles, confirmación destructiva, agrupación y límites.
- **UI resiliente**: carga inicial desde el servidor (sin parpadeo), estados de carga (skeleton), vacío (icono + título), error con *Reintentar* y notas informativas/de error junto al campo; las casillas quedan bloqueadas hasta que el PATCH confirma y hacen rollback visible si falla; el refresco al volver a enfocar la pestaña descarta respuestas obsoletas si mientras voló se aplicó algo localmente, y el dictado convive con la escritura (teclear mientras se dicta cancela la sesión de voz).
- **Verificación y despliegue**: `node scripts/test-lista-compras.mjs` + `npm run lint` + `npx tsc --noEmit` + `npm run build`; el E2E del API (aislamiento entre usuarios, idempotencia, 409, confirmación e interpretación real) se ejecutó contra producción con usuarios QA efímeros y se limpió al terminar. Despliegue estándar (ver [Deployment](#deployment)) con la migración `node db/apply-shopping-list.mjs` **antes** del build (paso obligatorio en [AGENTS.md](AGENTS.md)).

## Alta de tickets con IA

Herramienta en `/modulos/alta-de-tickets` (hub de Módulos): registro de tickets de compra o gasto **a partir de la foto**, con extracción estructurada en umeJSON y revisión del propietario. Dominio puro en `src/lib/tickets.ts` (compartido por cliente, servidor y pruebas), análisis LLM en `src/server/tickets/llm.ts`, repositorio transaccional en `src/server/tickets/repository.ts`, servicio (validación de imagen + orquestación) en `src/server/tickets/service.ts`, rutas `/api/tickets*`, UI en `src/components/herramientas/tickets/tickets.tsx` y página en `src/app/(dashboard)/modulos/alta-de-tickets/page.tsx`. Registrada en el catálogo del hub (`MODULOS` en `src/lib/modulos.ts`, icono `ReceiptTextIcon`).

- **Dos vías de captura, una sola foto por ticket**: *Tomar foto* y *Elegir archivo* son dos entradas independientes sobre el mismo hook de ReUI (`use-file-upload`); la de cámara lleva `capture="environment"` (en dispositivos sin cámara se abre el selector y la pista lo aclara). Con vista previa, *Quitar*/*Otra foto*/*Otro archivo* y el botón primario *Guardar y analizar*: el POST guarda la foto y crea el ticket **antes** de llamar al modelo, así un fallo del proveedor nunca pierde la foto (queda `failed` con mensaje y se reintenta con *Reintentar análisis*).
- **Imagen validada en servidor, nunca por el MIME del cliente**: sharp decodifica de verdad (JPEG/PNG/WebP; HEIC se normaliza a JPEG solo si el decodificador instalado lo soporta), rechaza animadas (`pages > 1`) y bombas de píxeles (lado > 12 000 px o > 40 MP) y respeta el tope global de subida. La copia que viaja al modelo corrige la orientación EXIF, quita metadatos y acota el lado a 2 200 px conservando el texto legible; el original queda intacto en disco y las variantes `low`/`thumb` se derivan solo si se piden.
- **Extracción con TICKET_SCAN_MODEL vía AI Gateway** (comparte `AI_GATEWAY_API_KEY` con Imágenes y Animación): la foto viaja como contenido multimodal privado (bytes en la petición, nunca una URL pública ni credenciales). El prompt exige transcripción fiel — texto de la imagen es **dato, no instrucción**; campo ilegible → `null`; moneda solo si está impresa el código ISO; fecha ISO o `null` si el orden día/mes es ambiguo; nunca números completos de tarjeta; imagen que no es un ticket → `esTicket: false` con aviso, jamás una compra inventada. La salida se valida dos veces (forma con Zod + contenido con el dominio) y una respuesta truncada (`finishReason: length` o > 100 KB) se **rechaza entera** en vez de guardarse a medias. Timeout de 75 s y límite de 5 análisis/min por usuario.
- **Documento umeJSON `TicketCompra` con revisión del propietario**: `db/tickets-schema.sql` + `db/apply-tickets.mjs` (idempotente, en la cadena obligatoria de [AGENTS.md](AGENTS.md)) añaden la tabla `tickets` de control — FK a `entities`/`users`/`user_files`, unicidad `(user_id, request_id)` y `(user_id, sha256)`, estado del análisis `pending|processing|succeeded|failed` con **lease de 180 s** (single-flight entre procesos y recuperación de intentos colgados tras un reinicio) — mientras los datos viven en `entities.doc.dynamicProperties` (`fileId`, `ticketSchemaVersion`, `datos`, `advertencias`, `extraccion` con modelo/fecha/intento, `revisadoAt`): el ciclo `draft → validation_required → active` queda journalado (`created`, `imported.from`, `property.updated`, `state.changed`). La extracción exitosa solo aplica sobre un borrador **sin datos** y con el intento vigente: un resultado tardío u obsoleto se descarta y jamás sobrescribe una corrección.
- **Montos exactos y conciliación honesta** (`src/lib/tickets.ts`): los importes se normalizan a cadenas decimales canónicas con redondeo half-up por aritmética de cadenas (cero flotantes) y la conciliación opera en centavos enteros: partidas↔subtotal (tolerancia de redondeo por partida), total↔subtotal−descuentos+impuestos+propina (solo con todo conocido) y cantidad×precio↔importe por partida. Las discrepancias **se muestran y no se corrigen**: manda lo impreso. Confirmar exige comercio, fecha, moneda y total conocidos (el servidor lo verifica; las partidas pueden quedar parciales con su aviso); corregir un confirmado lo devuelve a revisión; el PATCH lleva compare-and-swap por `version` (409 con recarga explícita que conserva los cambios locales para copiarlos).
- **Privacidad estricta por propietario**: `/api/tickets*` filtra siempre por el usuario de sesión — **ni un admin ve tickets ajenos** (decisión de producto) —, los endpoints genéricos de entidades excluyen `TicketCompra` del listado, exigen pertenencia en detalle y bitácora (404 sin revelar existencia), bloquean su mutación por el PATCH genérico (403 `reserved_entity_name`) y `/api/v1/ume-json/finalize` rechaza crear entidades con ese nombre (la creación solo existe por el módulo, que garantiza foto + control + idempotencia). Los eventos de tickets no se publican en el bus SSE porque el stream de admin reenvía todos los eventos `entity` (`publish: false` en las opciones del repositorio umeJSON; el resto de entidades conserva el comportamiento). La foto se sirve por `GET /api/tickets/[id]/imagen` con `private, no-store`.
- **Retención y seguridad de la foto**: la foto de un ticket es parte del registro y **no caduca** — el sweep de adjuntos (`db/sweep-attachments.mjs`) excluye los archivos referenciados por tickets antes de borrar del disco, y `DELETE /api/files/[id]` responde 409 `archivo_vinculado_a_ticket`; la FK `RESTRICT` es la última red y `deleteAccount` elimina primero los tickets del usuario para que la baja de cuenta nunca se bloquee. Alta idempotente: mismo `(user, request_id)` con el mismo archivo devuelve el ticket ya creado; el **mismo archivo** (`sha256`) con otro `request_id` devuelve el ticket existente sin pagar otro análisis (`duplicado: true`), y el mismo `request_id` con otro archivo es 409.
- **UI resiliente** (card única sin anillo, patrón Lista de compras): badges de estado (Borrador/En revisión/Confirmado + *Error de lectura*), avisos y discrepancias en alerts, ampliación de la foto en dialog, historial con miniaturas (`?variant=thumb`), paginación *Cargar más*, estados vacío/cargando/error con reintentar y detalle técnico JSON en acordeón de solo lectura. Un 409 de guardado no descarta los cambios locales: la nota ofrece recargar de forma explícita.
- **Dominio puro y probado**: `scripts/test-tickets.mjs` (24 pruebas con `node:assert/strict`) cubre montos (canonización, half-up sin flotantes, rechazo de basura), centavos exactos, fechas/horas sin ambigüedad, validación de la entrada del LLM y del formulario (recortes y descartes con aviso), conciliación (cuadra, rompe subtotal, rompe total, cantidad×precio, null = desconocido), campos para confirmar, estados y resumen. Despliegue estándar (ver [Deployment](#deployment)) con `node db/apply-tickets.mjs` **antes** del build (paso obligatorio en [AGENTS.md](AGENTS.md)); el smoke real del análisis (usuario QA efímero + ticket sintético sin PII, alta → análisis con el modelo → confirmación → foto privada → limpieza completa) se ejecutó contra producción y dejó cero restos.

## Control de gastos

Módulo de Finanzas (`/finanzas/gastos` y `/finanzas/estado-de-cuenta`); backend en `src/server/finanzas/gastos.ts`, rutas `/api/finanzas/*` y UI en `src/components/finanzas/`. Lleva un control de gastos **persistente y aislado por usuario**, que alimenta la UI, el estado de cuenta y los reportes del asistente.

- **Modelo** (`db/expenses-schema.sql`): tabla `expenses` con FK a `users` (ON DELETE CASCADE), `description` (1–300), `category` (lista cerrada), `amount` `numeric(14,6)` (> 0), `currency` (`MXN`|`USD`), `exchange_rate` + `mxn_equivalent` congelados al registro para que los reportes históricos no cambien si el tipo de cambio se mueve, `spent_on` (día hábil en `America/Mexico_City`), `notes` (≤ 1000), `created_by` (`user` | `asistente` | `sistema`), soft delete (`deleted_at`) e índices `(user_id, spent_on DESC)` y `(user_id, category)`. La columna `source_image_id` (única) liga los gastos espejo del tarificador de imágenes, y `source_animation_session_id`/`source_animation_turn_id` (índice único compuesto) los del tarificador de animación por turno.
- **Categorías cerradas** (`src/lib/finanzas.ts`, compartida por servidor y cliente): `Inventario`, `Envíos`, `Publicidad`, `Servicios`, `Imágenes`, `Animación`, `Equipo`, `Otros`. La validación acepta la categoría en mayúsculas/minúsculas y devuelve la lista permitida en el error.
- **Conversión USD → MXN**: los gastos en USD congelan el tipo de cambio **FIX de Banxico** publicado para el día del gasto (mismo módulo `src/server/banxico.ts` del tarificador, con fallback al último publicado). Si Banxico no responde, el registro no falla: el gasto se guarda sin conversión y los totales lo reportan aparte como *USD pendiente de conversión* (la UI lo marca con badge y el estado de cuenta lo detalla al pie).
- **Scoping obligatorio**: toda consulta y mutación filtra por `user_id = <usuario de la sesión>` en el servidor — la identidad nunca viene del cliente ni de argumentos del modelo. Ni `admin` ni nadie ve gastos ajenos. Validaciones: monto > 0 (≤ 9,999,999.99), fecha real `YYYY-MM-DD` sin futuro (tolerancia de 1 día), descripción/notas dentro de límites. La edición recalcula la conversión solo si cambian monto, moneda o fecha; el borrado es soft-delete.
- **UI** (patrón ReUI, ver [Convenciones de UI](#convenciones-de-ui)): **Gastos** con fila de KPIs (mes, movimientos, categoría principal, USD pendiente), data-grid con búsqueda por descripción/notas, filtro por categoría y rango de fechas, alta/edición en dialog y baja con confirmación en `AlertDialog` (toasts sonner). **Estado de cuenta** con selector de periodo (mes / 3 meses / año), KPIs, gráfico de barras por mes y desglose por categoría.
- **API**: ver [API](#api) (`/api/finanzas/gastos`, `/api/finanzas/gastos/[id]`, `/api/finanzas/estado-de-cuenta`). Los totales del estado de cuenta agregan en SQL (`SUM` sobre `numeric`), por lo que no hay pérdida de precisión por coma flotante.
- **Asistente**: las herramientas `registrar_gasto`, `consultar_gastos` y `resumen_gastos` usan la misma capa de servicio (`src/server/asistente/tools.ts`); `resumen_gastos` es la base de cualquier estado de cuenta o cálculo pedido por chat. Aceptan alias de argumentos en español/inglés para tolerar variaciones del modelo.

## Pago de licencias (Mercado Pago)

El botón de compra de la pantalla **Clientes** (`/clientes`) cobra la renovación mensual con **Mercado Pago Checkout Pro** (`purpose: "wallet_purchase"`: solo pueden pagar cuentas de Mercado Pago, wallet a wallet, sin efectivo ni tarjetas). Toda renovación pasa por cobro: no existe vía que renueve sin pago aprobado (la ruta `POST /api/flujotv/renewals` se retiró y el Lab es solo admin). Backend en `src/server/mercadopago/` (cliente `fetch` puro, sin SDK), rutas `src/app/api/mercadopago/`, cliente de navegador en `src/components/entities/pago-api.ts` y tabla `mp_orders` (`db/mp-orders-schema.sql`, aplicada con `node db/apply-mp-orders.mjs`).

### Flujo

1. El bottom sheet de compra (usuario, 1 mes, importe en MXN) llama `POST /api/mercadopago/orders`: valida sesión y alcance del distribuidor, congela el importe en la orden (`pending`) y crea la **preferencia** con `purpose: "wallet_purchase"`, `external_reference` = id de la orden, `notification_url` del webhook y `back_urls` de retorno a `/clientes?orden=<id>&estado=<aprobado|rechazado|pendiente>`. Devuelve el `init_point` y el navegador redirige al checkout.
2. El comprador paga con su cuenta de Mercado Pago. **El cobro no renueva nada por sí solo**: el webhook `POST /api/mercadopago/webhook` (público, sin sesión) consulta el pago a la API de MP (`GET /v1/payments/{id}`) y verifica estado `approved`, monto, moneda y `external_reference` contra la orden — el cuerpo de la notificación nunca es fuente de verdad. Con el pago verificado reclama la orden hacia `paid` (transición atómica) y renueva la licencia en el panel FlujoTV con la clave de idempotencia determinista `mp-<orderId>`: los reintentos de MP nunca suman meses dos veces. La orden termina `renewed` o `renewal_failed`.
3. **La renovación se verifica, no se declara**: antes de renovar se congela el vencimiento original de la licencia como línea base (`mp_orders.renewal_baseline_expires_at`, leída del panel en el primer intento) y, tras el OK del panel, se relee el vencimiento hasta verlo **cambiar** respecto a esa línea base. Un panel que responde 200 sin aplicar la renovación (falso positivo observado con los cupones QA) deja la orden `renewal_failed` con el motivo `renewal_not_applied` en lugar de un falso «renovación exitosa»; sin línea base legible la renovación tampoco se ejecuta (`renewal_unverifiable`). Aplica a los tres métodos (Mercado Pago, transferencia y cupón), al reintento admin y a la conciliación, que comparten `attemptOrderRenewal`. Cada lectura de verificación es un `/find_user` en vivo del panel (~20 s); se reintenta hasta 3 veces con pausa.
4. El navegador vuelve de MP a `/clientes?orden=…&estado=…`: un aviso muestra el resultado y sondea `GET /api/mercadopago/orders/{id}` cada 2 s; al verla `renewed` refresca la fila con una lectura en vivo del cliente y limpia la query. La llegada por el back_url de fallo no se sondea: no hubo cargo.

### Selección de método y desglose del cargo (sheet)

El sheet abre **sin método por defecto**: solo el resumen (usuario, 1 mes, importe neto en MXN) y la lista de las tres opciones — **Mercado Pago**, **Transferencia** (solo con datos bancarios en el servidor) y **Cupón** (solo con `COUPON_QA_ENABLED=1`) — sin ningún radio marcado y sin botón «Continuar». Tocar una opción abre **directamente su propia pantalla** (la lista desaparece); «Cambiar método de pago» regresa a la lista limpiando la selección, y existe en las pantallas de **Mercado Pago y Cupón** pero **no en la de Transferencia**: al llegar ahí el comprador ya hizo la transferencia, así que cambiar de método ya no aplica. Cada pantalla muestra solo su primario («Pagar con Mercado Pago», «Ya hice la transferencia» / «Enviar comprobante», «Aplicar cupón» / «Reintentar renovación»).

- **Pantalla de Mercado Pago — desglose del cargo**: tres montos — *Concepto (costo de licencia)* = `LICENSE_PRICE_MXN`, *Costo por procesamiento* y *Total a cobrar*. La comisión del procesador (**3.49% + $4.00 MXN** fijos, más **IVA 16%** sobre la comisión) se descuenta del precio final de venta, así que cobrar el precio neto depositaría menos: el total se **engrosa** con la fórmula compartida `src/lib/mp-pricing.ts` (`Precio final = (Neto + Fija×1.16) / (1 − Variable×1.16)`; con neto $100 → **$109.05**, procesamiento $9.05 — la fija se cobra una vez por pago, sobre el total del cargo). La orden se crea con ese total (`mpTotalMxn` en `createPaymentOrder`), el webhook verifica contra él y los reembolsos devuelven el total: depositan íntegros el costo de licencia.
- **Pantalla de Transferencia**: solo la información del pago (banco, titular, cuenta y concepto de pago, o el paso 2 del comprobante). El importe **neto** sigue visible en el resumen porque es el monto exacto a transferir: la orden de transferencia se congela sin recargo (no hay comisión de procesador).
- **Pantalla de Cupón**: InputOTP de 4 dígitos y el aviso de que el servidor valida y renueva al instante; sin recargo.
- **Coherencia en Paquetes FlujoTV**: el mismo engrose aplica a las órdenes de paquete pagadas con Mercado Pago (la comisión fija se cobra una vez por pago, sobre el total del paquete): las filas del selector y el total del sheet muestran el importe engrosado con la leyenda «Incluye $X de procesamiento» para que el comprador nunca vea un importe distinto al cargo real.

### Estados de la orden

| Estado | Significado |
|---|---|
| `pending` | Creada, sin pago verificado |
| `paid` | Pago verificado, renovación en vuelo (estado intermedio) |
| `renewed` | Cobro confirmado y licencia renovada en el panel — con el vencimiento nuevo verificado en `renewal_verified_expires_at` |
| `applied` | Cobro confirmado y **abono de saldo acreditado** en la cuenta del comprador (`months = 0`; terminal y con su movimiento en `saldo_movimientos`) |
| `renewal_failed` | Cobro confirmado pero la renovación falló — exige reintento (endpoint admin) o los propios reintentos de MP |
| `refunding` | Reembolso total en vuelo en la API de MP (intermedio; bloquea reintentos de renovación) |
| `refunded` | Reembolso total ejecutado; terminal: sin reintento de renovación ni nueva devolución |
| `rejected` / `cancelled` | Pago rechazado/cancelado; informativo, sin renovación. Si el comprador reintenta dentro del checkout y el pago se aprueba, la orden se recupera: el claim de pagos aprobados incluye estos estados |

### Redes de seguridad

- **Webhook perdido**: al consultar una orden `pending` con más de 90 s, el servidor busca el pago por `external_reference` en MP (prefiriendo un `approved` aunque no sea el más reciente: en Checkout Pro el comprador puede reintentar un pago rechazado y cada intento es un pago nuevo con la misma referencia) y lo procesa como si hubiera llegado la notificación.
- **Rechazo sin ejecución (cooldown del panel)**: el panel puede responder HTTP 200 con `success: false` cuando hay una operación muy reciente para el mismo usuario (cooldown post-éxito de ~5 min u otra compra en curso); `renewFlujoLicense` lo rechaza en la puerta de entrada como `renewal_rejected` con la espera estimada en el mensaje (antes ese 200 pasaba como éxito y la verificación lo degradaba a un críptico «el vencimiento no cambió», que el comprador reintentaba para volver a chocar con el cooldown). Si el rechazo llegó **sin ejecutar nada** (`months_added: 0`, `attempts: 0`: el lock de cooldown bloqueó antes de tocar el panel), la orden **rota su clave de idempotencia** (`mp-<id>` → `mp-<id>-r2` → … → `-r4`, contador `renewal_key_attempts` de `db/mp-renewal-attempts-schema.sql`, tope 4): la respuesta del panel quedó cacheada bajo la clave vieja —incluido el rechazo—, así que repetirla re-obtendría el «bloqueado» para siempre y la orden quedaría atrapada en `renewal_failed`; rotar solo cuando la compra real nunca usó la clave anterior no puede duplicar meses. Superado el tope, la orden pide revisión del administrador en lugar de quemar claves infinitas. Las claves de los meses bonus (`…-b1`, `-b2`) **nunca rotan**: un paso ya ejecutado debe re-playearse, no duplicarse con clave nueva.
- **Orden `paid` varada** (un crash o deploy cortó el proceso entre el cobro y la renovación): pasados 10 min la conciliación reintenta la renovación al consultarse, y `POST /api/mercadopago/orders/[id]/retry` (solo admin) la recupera a demanda. Nunca vuelve a cobrar: re-ejecuta la renovación con la misma clave determinista.
- **Firma del webhook**: con `MERCADOPAGO_WEBHOOK_SECRET` en `.env` se valida el header `x-signature` (HMAC-SHA256 del manifest `id:<pago>;request-id:<x-request-id>;ts:<ts>;`) y una notificación sin firma válida responde 401 sin consumir la API de MP. Sin secret la validación se omite (la integridad queda garantizada por la verificación contra la API de MP); conviene configurar el mismo secret como webhook en el panel de desarrolladores de MP.
- **Pago ajeno o monto alterado**: se descarta si `external_reference`, monto o moneda no coinciden con la orden (queda registrado en el log).
- **Pagos no aprobados**: solo sellan (`rejected`/`cancelled`) una orden `pending`; nunca degradan una orden pagada, en renovación o renovada.
- **Idempotencia en curso**: MP reenvía sus notificaciones (*at-least-once*); si un segundo intento de renovación golpea al panel mientras el primero sigue procesando, el panel responde *"Idempotency-Key está en curso. No se ejecuta una segunda compra."* Ese caso **no** se marca `renewal_failed`: se registra como `in_progress` y el intento original es quien sella el resultado (`renewed` o el fallo real). Sin esta distinción el comprador vería un falso «la renovación falló» corregido segundos después (así ocurrió en la orden `4d19d5cb…` antes del fix). Si el intento en curso muere sin respuesta, la conciliación de `paid` varado reintenta a los 10 min.
- **Éxito verificado (anti-falso-positivo)**: la orden solo pasa a `renewed` si el vencimiento de la licencia en el panel **cambió** respecto a la línea base congelada en `renewal_baseline_expires_at`; el 200 del panel por sí solo ya no basta (respondía éxito sin aplicar la renovación). La línea base se lee en el primer intento y se persiste para que los reintentos comparen contra el original aunque un intento anterior ya hubiera movido el vencimiento; si el panel no reporta vencimiento legible, la renovación no se ejecuta y la orden queda `renewal_failed` (`renewal_unverifiable`) lista para el reintento idempotente. El vencimiento nuevo que la verificación leyó queda en `renewal_verified_expires_at` y **todas las confirmaciones de éxito lo muestran** («nuevo vencimiento: 8 ene 2027»): el toast de cupón y su reintento, el aviso y toast de retorno del checkout de MP, y el toast de aprobación de transferencia del admin — el comprador ve la fecha real del panel, no solo un «éxito».

### Reembolsos

Devolución **total** del cobro vía la API de pagos de Mercado Pago (`POST /v1/payments/{payment_id}/refunds` con body vacío; la integración es Checkout Pro + Payments API, así que el identificador correcto es `payment_id`, no un `order_id` de la Orders API). **Política: solo se reembolsa una orden `renewal_failed` de Mercado Pago con cobro confirmado cuya renovación NO se consumió** — jamás una orden `renewed` (la API de FlujoTV no tiene reversa de licencia, así que renovado + reembolsado sería una licencia gratis). La acción es **manual y solo admin**, desde la sección **Reembolsos** de `/clientes` (junto a la revisión de transferencias, `src/components/entities/refunds-review.tsx`); no hay reembolso automático: la conciliación reintenta la renovación sola y el admin decide entre reintentar o devolver el dinero.

- **Reclamo atómico**: `renewal_failed → refunding` en un solo `UPDATE … WHERE status = 'renewal_failed'`. `refunding` bloquea reintentos de renovación (webhook, conciliación y endpoint `/retry` lo excluyen; los `UPDATE` de `attemptOrderRenewal` llevan guard de estado) y los dobles clic (el segundo reclamo no encuentra fila → 409). Sin este estado, una renovación exitosa tras devolver el dinero sería una licencia gratis.
- **Dos fases en `refundOrder`**: la llamada a MP es la única clasificable — rechazo explícito (4xx: sin saldo disponible en la cuenta vendedora, fuera de la ventana de **180 días** desde la aprobación, etc.) revierte a `renewal_failed` conservando el error original y el motivo viaja traducido al admin; timeout/red/5xx deja la orden en `refunding` (resultado desconocido). Tras una respuesta exitosa de MP, un fallo de base de datos **nunca** revierte: la orden queda `refunding` y la conciliación la cierra como `refunded`.
- **Conciliación de `refunding` estancadas** (> 90 s; un crash o deploy cortó el proceso): `GET /v1/payments/{id}/refunds` decide — devolución registrada por el total → `refunded` con su fila de auditoría (idempotente por `mp_refund_id`); sin ningún reembolso vigente (ninguno registrado o todos `rejected`) → `renewal_failed` para reintentar. Corre *fire-and-forget* (lote de 3, fuera del camino de la petición): el listado responde de inmediato y el evento realtime `mp_order` recarga la sección al cerrar cada conciliación.
- **Auditoría**: cada devolución se registra en `mp_refunds` (`db/mp-refunds-schema.sql`, aplicada con `node db/apply-mp-refunds.mjs`, en la cadena de despliegue de AGENTS.md): orden, `payment_id`, monto, `mp_refund_id` (único), estado que devolvió MP, nota opcional del admin (máx. 500 caracteres en el diálogo de confirmación) y autor. La migración **vuelve a crear** el CHECK `mp_orders_status_check` y su lista incluye `applied` —el estado final de las órdenes de abono de saldo, definido por `db/saldo-schema.sql`—: ambas migraciones declaran la misma restricción, así que el orden de la cadena da igual; sin `applied`, re-aplicar esta migración tras existir abonos reales falla la validación del CHECK (filas `applied` ya insertadas) y aborta la cadena entera de despliegue.
- **UI**: la sección lista `renewal_failed` (botón destructivo *Reembolsar* con confirmación), `refunding` (*En curso*) y `refunded` (*Reembolsada*, solo lectura, últimas 20 por `updated_at`). Cada fila muestra el motivo del fallo de renovación y el `payment_id`; una orden con más de 180 días lleva el aviso *Fuera de ventana* (MP rechazaría la devolución). El dinero vuelve a la cuenta de Mercado Pago del pagador (en tarjeta puede tardar días en reflejarse); exige saldo disponible en la cuenta vendedora.
- **API** (envoltorio `{ ok, data, error }` con `mpErrorResponse`; solo admin): `GET /api/reembolsos/orders` y `POST /api/reembolsos/orders/[id]/refund` (`{ reason? }` → `{ order }`). Fuera de alcance: reembolsos parciales (el esquema ya guarda `amount` por si llegan), transferencias (se rechazan antes de mover dinero) y cupones (no cobran).

### Cupón y transferencia

Además de Mercado Pago, el sheet de compra ofrece **transferencia bancaria** (flujo de **dos pasos**: primero el **concepto de pago** de 4 caracteres —ver [Concepto de pago de la transferencia](#concepto-de-pago-de-la-transferencia-paso-1)— y después el ticket adjunto, con **revisión automática del comprobante** —ver abajo—; sin escaneo configurado queda `pending` hasta que el admin aprueba o rechaza en `/clientes`) y **cupón** (`POST /api/cupones/orders`): el código QA `0000` —el único activo para `/clientes`, sin catálogo ni vigencia— vale como pago: la orden nace `paid` y la renovación corre al instante con la misma clave determinista `mp-<orderId>`, **verificando el cambio de vencimiento como en los demás métodos** (la respuesta incluye el `error` guardado en la orden cuando la renovación no se confirma —la UI de /clientes lo muestra junto al botón *Reintentar renovación*— y el `verified_expires_at` verificado en el panel cuando sí se aplicó). El método está apagado por omisión: solo con `COUPON_QA_ENABLED=1` en el servidor se acepta el canje, y es idempotente por el `request_id` que genera el cliente (`mp_orders.coupon_request_id`, índice único parcial: un reintento con el mismo id devuelve la orden original en vez de sumar otro mes). Para los paquetes del módulo *Paquetes FlujoTV* existe además el cupón **asignado** `1010`, que no depende de `COUPON_QA_ENABLED` pero comparte estos mismos topes por comprador; ver [Paquetes FlujoTV](#paquetes-flujotv).

Para que un código de prueba no sea una fuente ilimitada de renovaciones gratis, el canje pasa por **dos topes por comprador**, ambos de ventana rodante sobre `mp_orders` (`method = 'cupon'`): **diario** (24 h, default `COUPON_QA_DAILY_LIMIT=3`, error `429 coupon_limit`) y **mensual acumulado** (30 días, default `COUPON_QA_MONTHLY_LIMIT=10`, error `429 coupon_monthly_limit`). Cada uno admite **override por usuario** (`users.coupon_daily_limit` / `users.coupon_monthly_limit`, `db/coupon-limit-schema.sql` y `db/coupon-monthly-limit-schema.sql`): el admin lo ajusta desde `/users` con el icono de permisos (ver [Convenciones de UI](#convenciones-de-ui)); vacío = manda el valor global del servidor, y los `apply-*.mjs` de ambos están en la cadena de despliegue de AGENTS.md.

### Concepto de pago de la transferencia (paso 1)

El método **Transferencia** es un flujo de **dos pasos**: antes de pagar, el comprador recibe un **concepto de pago** — código de **4 caracteres alfanuméricos** (alfabeto de 32 símbolos sin ambiguos: sin `0/1/O/I`, 32⁴ ≈ 1M de códigos por mes) que escribe **solo él** como concepto de su transferencia — y solo después sube el comprobante, que el escaneo valida contra ese código. El código está ligado internamente a la tupla (cuenta del comprador, usuario de FlujoTV que se renueva, mes de vigencia `YYYY-MM`), así que el concepto impreso identifica el movimiento sin necesidad de escribir el usuario.

- **Emisión idempotente**: `POST /api/transferencias/concepto` (`{ user_name }` → `{ code, month }`, sesión requerida) devuelve el código **activo** de la tupla comprador+usuario+mes; si el comprador canceló y vuelve a elegir Transferencia en el mismo mes, recibe el **mismo** código (queda latente). Módulo en `src/server/transferencias/concepto.ts` (`getOrCreateTransferConcept`); sin lectura del panel de licencias (la guarda de alcance ya ocurre al crear la orden).
- **TTL mensual**: los códigos viven dentro de su `period_month` (hora del servidor, la misma base que la verificación de fecha del comprobante); al vencer el mes ya no se entregan ni se aceptan, y se emite uno nuevo.
- **Anulación**: cuando la orden que usa el código termina —aprobada (`paid`) o rechazada (`rejected`), vía escaneo automático o revisión del admin— el código pasa a `consumed` (`consumeTransferConceptByOrder`, llamado desde `approveTransferOrder`/`rejectTransferOrder` con la orden que lo consumió en `consumed_by_order_id`): cada transacción del mes queda trazada con su propio concepto y la siguiente recibe uno distinto. Mientras la orden siga `pending` (p. ej. un comprobante rechazado por el escaneo), el código sigue activo y sirve para reintentos.
- **Unicidad**: dos índices únicos parciales garantizan en base — un solo código activo por comprador+usuario+mes (el botón es idempotente incluso en carrera: ante `23505` se relee el ganador) y códigos activos **únicos globalmente en el mes** (el concepto identifica la transacción sin ambigüedad entre compradores).
- **Puerta en la orden**: `POST /api/transferencias/orders` exige el campo `concepto` y lo resuelve con `getActiveTransferConcept` (activo, del mes, del comprador y del usuario correcto); un código ajeno, vencido o ya anulado responde `422 concepto_invalido` y la orden no se crea. El código queda en la orden (`mp_orders.concept_id`/`concept_code`) y el admin lo ve como badge en «Transferencias por revisar» para cruzarlo contra el estado de cuenta.
- **Topes de emisión**: 12 emisiones/min por comprador (bucket en memoria, `429 concepto_rate_limited`) y máximo **50 conceptos activos** por comprador y mes (`422 concepto_limit`): una cuenta que supera el tope está acuñando, no comprando (los consumidos no cuentan).
- **UI** (`clientes-accordion.tsx`): paso 1 — datos bancarios + el código en grande (copiable) con el badge «Vigente · mes», y el botón *Ya hice la transferencia* abre el paso 2 (*Subir comprobante*, con recordatorio del código y regreso a *Ver datos de pago*). Ante `concepto_invalido` (código anulado en el servidor o mes vencido con el sheet abierto) se descarta el código y el paso 1 re-consulta el vigente al instante; al cerrar el sheet la sesión de transferencia se descarta por completo.
- **Por qué basta el código**: usar el código de otro es imposible (la orden lo valida contra la tupla del comprador) y la coincidencia accidental es despreciable — códigos activos únicos en el mes (~1M de combinaciones), comprobantes privados, e importe/fecha/beneficiario/dedup sha256 siguen aplicando; cualquier fallo degrada a revisión manual, nunca a una renovación equivocada.

### Revisión automática del comprobante (transferencia)

Al enviar el comprobante en el método **Transferencia**, `POST /api/transferencias/orders` guarda el ticket, crea la orden y la revisa con el modelo de visión `RECEIPT_SCAN_MODEL` (AI Gateway, mismo transporte que el análisis de tickets; módulo `src/server/transferencias/scan.ts`, veredicto en el dominio puro `verificar.ts`). El modelo **solo extrae** lo impreso (fecha, hora, concepto, importe, beneficiario —el prompt lo instruye para tomar el nombre de quien **recibe** aunque el comprobante no diga «beneficiario», distinguiendo origen/destino cuando hay dos nombres, y transcribiendo iniciales tal cual («E. Ortiz») sin completarlas—); las condiciones se evalúan **en código** contra los datos reales de la orden, así el veredicto es reproducible y auditable sin re-consultar al modelo:

| Condición | Regla | Rigor |
|---|---|---|
| Fecha | dentro del mes actual (año y mes; la hora es informativa) | **estricta** |
| Concepto | menciona el **código de pago de 4 caracteres** entregado al comprador en el paso 1 (ver [Concepto de pago de la transferencia](#concepto-de-pago-de-la-transferencia-paso-1)), sin mayúsculas/acentos/espacios («pvne», «Pago PVNE» pasan; otro código no). El comprador escribe **solo el código**: la orden ya lo liga internamente al usuario renovado | **estricta** |
| Importe | ≥ al importe congelado de la orden (tolerancia de 1 ¢ por redondeo bancario; sobre-pago pasa, faltante no) | **estricta** |
| Beneficiario | **tolerante**: cada palabra del titular (`TRANSFER_HOLDER`) aparece completa en el nombre impreso («ENRIQUE ORTIZ», «Enrique Ortiz Santos», «ORTIZ, ENRIQUE», «Destino: Enrique Ortiz») o como inicial suelta («E. Ortiz», «Enrique O»); sin beneficiario legible no bloquea | tolerante |

Resultados:

- **Todo pasa** → `scan_status = 'approved'`, la orden pasa a `paid` y la renovación se lanza desacoplada con la misma clave determinista `mp-<orderId>` (con la verificación anti-falso-positivo de vencimiento incluida). La respuesta del POST trae `review: "auto_approved"`.
- **Alguna condición falla** (o el comprobante ni siquiera parece una transferencia legible) → `scan_status = 'rejected'`, la orden queda `pending` para la revisión manual del admin y la respuesta trae `review: "auto_rejected"` con los motivos: el comprador ve el aviso de contactar al administrador y puede subir otro comprobante. Además, la **campana de cada administrador** recibe la copia del rechazo con los motivos en versión revisión — cada condición fallida con su detalle (esperado vs leído) — para que la orden pendiente no dependa de abrir el listado (ver [Notificaciones de renovación](#notificaciones-de-renovación)).
- **El escaneo no puede ejecutarse** (sin `RECEIPT_SCAN_MODEL`/`AI_GATEWAY_API_KEY`/`TRANSFER_HOLDER`, cupón de escaneos del comprador agotado, modelo caído, timeout o salida rota) → `review: "manual"` con revisión admin como siempre: **jamás se rechaza un pago por un fallo de infraestructura**.

Redes de seguridad:

- **Dedup por huella** (`mp_orders.ticket_sha256`, sha256 de los bytes, índice `(buyer_user_id, ticket_sha256)`): el mismo comprobante re-subido por el mismo comprador nunca auto-aprueba otra orden — va a revisión manual con el motivo «Este comprobante ya fue registrado en otra orden de tu cuenta». La huella se registra en todas las rutas del escaneo (error, rechazado y aprobado), así que reintentar con el mismo archivo —incluso uno que el admin rechazó— nunca renueva solo.
- **Tope de escaneos**: 3/min por comprador (bucket en memoria, mismo patrón que el escaneo de tickets); agotado → la orden va a revisión manual sin error para el comprador (`transfer_scan_rate_limited` en el log).
- **Presupuesto de respuesta**: timeout del escaneo de 25 s (más el guard de alcance del distribuidor, cabe en los ~100 s de Cloudflare); un timeout degrada a revisión manual, nunca a rechazo. Si la persistencia del resultado falla, la aprobación automática se degrada a revisión manual: no se autoriza un pago sin evidencia guardada.
- **Trazabilidad**: datos extraídos, condiciones evaluadas (con lo esperado y lo leído), motivos, modelo y fecha quedan en `mp_orders.scan_status/scan_result/scan_model/scan_at` (`db/transfer-receipt-scan-schema.sql` + `db/apply-transfer-receipt-scan.mjs`, en la cadena obligatoria de AGENTS.md), y el admin los ve en «Transferencias por revisar» con el badge del veredicto (*Comprobante verificado* / *No autorizado por escaneo* / *Escaneo falló*) y los motivos debajo de la fila.

**Bloqueo de la app por etapas hasta el 100%**: al enviar el comprobante la app queda bloqueada con un overlay no descartable de tres etapas (timeline vertical ReUI `c-timeline-3`: **Comprobante → Renovación → Resultado**). Etapa 1 cubre el escaneo; si el veredicto es aprobado, la etapa 2 sondea `GET /api/mercadopago/orders/{id}` cada 3 s —la lectura además concilia órdenes `paid` varadas (reintento a los 10 min)—, muestra «sigue en proceso» si el panel tarda más de 90 s y termina en un panel final: **«Renovación exitosa»** con el vencimiento nuevo verificado en el panel, o **«La renovación falló»** con el aviso de contactar al administrador para el reintento manual. Solo el botón de ese panel final libera la app. El bloqueo se restaura desde `localStorage` si el comprador recarga o vuelve más tarde: el sondeo lo conduce al mismo resultado final aunque el proceso haya terminado fuera de la pestaña. Un comprobante no autorizado o una revisión manual liberan al instante (la orden queda `pending` para el admin, como siempre).

### Credenciales y prueba

- `MERCADOPAGO_ACCESS_TOKEN` en `.env` (producción `APP_USR-…`, pruebas `TEST-…`). **Cuidado**: los *usuarios de prueba* creados desde el panel de desarrolladores tienen sus propias credenciales `APP_USR-…`, y no son las credenciales de producción de la cuenta real — un token de usuario de prueba rechaza pagos de cuentas reales con *"Una de las partes con la que intentas hacer el pago es de prueba"*. Verificar el token con `GET https://api.mercadopago.com/users/me`: el `nickname` no debe empezar por `TESTUSER`.
- En producción MP **bloquea el autopago**: la cuenta del token no puede pagar sus propias preferencias (comprador y vendedor deben ser cuentas distintas). Para validar el flujo completo sin dinero real, usar el token `TEST-…` (credenciales de prueba de la aplicación) con un comprador también de prueba; las notificaciones webhook de pagos de prueba llegan igual a la `notification_url`.
- El precio vive en `LICENSE_PRICE_MXN` (MXN por mes; neto que debe depositarse) y la URL pública en `SITE_URL` (base de `back_urls` y `notification_url`). El importe congelado al crear la orden depende del método: con **Mercado Pago** es el total **engrosado** (`mpTotalMxn(precio × meses)`, ver [Selección de método y desglose del cargo](#selección-de-método-y-desglose-del-cargo-sheet)); con **transferencia** y **cupón** es el precio neto (`precio × meses`). Ambas variables se leen en cada request: cambiarlas solo exige `pm2 reload distribuidor-tvbox`.

### Notificaciones de renovación

Cada resultado de renovación deja una **notificación persistente para el comprador** (`mp_orders.buyer_user_id`): así el usuario que pagó —en `/clientes` o en los paquetes— consulta en cualquier momento qué pasó, sin depender del aviso del navegador que hizo la compra. El feed vive en la tabla `notifications` (`db/notifications-schema.sql` + `db/apply-notifications.mjs`, idempotente y en la cadena obligatoria de AGENTS.md) y la campana de la cabecera (`AppNotifications` en `src/components/dashboard/app-notifications.tsx`, adaptada del patrón ReUI `c-dropdown-menu-11`) la muestra con insignia de no leídas.

- **Un solo punto de generación**: todas las renovaciones terminan en `attemptOrderRenewal` (`src/server/mercadopago/service.ts`) —webhook de MP, transferencia aprobada, cupón, reintento admin, conciliación de `paid` varadas— y ahí se crean los avisos; `rejectTransferOrder` añade el aviso de **transferencia rechazada**. La creación es *best effort* (`void` + catch interno): un fallo de notificación se registra y **jamás bloquea ni revierte** la renovación que la originó.
- **Contenido por resultado**: `renewal_success` → *«Renovación exitosa»* con los meses aplicados (+ los meses gratis del paquete) y el **vencimiento nuevo verificado** (`renewal_verified_expires_at`, formateado por la UI con `formatFlujoDate`); `renewal_failed` → *«Renovación fallida»* con el motivo (recortado a 200 caracteres) y la sugerencia de reintentar desde Clientes; `transfer_rejected` → *«Transferencia rechazada»* con el motivo del admin. Cada fila muestra además el usuario FlujoTV renovado (tile de iniciales) y el tiempo relativo de creación. Con `months = 0` (abonos de [Abonar saldo](#abonar-saldo)) los mismos kinds traen *«Abono aplicado»* / *«Abono no acreditado»* con el monto, sin motivo técnico para el comprador.
- **Anti-duplicación**: el éxito notifica solo cuando el claim atómico de la orden ganó (`WHERE status IN ('paid','renewal_failed')` con `rowCount > 0`; un reintento sobre una orden ya `renewed` no notifica) y el fallo solo en el **primer** fallo (la orden venía de `paid`; los reintentos que re-fallan sobre `renewal_failed` no repiten el aviso). Como los intentos solapados (webhooks *at-least-once*, reintento + conciliación en vuelo) pueden atravesar ese guard por carrera, el INSERT lleva `ON CONFLICT DO NOTHING` contra el **índice único parcial** `notifications_user_order_failed_idx (user_id, order_id) WHERE order_id IS NOT NULL AND kind IN ('renewal_failed','transfer_rejected')`: una sola notificación de fallo o rechazo por orden y destinatario —comprador o admin—, garantizado en base (los re-escaneos de la misma orden tampoco apilan copias al admin). Solo se publica el evento realtime cuando la fila realmente se insertó.
- **Copia al admin en rechazos automáticos**: cuando el escaneo del comprobante rechaza (`transfer_rejected`), además del aviso al comprador se inserta una copia en la cuenta de **cada admin** (`createAdminTransferRejectedNotification`, invocada desde `src/server/transferencias/scan.ts`): la campana del admin anuncia la orden pendiente de «Transferencias por revisar» sin depender de abrir el listado. Los motivos viajan en **versión revisión** — cada condición fallida con su detalle (esperado vs leído, p. ej. «Concepto (esperado el usuario tv3abcd; el comprobante menciona tv3xyz)») y los motivos sin check asociado (comprobante ilegible, duplicado) tal cual; el comprador sigue viendo los motivos planos. Mismo contrato *best effort*: un fallo de la copia se registra y jamás bloquea el flujo de escaneo.
- **Tiempo real y frescura**: cada inserción difunde el evento SSE `notifications` (`src/server/realtime/bus.ts`), filtrado en `inScope` **antes** del atajo de admin: solo recibe el evento el comprador destinatario (`distribuidorId === scope.userId`), ni un admin los ajenos. La campana refresca feed e insignia al vuelo vía `useRealtimeEvent`, y además refresca siempre al abrir el menú (cubre SSE caído o pestaña oculta).
- **Acciones estándar**: clic en una fila la marca leída; *Marcar leídas* marca todas; el icono de papelera por fila borra una; el papelera del encabezado borra **todas** con confirmación en `AlertDialog`. El servidor devuelve el contador `unread` restante para actualizar la insignia sin refetch.
- **Requisito Base UI del menú**: en este proyecto `DropdownMenuLabel` envuelve a `Menu.GroupLabel` de Base UI, que **exige** un `Menu.Group` (`DropdownMenuGroup`) ancestro — sin él, abrir el menú lanza el error #31 (`MenuGroupContext is missing`) y crashea la app. La campana mantiene etiqueta + separador dentro de su propio `DropdownMenuGroup` (igual que el patrón ReUI `c-dropdown-menu-11` del que se adaptó y que los usos de data-grid); cualquier edición futura del `DropdownMenuContent` debe conservar ese grupo.
- **API acotada al comprador** (envoltorio `{ ok, data }`, sesión requerida): `GET /api/notificaciones` (últimas 30 + `unread`), `POST /api/notificaciones/leer` y `DELETE /api/notificaciones`. Ambas acciones aceptan `{ ids: uuid[] }` (lote de 1-200 UUID validados) o sin `ids` para aplicar a todas; **un array inválido o sobredimensionado responde 422 y nunca se interpreta como «todas»** — un payload malformado no puede vaciar el feed por accidente.

## Paquetes FlujoTV

Módulo en `/modulos/paquetes-flujotv` (herramienta *Paquetes FlujoTV* del hub de Módulos, `PackageIcon`): venta de renovaciones **en paquete** con la misma estructura de la compra de licencias individuales de `/clientes` — listado de clientes con búsqueda y carrito por fila, bottom sheet (Drawer) con selector de paquete y método de pago, aviso de retorno del checkout con sondeo, y lectura en vivo del panel para refrescar la fila tras renovar. Catálogo en `src/lib/paquetes.ts` (compartido por cliente y servidor), UI en `src/components/herramientas/paquetes/` (`paquetes-view.tsx` + cliente de API `paquetes-api.ts`), rutas `src/app/api/paquetes/` y página en `src/app/(dashboard)/modulos/paquetes-flujotv/page.tsx`. Las órdenes viven en la misma tabla `mp_orders` con una columna nueva: `bonus_months` (`db/paquetes-schema.sql` + `node db/apply-paquetes.mjs`, idempotente y en la cadena obligatoria de [AGENTS.md](AGENTS.md)).

### Paquetes y precio

| Paquete | Se paga | Se renueva | Precio (congelado en la orden) |
|---|---|---|---|
| 3 meses | 3 meses | 3 meses | `LICENSE_PRICE_MXN` × 3 |
| 6 meses | 6 meses | **7 meses** (1 gratis) | `LICENSE_PRICE_MXN` × 6 |
| 12 meses | 12 meses | **14 meses** (2 gratis) | `LICENSE_PRICE_MXN` × 12 |

Los meses gratis **no cobran**: la orden congela el importe de los meses pagados y la renovación aplica el total (`months + bonus_months`). Con perfil distribuidor el alcance es el mismo que en `/clientes` (solo puede comprar para clientes de su reseller ligado), el listado llega ya filtrado del servidor y el retorno del checkout vuelve al módulo (`/modulos/paquetes-flujotv?orden=…&estado=…`). Con **Mercado Pago** el importe congelado —y el que muestran las filas y el total del sheet, con la leyenda «Incluye $X de procesamiento»— es el total engrosado con la misma fórmula de `/clientes` (`mpTotalMxn`, ver [Selección de método y desglose del cargo](#selección-de-método-y-desglose-del-cargo-sheet)); con transferencia y cupón queda el precio neto de la tabla.

### Renovación por plan (meses gratis idempotentes)

`attemptOrderRenewal` —el núcleo compartido por el webhook de MP, la aprobación de transferencias, el reintento admin, la conciliación y el canje de cupón— ejecuta la renovación de una orden de paquete como un **plan de pasos secuenciales** contra la API del panel (que acepta `months` de 1, 3, 6 o 12):

- Paso base: los meses pagados con la clave determinista `mp-<orderId>` (idéntica a las órdenes individuales).
- Un paso extra de **1 mes por cada mes gratis**, con claves derivadas `mp-<orderId>-b1`, `mp-<orderId>-b2`.

Cada paso es idempotente por separado, así que un corte a mitad del plan (crash, deploy, respuesta perdida del panel) se recobra re-ejecutándolo: los pasos ya aplicados devuelven su renovación original (el panel responde con la misma renovación para la misma clave) y solo los pendientes se ejecutan de verdad. La verificación anti-falso-positivo (`renewal_baseline_expires_at` + relectura del vencimiento) sigue cubriendo el plan completo: la orden solo pasa a `renewed` si el vencimiento del panel **cambió** respecto a la línea base original, y el vencimiento verificado queda en `renewal_verified_expires_at` para las confirmaciones de éxito. Transferencias de paquete se revisan en la misma sección admin de `/clientes` (ahora muestran «6 meses + 1 gratis») y al aprobarlas aplica el paquete completo.

### Métodos de pago

- **Mercado Pago**: `POST /api/paquetes/mercadopago` crea la orden con el importe del paquete y la preferencia Checkout Pro idéntica a la individual (título «Paquete N meses + N meses gratis FlujoTV — usuario», `returnPath` del módulo). El webhook verifica el pago y ejecuta el plan del paquete; el retorno sondea `GET /api/mercadopago/orders/{id}` como en `/clientes` y los avisos muestran el paquete completo con el vencimiento verificado.
- **Transferencia**: `POST /api/paquetes/transferencias` (mismo ticket de comprobante y validaciones); queda `pending` hasta que el admin la apruebe en la revisión de `/clientes`, donde la renovación aplica el paquete completo con sus meses gratis.
- **Cupón asignado `1010`**: la forma de pago *Cupón* del módulo **no pide código** — el sistema lo asigna (constante isomórfica `PAQUETE_COUPON_CODE` en `src/lib/paquetes.ts`, importada por el servidor y la UI) y vale para cualquiera de los tres paquetes; el servidor lo valida en `POST /api/paquetes/cupones` (cualquier otro código → `422 invalid_coupon`). No depende de `COUPON_QA_ENABLED` (el módulo lo ofrece siempre) pero **comparte los topes por comprador** del resto de cupones (diario y mensual, con sus overrides desde `/users`), y el conteo + el INSERT corren en una transacción con advisory lock por comprador (`pg_advisory_xact_lock`) para que dos canjes concurrentes no salten el tope.

### Canje de paquete sin colgar la respuesta

El plan de un paquete (línea base + hasta 3 renovaciones + verificación de vencimiento) excede de largo la paciencia de Cloudflare (~100 s) cuando el panel está lento: sostener la respuesta la perdería **siempre** en el caso típico. Por eso el canje de paquete es **asíncrono por diseño**: `POST /api/paquetes/cupones` valida el cupón, crea la orden `paid` (con la verificación de topes ya hecha), responde al instante con status `pending` y dispara la renovación desacoplada en el servidor. La UI sondea `GET /api/mercadopago/orders/{id}` hasta el resultado: `renewed` cierra con el éxito (paquete y vencimiento verificados leídos de la orden, nunca de la selección en pantalla), `renewal_failed` activa el botón *Reintentar renovación* (idempotente por la clave determinista) y, si la ventana de sondeo se agota, el mensaje informa y volver a pulsar *Aplicar cupón* consulta la misma orden (mismo `request_id`) sin canjar ni sumar meses extra. La conciliación de órdenes `paid` varadas (10 min) recupera una renovación cortada a mitad del plan aunque se cierre el navegador. Los canjes individuales (`0000` en `/clientes`, 1 mes) siguen sincrónicos: caben en el presupuesto y su flujo no cambió.

## Abonar saldo

Módulo `/modulos/abonar-saldo` (herramienta *Abonar saldo* del hub de Módulos, `PiggyBankIcon`): el **mismo motor de pagos** de las renovaciones con **tres métodos** —Mercado Pago, transferencia bancaria y cupón QA— pero con dos diferencias: el comprador **define el monto y el tipo de saldo** y el pago se acredita como **saldo en su propia cuenta del panel**, no como renovación de una licencia. Alcance de esta entrega: **solo acumular** — el módulo registra abonos y muestra el saldo; el gasto con saldo queda para una entrega posterior. Página en `src/app/(dashboard)/modulos/abonar-saldo/page.tsx` (server component que lee el snapshot de saldos y movimientos), UI en `src/components/herramientas/saldo/` (`abonar-saldo-view.tsx` + cliente de API `saldo-api.ts`), rutas `src/app/api/saldo/` y módulos servidor en `src/server/saldo/service.ts` + `src/server/mercadopago/saldo-orders.ts`.

### Dos tipos de saldo

La cuenta mantiene **dos billeteras** (`db/saldo-tipos-schema.sql` + `node db/apply-saldo-tipos.mjs`, idempotente y en la cadena obligatoria de AGENTS.md):

- **Saldo en tokens** (`users.saldo_tokens`): para pagar el uso de **herramientas que consumen APIs externas** (fal.ai, OpenRouter, etc.). Empieza en 0 para todas las cuentas.
- **Saldo en cupones** (`users.saldo_cupones`): para la **compra de licencias de FlujoTV**. **Es la antigua `users.saldo` renombrada**: todo el saldo que los usuarios ya tenían quedó direccionado aquí sin migración de datos.

Trazabilidad del destino: `mp_orders.saldo_tipo` guarda la billetera que acredita cada orden de abono (NULL en renovaciones y abonos legados, que se leen como cupones), y `saldo_movimientos.tipo` rotula cada movimiento con su billetera (los históricos quedaron en `cupones`); `balance_after` es el saldo **de esa billetera** tras el movimiento. El tipo vive en `src/lib/saldo.ts` (`SaldoTipo`, `parseSaldoTipo`, `SALDO_TIPO_COLUMN` — la interpolación de columna en SQL solo acepta valores validados por `parseSaldoTipo`, jamás entrada cruda). Las tres rutas de abono aceptan `tipo` (`tokens` | `cupones`): sin el campo (bundle viejo en caché) el destino es cupones, la billetera que siempre existió; un valor inválido explícito responde 422.

**Abono directo del admin** (sin checkout): desde `/users`, el menú de los tres puntos de cada fila trae la opción **Saldo**, que abre un diálogo con los saldos vigentes de la cuenta, el selector de tipo y el monto (misma validación `parseAbonoAmount` del módulo). Lo ejecuta `adjustUserSaldoAction` (`src/app/actions/users.ts`, solo admin) vía `ajustarSaldoAdmin` (`src/server/saldo/service.ts`): transacción con el mismo advisory lock por comprador que los abonos de checkout, acredita la billetera elegida al instante y registra el movimiento como `kind = 'ajuste'` con `created_by` apuntando al admin responsable.

### Cómo convive con las órdenes de renovación

- **Marca `months = 0`**: toda orden de abono vive en la misma tabla `mp_orders` con `months = 0` (las de renovación validan 1/3/6/12, así que 0 no colisiona) y `user_name` = username del comprador. El despacho del cumplimiento vive al inicio de `attemptOrderRenewal` (`src/server/mercadopago/service.ts`): con `months = 0` no toca el panel de FlujoTV — acredita el saldo de la billetera de la orden vía `applySaldoCredit` (`src/server/saldo/service.ts`). El webhook de MP, la conciliación de `paid` varado, el reintento admin (`POST /api/mercadopago/orders/[id]/retry`), la aprobación de transferencia y el reintento de cupón pasan todos por ese mismo despacho: no hay un flujo de abono paralelo que mantener.
- **Estado nuevo `applied`**: el final feliz de un abono. La transacción de acreditación **reclama la orden** atómicamente (`paid`/`renewal_failed` → `applied` con guard de estado: jamás pisa un reembolso en curso), suma el monto en la billetera destino (`saldo_cupones` o `saldo_tokens` según `saldo_tipo`; NULL legado → cupones) e inserta el movimiento con **ON CONFLICT contra el índice único parcial** `saldo_movimientos_order_uidx (order_id) WHERE order_id IS NOT NULL` — la segunda cerradura de idempotencia: aunque el claim pasara dos veces, el movimiento solo entra una y el conflicto deshace todo el crédito (la cláusula repite el predicado del índice: sin él Postgres no la infiere, y ese fue el fallo corregido del primer despliegue). Con advisory lock por comprador, créditos concurrentes se serializan; los reintentos del webhook, la conciliación a los 10 min y «Reintentar abono» son seguros por diseño.
- **Libro mayor**: `saldo_movimientos` (`db/saldo-schema.sql` + `db/saldo-tipos-schema.sql`, idempotentes y en la cadena obligatoria de AGENTS.md): `kind` (`abono` | `cargo` | `ajuste`), `tipo` (billetera del movimiento: `tokens` | `cupones`), monto, `balance_after` (el saldo de esa billetera tras el movimiento, como evidencia del momento), `note`, `created_by` (para ajustes manuales del admin) y `order_id` único. La pantalla muestra ambos saldos y los últimos 15 movimientos («Abono de saldo en tokens · 9 nov 14:05 · saldo en tokens $X · +$Y»).
- **Saldos en el menú de la cuenta**: los dos renglones del avatar de la cabecera — *Saldo en tokens* (`CoinsIcon`) y *Saldo en cupones* (`TvIcon`), montos con `formatMxn` en `tabular-nums`; orden *Perfil* → *Saldos* → divider → *Usuarios*— son `DropdownMenuItem`-enlaces a `/modulos/abonar-saldo`: un toque abre el módulo desde cualquier pantalla. Se muestran **solo a quien ve la sección Módulos** (mismo gate de permisos del hub: el shell pasa ambos saldos al menú condicionado a `visibleSections.includes("modulos")`). Los montos los sirve el layout del dashboard (`src/app/(dashboard)/layout.tsx` con `getSaldosActual(userId)` de `src/server/saldo/service.ts`: una lectura por PK en paralelo con los permisos) y se mantienen frescos con el mismo tubo de las páginas — el evento `mp_order` con estado `applied` refresca el layout vía SSE y el menú se abre siempre con los valores vigentes. Informativo: el cobro revalida el saldo en el servidor, nunca se confía en el renglón.

### Los tres métodos

La UI del módulo pide primero el **tipo de saldo** (radio-cards *Saldo en tokens* / *Saldo en cupones* con su propósito; tokens preseleccionado) y después el monto; la tarjeta superior muestra **ambos saldos** lado a lado. El checkout confirma la billetera destino en el resumen («Abono a tu saldo en tokens»), los toasts y el historial nombran la billetera de cada movimiento.

- **Mercado Pago**: el comprador ve el desglose de tres montos — *Abono a tu saldo en tokens/cupones* (el monto definido), *Costo por procesamiento* y *Total* — porque el cargo se **engrosa** con `mpTotalMxn` igual que las renovaciones: la comisión del procesador (3.49% + $4 + IVA) va aparte y el depósito neto acredita **exactamente** el monto definido. `POST /api/saldo/mercadopago` (`{ amount, tipo }`) crea la orden `pending` (importe congelado, `wallet_purchase`, retorno a `/modulos/abonar-saldo?orden=…&estado=…`) y el webhook verifica y acredita; el aviso de retorno sondea `GET /api/mercadopago/orders/{id}` hasta ver `applied`.
- **Transferencia**: mismo flujo de dos pasos de las renovaciones — **concepto de pago** de 4 caracteres ligado al comprador (aquí con su propio username) y **comprobante** con revisión automática (`RECEIPT_SCAN_MODEL`: fecha del mes, código, importe ≥ y beneficiario; sin modelo → revisión admin de siempre en «Transferencias por revisar», donde la fila se rotula *Abono de saldo en tokens/cupones* según `saldo_tipo`). `POST /api/saldo/transferencias` (multipart: `amount`, `tipo`, `concepto`, `file`). La orden acredita cuando se aprueba; el importe a transferir es el definido, sin recargo.
- **Cupón QA (`0000`)**: solo con `COUPON_QA_ENABLED=1`, con **los mismos topes por comprador** que las renovaciones (diario 24 h y mensual 30 días, con sus overrides por usuario: un canje de abono y uno de renovación comparten contador). `POST /api/saldo/cupones` (`{ amount, tipo, code, request_id }`) crea la orden ya pagada y **acredita en la misma respuesta** (la acreditación es local, sin panel externo): la respuesta trae el saldo nuevo **de la billetera elegida** y el estado final. Idempotente por `request_id`: un reintento con el mismo id devuelve la orden original (con el tipo de saldo de la primera intención) sin acreditar doble. Si la acreditación fallara, la orden queda `renewal_failed` y el botón pasa a *Reintentar abono* (mismo cumplimiento, sin nuevo canje).

### Errores al comprador

Los fallos de acreditación muestran al comprador **siempre texto genérico en español** («El abono volvió a fallar… Quedó registrada para revisión; inténtalo de nuevo en unos minutos o contacta al administrador»): el detalle técnico crudo —errores de base o de Mercado Pago llegan en inglés— queda solo en `mp_orders.error` para el administrador, y las notificaciones de campana del comprador usan el mismo criterio («Abono aplicado» / «Abono no acreditado» sin motivo técnico; los kinds de notificación se reutilizan con `months = 0` para conservar los badges del feed y la deduplicación por orden). El evento realtime `mp_order` con estado `applied` refresca el saldo y el historial en vivo en todos los dispositivos de la cuenta.

## Sincronización en tiempo real

La "versión mobile" es la misma PWA abierta en el teléfono: sin un canal push, dos dispositivos con la misma sesión mostraban datos viejos hasta recargar manualmente. Hoy toda mutación relevante difunde una **señal de invalidación** por el bus de tiempo real y el otro dispositivo refresca solo, en un par de segundos.

### Transporte: SSE + LISTEN/NOTIFY (no WebSockets)

- **Server-Sent Events** vía un Route Handler (`GET /api/realtime`, `src/app/api/realtime/route.ts`). Solo se necesita push servidor→cliente: las mutaciones ya viajan por Server Actions y API routes, así que la bidireccionalidad de un WebSocket/socket.io no se usaría y exigiría un custom server (reemplazar `next start`, tocar PM2 y el pipeline `eve build`), algo que la documentación de Next.js 16 desaconseja. SSE funciona con el despliegue actual (`next start` → PM2 → Caddy → Cloudflare) sin cambios de infraestructura y `EventSource` del navegador reconecta solo.
- **Fan-out entre procesos por Postgres**: `src/server/realtime/bus.ts` publica con `pg_notify` **dentro de la misma transacción** de cada mutación (Postgres entrega el NOTIFY solo tras el COMMIT, así que jamás se notifica una escritura revertida) y un cliente `pg` dedicado (singleton en `globalThis`, no sale del pool) hace `LISTEN realtime` y reparte a los suscriptores del proceso. Si PM2 corriera en cluster o hubiera varios procesos, el canal sigue funcionando sin estado compartido en memoria.
- **Payload mínimo**: los eventos solo llevan señales (`kind` + ids + marca de tiempo), nunca documentos ni datos de negocio. El `router.refresh()` del cliente es el que trae los datos, por los cauces ya autorizados (RSC/API).

### Eventos y alcance

El endpoint SSE autentica por la cookie de sesión y **filtra cada evento por el alcance de la conexión en el servidor** (el cliente nunca decide qué ve; un evento que llega siempre es relevante para esa sesión):

| `kind` | Lo emite | Quién lo recibe |
|---|---|---|
| `entity` | `src/server/umejson/repository.ts` (create/properties/state/delete) | admin: todo; distribuidor: su propia entidad Cuenta (`distribuidorId`) o lo ligado a su reseller (`distribuidorName`) |
| `mp_order` | `src/server/mercadopago/service.ts` (renovada, fallida, rechazada —incluye el webhook externo de MP—; también el escaneo de comprobante en `src/server/transferencias/scan.ts`) | todos (el refetch llega ya filtrado por alcance). El evento viaja con el **usuario renovado** (`userName`) y el **estado nuevo** (`status`): `/clientes` y *Paquetes FlujoTV* lo usan para refrescar **solo la fila** del cliente renovado (ver [Refresco dirigido de la fila renovada](#refresco-dirigido-de-la-fila-renovada-mp_order)) |
| `expenses` | `src/server/finanzas/gastos.ts` (alta/edición/borrado, incluidos los espejos del tarificador) | solo el propietario (incluso un admin ignora los ajenos) |
| `users` | `src/server/auth/users.ts` y `permissions.ts` (alta/edición/baja y matriz de secciones) | admin: todo; el usuario afectado recibe los que lo tocan (p. ej. permisos de navegación) |
| `prefs` | `src/server/modulos/preferences.ts` (guardado de preferencias de Módulos) | **solo el propietario**, sea cual sea el rol: ni un admin recibe los de otras cuentas |
| `notifications` | `src/server/notifications/service.ts` (resultado de una renovación para su comprador; copia del rechazo automático de una transferencia a cada admin) | **solo el destinatario de la fila** (`distribuidorId` = su `user_id`: el comprador, o cada admin en la copia de un rechazo), sea cual sea el rol; el filtro corre antes del atajo de admin |

### Cliente

- **`RealtimeProvider`** (`src/components/realtime/realtime-provider.tsx`, montado una vez en el layout del dashboard): una **sola conexión SSE por pestaña**. Al recibir eventos ejecuta `router.refresh()` **coalescido** (debounce de 300 ms) para que una ráfaga (p. ej. orden + entidad de una renovación) produzca un único refresco; con la pestaña oculta no refresca, y al volver (`visibilitychange`) refresca de una vez. Si la conexión cae, al reabrir pide un **catch-up** (el refresh cubre lo perdido durante el hueco) y la cabecera muestra el badge *Reconectando…* / *Sin conexión* (`RealtimeIndicator`, oculto mientras está en vivo).
- **`useRealtimeEvent(kinds, callback)`** (`src/hooks/use-realtime.ts`): para las vistas que se alimentan de API routes (un `router.refresh()` no refetchea sus datos). El callback recibe el mensaje completo (`kind` + ids y, en `mp_order`, el usuario renovado y su estado nuevo) para que la vista decida entre refrescar una sola fila o el listado: *Gastos* recarga lista + resumen (sin resetear paginación), *Clientes* y *Paquetes FlujoTV* refetchan el listado FlujoTV solo en los eventos `entity`, y un `mp_order` con renovación aplicada refresca **solo la fila** del renovado (ver [Refresco dirigido de la fila renovada](#refresco-dirigido-de-la-fila-renovada-mp_order)); el hub *Módulos* adopta las preferencias que llegan refrescadas.
- El propio autor del cambio también recibe el eco de su evento; el snapshot confirmado por el servidor hace que ese refresco sea un no-op.

#### Refresco dirigido de la fila renovada (`mp_order`)

Al completarse una renovación (webhook de MP, aprobación de transferencia, cupón, reintento o conciliación —todos comparten `attemptOrderRenewal`—), el evento `mp_order` sale con el **usuario renovado** (`userName`, de `mp_orders.user_name`) y el **estado nuevo** (`status`). Las pantallas de clientes (`clientes-accordion.tsx` en `/clientes` y `paquetes-view.tsx` en `/modulos/paquetes-flujotv`) **no recargan el listado** con ese evento:

- Recargarlo es lento (todo el listado del panel) y, peor, el listado viene del **snapshot cacheado** del panel: presentaría el vencimiento **viejo** pisando la fecha nueva que la fila ya mostraba — la incoherencia visual donde la notificación anunciaba el vencimiento nuevo y la lista conservaba el viejo.
- Con `status === "renewed"` la vista refresca **solo esa fila** con la lectura en vivo del panel (`GET /api/flujotv/clients/{usuario}` → `/find_user` sin caché, el mismo `refreshRow` que ya usaban los flujos de compra de la propia pestaña): barra de días, punto de estado y «vence …» quedan coherentes al instante, y el resto del listado no se toca.
- Los demás estados de la orden (`pending`, `paid` en curso, rechazos, reembolsos, guardado del escaneo del comprobante) **no mueven el vencimiento de nadie**: no tocan filas. Los eventos `entity` siguen refetchando el listado en silencio, y la sincronización real (~90 s) sigue siendo la única recarga completa deliberada (botón de recargar).

### Preferencias del hub de Módulos (`/modulos`)

Favoritos, filtros creados y asignaciones módulo→filtro viven en `user_module_prefs` (`db/module-prefs-schema.sql`, una fila por usuario con `prefs` JSONB; aplicar con `node db/apply-module-prefs.mjs`). Antes estaban en `localStorage` y cada dispositivo tenía su propio estado.

- **Lectura**: la página `/modulos` las resuelve en el servidor (`getModulePrefs`) y las pasa al acordeón como estado inicial.
- **Escritura**: cada cambio local guarda vía `saveModulePrefsAction` con **debounce de 400 ms** (el último snapshot gana, *last-write-wins*); la UI es optimista y el servidor devuelve las preferencias normalizadas, que quedan como snapshot confirmado.
- **Tiempo real**: cada guardado emite el evento `prefs` (solo-propietario); el otro dispositivo refresca la RSC y adopta el estado remoto si no tiene ediciones locales pendientes.
- **Migración**: la primera visita sin fila en el servidor sube lo que hubiera en `localStorage` (`modulos.filtros.v1`) y limpia la clave. Con estado ya en el servidor, el dato local viejo se descarta: si dos dispositivos tenían favoritos distintos, gana el que migre primero.
- La validación (`normalizeModulePrefs`) vive en `src/lib/modulos.ts` junto al catálogo de módulos, compartida por cliente (migración) y servidor (guardado): favoritos de módulos inexistentes, filtros sin nombre y asignaciones huérfanas se sueltan.

### Operación y verificación

- **Cloudflare corta respuestas idle a los ~100 s**: el endpoint envía un heartbeat (`: ping`) cada 25 s y responde con `Cache-Control: no-store, no-transform` y `X-Accel-Buffering: no` para que ni Caddy ni Cloudflare buffericen el stream. El smoke de producción confirma conexión inmediata, entrega del evento publicado por `pg_notify` y heartbeat a los ~25 s.
- **`pm2 reload`**: las conexiones SSE mueren con el proceso; `EventSource` reconecta solo y el refresh de catch-up cubre lo perdido, sin intervención.
- **Prueba manual**: `curl -N -H "Cookie: reseller_session=<token>" https://distribuidor-tvbox.people-ia.com/api/realtime` (heartbeat cada ~25 s) y, en otro dispositivo, crear un gasto o marcar un favorito: el evento `event: change` llega al stream y la otra pantalla se actualiza sola. Sin cookie responde `401`.

## Modelo de datos

Cada entidad es un documento umeJSON (`doc` JSONB) con espejos relacionales para indexado y concurrencia:

```json
{
  "id": "uuid-v7 (servidor)",
  "entityName": "Venta",
  "dynamicProperties": { "monto": 500 },
  "lifecycle": { "createdAt": "...", "updatedAt": "...", "version": 1 },
  "state": { "current": "active", "statusLog": [ ... máx. 20 ... ] },
  "markdownDocumentation": "### Venta ..."
}
```

Toda mutación es una transacción atómica: `UPDATE entities ... WHERE id = $1 AND version = $esperada` (0 filas → conflicto 409) + `INSERT` en `entity_events` con `seq = max(seq)+1`. Los tipos de evento son cerrados: `created`, `property.updated` (con diff `from`/`to`), `state.changed`, `relation.added`, `annotation.added`, `imported.from`, `correction`. `state.statusLog` es una proyección de la bitácora (se recalcula en la misma transacción). `db/create-user.mjs` respeta el mismo protocolo: al cambiar el rol de una cuenta existente aplica lock optimista y journala un `property.updated` con el diff.

## Tema y marca

- **Tema claro/oscuro**: `ThemeProvider` (next-themes, atributo `class`) montado en el layout raíz (`src/app/layout.tsx`) con `suppressHydrationWarning`; tema por defecto **Sistema**, con opción Claro / Oscuro. El selector Claro / Oscuro / Sistema vive como submenú del **menú de la cuenta** —el avatar de la cabecera— (`src/components/theme-toggle.tsx`, `DropdownMenuSub`), y la cabecera del dashboard es sticky (`sticky top-0`). Cualquier módulo presente o futuro hereda el tema automáticamente: los tokens de ambos modos ya están definidos en `globals.css` (`:root` y `.dark`) y los componentes shadcn/ReUI reaccionan solos; el Toaster (sonner) sigue el tema vía `useTheme`. Para respetar el tema, el código nuevo usa tokens semánticos (`bg-card`, `text-muted-foreground`, …) y no colores crudos; un color crudo lleva siempre su par `dark:`.
- **Marca TVBOX**: la identidad son **dos SVG en línea** (no `<img>`), cada uno con los paths del artwork original copiados dentro del componente (`assets/mascota-tvbox.svg` y `assets/texto-tvbox.svg`; los assets quedan en el repo como fuente, pero la app no los sirve: así cada trazo se puede pintar con un token del tema).
  - `src/components/mascota-logo.tsx` (`MascotaLogo`): la mascota. Cuerpo y ojos usan `fill-mascota-ink` (`#171717` en claro, `#fcfcfb` en oscuro → **blanca en tema oscuro**) y la pantalla `fill-mascota-face` (`#fcfcfb` en claro, `#171717` en oscuro). El rectángulo de fondo del artwork va en `fill-transparent`: la cabecera y el splash usan `bg-background`, así que un lienzo sólido se vería como un recuadro tapando el logo.
  - `src/components/tvbox-wordmark.tsx` (`TvboxWordmark`): el logotipo *TVBOX NETWORK*. Todos los trazos del artwork —**incluidos los contadores blancos de la B y la O**— van en **un solo `<path>` con `fill-rule="evenodd"`**: al superponerse, los contadores se recortan como huecos reales y quedan transparentes. Sin eso, al invertir los colores las letras quedarían blancas y sus huecos también, y el logotipo se perdería. El relleno es `fill-foreground`, que se invierte solo con el tema.
  - Los tokens viven en `globals.css` (`--mascota-ink` / `--mascota-face`, con su par invertido en `.dark`) y se exponen como utilidades de Tailwind (`fill-mascota-ink`, `fill-mascota-face`) desde `@theme inline`.
  - **Dónde se usan**: el splash de arranque muestra el lockup completo (mascota + wordmark); la cabecera del dashboard lleva **solo la mascota**, como enlace a Inicio (el wordmark ya no cabe en una barra de 64 px y no había dónde ponerlo sin competir con la marca).
  - **Login y registro** (`src/components/auth/auth-shell.tsx`) muestran el **wordmark** `TvboxWordmark` (`h-12`, sin texto adicional: el artwork ya incluye la marca) sobre el card, reemplazando al antiguo monograma "T" (`src/components/togu-logo.tsx`, retirado de la UI; sus assets estáticos siguen en `public/togu-icon-light.svg` y `public/togu-icon-dark.svg`). La metadata raíz (`src/app/layout.tsx`) es título *TVBOX* con descripción *Panel de administración de TVBOX*, y `/login` sobreescribe el título con *Iniciar sesión*.
- **Icono de la app**: la mascota es el icono de la app, y **todos los formatos se generan desde el artwork** con `node assets/generate-icons.mjs` (no se editan a mano): el script mide la caja real de la mascota (renderizando los paths sin el rectángulo de fondo y recortando con `sharp`), la centra en un lienzo de 512×512 y escribe:
  - `src/app/icon.svg`: el favicon. Cuadro redondeado (radio 22%) con las clases `.tile`, `.body`, `.face` y `.eye`, que **alternan claro/oscuro según el `prefers-color-scheme` del navegador** (igual que hacía el monograma anterior): en claro el cuadro es `#fcfcfb` y la mascota `#171717`; en oscuro se invierten. Sustituye al antiguo `favicon.ico`.
  - `src/app/apple-icon.png` (180×180, cuadrado sin radio porque iOS aplica su propia máscara), `public/icons/icon-192.png`, `public/icons/icon-512.png` y `public/icons/icon-maskable-512.png` (este último a sangre completa y con la mascota dentro del círculo seguro del 80%).
  - `src/app/manifest.ts`: el manifiesto PWA (nombre *Distribuidor TVBox*, `display: standalone`, `theme_color`/`background_color` `#fcfcfb` e iconos 192/512 + el de máscara). Next.js lo enlaza solo; **`manifest.webmanifest` está excluido del `matcher` de `src/proxy.ts`**, porque si no el gate de sesión lo redirigía a `/login` y el navegador recibía un 307 en vez del manifiesto.
  - El layout raíz declara `applicationName`, `appleWebApp` y un `viewport` con `themeColor` por tema (`#fcfcfb` claro / `#171717` oscuro), más `viewportFit: "cover"` (el contenido llega a los bordes y las áreas seguras se respetan con `env(safe-area-inset-*)`) e `interactiveWidget: "resizes-visual"` (el teclado virtual reduce el viewport visual sin redimensionar el layout, que es lo que permite medir el teclado con `window.visualViewport`).
- **Splash de arranque**: al cargar la app se muestra una **ventana de splash** con la marca: la mascota (`h-24`), el wordmark *TVBOX NETWORK* (`h-10`) y un `Spinner` con el rótulo *Cargando…*, sobre `bg-background` a pantalla completa (`src/components/app-splash.tsx`, montado en el layout raíz). Puntos que conviene no romper:
  - El splash **se retira cuando la ruta termina de cargar**: los `loading.tsx` marcan su estado con `data-app-loading`, y un `MutationObserver` detecta cuándo ese marcado sale del DOM (el fallback y el contenido entran en el mismo commit). Como respaldo se usa el evento `load` del navegador y un máximo de 5 s.
  - **Dura al menos 800 ms** para que no parpadee en cargas rápidas, y se desvanece en 300 ms (`transition-opacity`, curva de casa); con `prefers-reduced-motion` el desvanecido es instantáneo y la entrada del lockup (`splash-enter` en `globals.css`) no se anima.
  - El splash es **del layout raíz**, así que no reaparece al navegar dentro de la app; los `loading.tsx` (raíz y grupo `(dashboard)`) son los que cubren las navegaciones internas, sin desmontar el shell del dashboard.

## Convenciones de UI

- La interfaz usa componentes **shadcn/ui** y **ReUI** (ver `src/components/ui` y `src/components/reui`) con iconos de `lucide-react`. Los componentes instalados se usan tal como están: no se reestilizan ni se retemporizan; el theming va por tokens semánticos (`bg-primary`, `text-muted-foreground`, etc.).
- **Adjuntos**: la selección de archivos usa el hook de ReUI `@reui/use-file-upload` (`src/hooks/use-file-upload.ts`, instalado con `npx shadcn@latest add @reui/use-file-upload`) y los chips se pintan con `Badge` de `src/components/reui/badge` (`src/components/herramientas/attachment-chips.tsx`). El hook viene del registro y está **parcheado en local** (dos arreglos): un duplicado ya no aborta el resto del lote (`continue` en vez de `return`) y `onError` se dispara también en los lotes mixtos, para que un archivo rechazado nunca se descarte en silencio. Si se reinstala el componente hay que volver a aplicar esos dos cambios.
- **Pestañas**: para **todas** las pestañas de la app se usa el mismo patrón que está en `/profile` (ver [Perfil de usuario](#perfil-de-usuario)): `Tabs` + `TabsList variant="line" className="mb-3.5 w-full"` + `TabsTrigger` + `TabsContent keepMounted` de `src/components/ui/tabs` (Base UI), con paneles `keepMounted` para no perder estado al cambiar de pestaña. No se introducen otras variantes ni componentes de pestañas.
- **Bottom sheets**: los flujos de confirmación **orientados a móvil** —hoy la compra de licencias en `/clientes`— se abren como **bottom sheet** con el `Drawer` de Base UI (`src/components/ui/drawer.tsx`, instalado con `npx shadcn@latest add drawer`): panel anclado al borde inferior (`swipeDirection="down"`, el default del componente), con **asa de arrastre** (`showSwipeHandle`; el asa no se dibuja por omisión), cuerpo con la información de la operación y pie con la **acción primaria a todo el ancho** y *Cancelar* debajo vía `DrawerClose`. El contenido se acota con `max-h-[80vh]` y el cuerpo hace scroll por dentro (`no-scrollbar overflow-y-auto px-4`), la composición del ejemplo ReUI `c-drawer-1`. Se cierra deslizando, tocando fuera o con `Escape`; mientras la acción procesa, los tres caminos quedan bloqueados (`onOpenChange` ignora el cierre y los botones van disabled). Los diálogos centrados (`Dialog`/`AlertDialog`) quedan para las confirmaciones puntuales (bajas, sincronización): una decisión no destructiva con información que se lee en el teléfono es un bottom sheet, no un diálogo flotante.
- **Barra de pestañas fija**: cuando la página tiene contenido largo (la galería de Imágenes), la barra de pestañas se ancla con `sticky top-0 z-10` —el scroll vive en `<main>` del shell (ver [Contención de scroll del shell](#convenciones-de-ui)), cuyo borde superior ya es el borde inferior de la cabecera— para poder cambiar de pestaña sin volver arriba. Va **envuelta en un `div` a todo el ancho** (`-mx-4 px-4 md:-mx-6 md:px-6`) que cancela el padding de la página: sin ese sangrado, el contenido que pasa por debajo se transparentaría por los costados del padding. El fondo del envoltorio es opaco (`bg-background`) y el `mb-3.5` se mueve del `TabsList` al envoltorio, para conservar la misma separación respecto al contenido.
- **Contención de scroll del shell**: el documento **nunca scrollea**. La raíz del shell (`dashboard-shell.tsx`) va a altura fija (`h-[var(--shell-viewport-height)]` con `overflow-hidden`) y **`<main>` es el contenedor de scroll** (`min-h-0 flex-1 overflow-y-auto`, con el `padding-bottom` del espacio de la barra). Si el documento scrolleara, al hacerlo en móvil la barra del navegador se colapsa/expande y la cabecera sticky y la barra inferior fixed "juegan" durante la transición; con el scroll adentro (un contenedor interno no mueve la barra del navegador) cabecera y barra quedan clavadas. El sticky que antes se anclaba a `top-[var(--shell-header-height)]` respecto al documento (la barra de pestañas de Imágenes, en `image-studio.tsx`) ahora se ancla a `top-0` respecto a `<main>`, cuyo borde superior ya es el borde inferior de la cabecera.
- **Barra inferior fija de cinco destinos**: la app **no tiene sidebar**. La navegación vive en una barra fija al pie (`src/components/dashboard/app-bottom-nav.tsx`, `position: fixed` + `z-40`, **sin borde superior**), `max-w-2xl` centrado en escritorio, altura `var(--shell-bottom-nav-height)` = 4rem + safe area, en este orden: *Inicio*, *Módulos*, *Clientes*, *Finanzas* y *Ayuda*. **Las cinco son enlaces**: cada botón lleva a su propia página y no hay menús contextuales. El **número de columnas es dinámico** (`gridTemplateColumns` en línea): las secciones que el usuario tiene **denegadas por permisos** no se renderizan y el resto se reparte el ancho. *Módulos* no tiene pestañas: su **hub** (`/modulos`) es un acordeón de filas con filtros, favoritos y asignación por clic sostenido (ver el **Hub de módulos** en [Características](#características)) y su rótulo viaja en la cabecera. Las secciones con opciones (*Finanzas*, *Ayuda*) las muestran como **pestañas de enlaces reales** en la parte superior de su página: el riel lo dibuja `SectionTabs` dentro de `SectionTabsLayout` (un `layout.tsx` por sección), toma las entradas de `children` en `navSections` y marca la vigente con `aria-current="page"`; el botón de la barra apunta a la página de la sección —en *Finanzas* y *Ayuda* a la primera pestaña, a la que redirige su página índice. El contenido reserva abajo **exactamente el espacio de la barra** (`padding-bottom: var(--shell-bottom-nav-space)` en el `<main>`), así que la última fila de cada página nunca queda tapada. La sección activa se expone con `aria-current="page"` en el botón (`isNavSectionActive`, match `exact` para Inicio y `prefix` para el resto).
- **Estado activo de la barra**: el botón activo mantiene su icono con el contraste normal (`text-foreground`) y la **inversión vive solo en el rótulo**: una cápsula `rounded-full bg-foreground px-2 text-background` (`bottomNavClass.labelActive` en `nav-layout.ts`) —negro sobre blanco en tema claro, blanco sobre negro en oscuro—. Invertir el botón entero resultó demasiado agresivo; el pill solo cubre la zona del texto y los iconos no cambian.
- **Permisos de secciones por usuario** (`/users`, solo admin): junto al lápiz de editar, el botón **Permisos** (escudo, `ShieldCheckIcon`) abre un dialog con la **matriz de visibilidad**: una fila por sección de la barra (tile de icono + nombre + descripción + `Switch`), pie con *Cancelar*/*Guardar*; guardar está deshabilitado si se intenta dejar cero secciones y las cuentas **admin** muestran el aviso «Las cuentas admin siempre ven todas las secciones» (el permiso no las restringe). La persistencia vive en `user_section_permissions` (`db/permissions-schema.sql`, PK `(user_id, section)`, FK con `ON DELETE CASCADE`; una fila por sección con su flag `visible`, escrita en transacción vía `setSectionPermissions`); **sin filas para un usuario = acceso completo**. El layout del dashboard resuelve las claves visibles (`getVisibleSectionKeys` en `src/server/auth/permissions.ts`) y las pasa por `DashboardShell` hasta `AppBottomNav`, que filtra `navSections` por la `key` estable de cada sección. Los permisos **solo ocultan la navegación**: las rutas siguen servidas por URL directa. El mismo dialog incluye los **topes de cupón por comprador** (`db/coupon-limit-schema.sql` y `db/coupon-monthly-limit-schema.sql`): **Cupones por día** (canjes en 24 h, `users.coupon_daily_limit`) y **Cupones por mes** (acumulado en ventana rodante de 30 días, `users.coupon_monthly_limit`); vacío = valor global del servidor (`COUPON_QA_DAILY_LIMIT` default 3, `COUPON_QA_MONTHLY_LIMIT` default 10) y el canje (`createCouponOrder`) usa los efectivos vía `couponDailyLimitForBuyer` / `couponMonthlyLimitForBuyer` (`429 coupon_limit` / `429 coupon_monthly_limit`).
- **Cabecera**: barra `sticky top-0` de `4rem` + `env(safe-area-inset-top)` **sin borde inferior** (la separación con el contenido es solo de espacio), con la **mascota** a la izquierda (enlace a Inicio, `aria-label="Inicio"`), el **rótulo de la sección** a su derecha y a la derecha la **campana de notificaciones** (ver [Notificaciones de renovación](#notificaciones-de-renovación)) y el **avatar de la cuenta**. Cuando la ruta activa es más profunda que el hub de su sección (`backHref` en `nav-config.ts`), el rótulo se vuelve un **solo botón de regreso** (chevron + rótulo dentro del mismo `Button` ghost enlazado al hub, envuelto por el `<h1>`); en el hub queda como texto simple. El avatar es el único punto de entrada a *Perfil*, *Saldo en tokens* y *Saldo en cupones* (dos renglones con icono y el monto en vivo de cada billetera, solo si el usuario ve la sección Módulos, seguidos de un divider), *Usuarios* (solo `admin`), *Tema* y *Cerrar sesión* (separada del resto por un `Separator` y con `variant="destructive"`); el nombre accesible del trigger incluye la cuenta (`aria-label="Cuenta de <usuario>"`) y en móvil el trigger muestra **solo el avatar**.
- **Iconos y etiquetas del menú**: cada entrada lleva **icono + etiqueta visible**; el icono acompaña a la etiqueta, no la sustituye. Todos son de `lucide-react` y deben ser **semánticos** (que el icono despierte la misma idea que el texto), nunca decorativos: *Clientes* usa `UsersRoundIcon` (grupo de personas) y *Perfil* `CircleUserRoundIcon` (una cuenta). Si una etiqueta no tiene un icono inequívoco, se deja solo con texto antes que inventar un icono.
- **Etiquetas de la barra**: las etiquetas van en `text-xs` (12 px) y **se leen completas y en una línea incluso a 320 px** (la más larga es *Módulos*): las columnas no se estrechan ni se truncan, la etiqueta simplemente se desborda unos píxeles de su celda sin pisar a la vecina, y la página **no genera scroll horizontal** (`scrollWidth` = ancho del viewport). Ninguna etiqueta baja de `text-xs`.
- **Métricas táctiles de la barra y de los menús**: cada destino de la barra mide **48 px** de alto (`min-h-12`) con icono de **20 px** (`size-5`), y las filas del menú de la cuenta usan la escala móvil de `nav-layout.ts` (`mobileNavClass`): `min-h-12` en móvil y medidas compactas en `md:`. El resto de medidas —altura de la cabecera (`4rem` + safe area), altura de la barra (`4rem` + safe area), ancho máximo (`max-w-2xl`)— viven en **`src/components/dashboard/nav-layout.ts`** (`shellLayout`, `bottomNavClass`) y los componentes de `src/components/ui` no se reestilizan: solo se les pasa `className`.
- **Teclado virtual**: el shell (`src/components/dashboard/dashboard-shell.tsx`) observa `window.visualViewport` **solo en cliente** y se suscribe a `resize` con limpieza. Se considera que el teclado está abierto cuando el viewport visual pierde **más de 150 px** frente al layout viewport (no se infiere por foco, porque un input puede tener foco sin teclado). Con el teclado abierto la barra inferior **se retira del DOM** (sale también del orden de tabulación), el espacio inferior reservado vuelve a `0px` y el alto útil pasa a ser `visualViewport.height`; al cerrarlo todo se restaura (`100svh` y `4rem` + safe area) **sin desmontar la página**, así que no se pierden borradores ni streams en curso. El mismo token (`--shell-bottom-nav-space`) lo consume el `Toaster` del layout raíz, para que los toasts no queden bajo la barra ni bajo el teclado.
- **Alto útil de las vistas con scroll interno**: las páginas que ocupa el alto de la pantalla y conservan riel de pestañas (el chat del asistente, en Ayuda) se miden con `h-[calc(var(--shell-viewport-height)-var(--shell-header-height)-var(--shell-bottom-nav-space)-var(--shell-section-tabs-height))]`, es decir **alto útil − cabecera − barra − pestañas de sección** (el riel de pestañas mide exactamente `--shell-section-tabs-height`, `2.5rem`, definido en `globals.css`; Módulos ya no lo resta porque su sección no dibuja riel; el `-mb-px` de la lista monta el subrayado sobre el borde, así que el borde cuenta dentro del alto). La cadena `min-h-0` + `flex-1` sigue siendo la que resuelve el scroll interno: el contenedor no crece nunca más allá del viewport.
- **Fecha de la cabecera**: el indicador del margen derecho del header (`src/components/app-header-date.tsx`) pinta el día en formato corto (`Vie 23 Oct`: weekday y mes abreviados con el locale `es` de date-fns, con la inicial en mayúscula y el día sin cero a la izquierda) y abre un `Popover` con el `Calendar` de shadcn (`src/components/ui/calendar.tsx`, instalado con `npx shadcn@latest add @reui/c-calendar-24`) para consultar otras fechas. El calendario es **informativo**: elegir un día solo cambia el rótulo, no filtra nada. Puntos que conviene no romper al tocarlo: (1) el día se calcula en **Ciudad de México** — el servidor lo resuelve con `mxToday()` (`src/lib/finanzas.ts`) y el cliente lo recalcula con `Intl.DateTimeFormat` en `America/Mexico_City` cada minuto y al abrir el popover, para que tras medianoche el rótulo no quede congelado en el día anterior (el layout es un Server Component y no se vuelve a renderizar al navegar dentro de la app); (2) el `Calendar` recibe `today` explícito, para que el anillo de «hoy» coincida con la fecha del rótulo y no con el día local del dispositivo; (3) el mes visible se resincroniza con la fecha seleccionada cada vez que se abre el popover (el contenido se desmonta al cerrarse), así que navegar a otro mes y salir no deja el calendario en un mes sin día resaltado; (4) el `Calendar` se carga **bajo demanda** con `next/dynamic` (`ssr: false`), para no sumar react-day-picker al bundle inicial de todas las rutas, con un `Skeleton` del tamaño real del calendario como fallback; (5) el locale se importa desde `src/lib/date-locale.ts` (que solo reexporta `es`), porque importar el barrel `date-fns/locale` arrastra los ~70 locales del paquete. El trigger es un `Button variant="ghost"` **sin icono**, con `aria-label` (`Fecha Vie 23 Oct. Abrir calendario`): el texto por sí solo no dice que abre un calendario.
- **Selección única excluyente**: cuando un control ofrece pocas opciones excluyentes mutuas (hoy el nivel de calidad *Media* / *Alta* de Imágenes), se usa `ToggleGroup` + `ToggleGroupItem` de `src/components/ui/toggle-group` (Base UI, instalado con `npx shadcn@latest add toggle toggle-group`), **no** un `Slider`: cada opción es un botón alterno y la activa queda presionada (`aria-pressed`), lo que hace visible el estado sin depender del color y permite tabular y operar con flechas. La opción presionada se pinta con el **relleno primario** (`bg-primary` / `text-primary-foreground`), igual que el botón principal de la card: el `bg-muted` por defecto de shadcn no contrasta con la card en ninguno de los dos temas y el nivel activo no se distinguía. El grupo se nombra con `aria-labelledby` apuntando a su `Label`. Para opciones con más de dos valores o para un rango continuo se sigue usando `Slider`.
- **Filas de controles mobile first**: las filas que mezclan etiquetas, controles y acciones (como la de Imágenes) se maquetan con `grid`, no con `flex` + `items-end`: en móvil se apilan en una columna con los controles y los botones a todo el ancho, y en ≥`lg` los wrappers pasan a `lg:contents` para que cada hijo ocupe su propia celda (`col-start`/`row-start`) y las etiquetas, los controles y los botones queden alineados en filas compartidas. `flex` + `items-end` alinea por la base de la caja más alta, que descuadra etiquetas y controles cuando una columna tiene una línea extra de texto. Las acciones **secundarias** que no forman parte de la fila se renderizan aparte, bajo el control al que afectan, en lugar de apiñar la fila.
- **Lightbox de media**: cuando una imagen se muestra dentro de un diálogo y el usuario quiere verla grande, se añade un **segundo `Dialog` a pantalla completa** (`inset-0`, fondo negro, `flex` + `items-center justify-center`, sin radio ni padding) con la imagen sola, en lugar de dejar que el navegador abra su visor nativo. Se cierra tocando cualquier parte, con la X o con `Escape`, y `Escape` cierra **solo** el lightbox: el diálogo de información sigue abierto debajo y recupera el foco. La imagen se renderiza con `pointer-events-none` y el toque lo captura un `<button>` con `cursor-zoom-in`, porque en móvil el navegador abre su visor de imagen a pantalla completa si el `<img>` es el destino del toque (el mismo criterio se aplica al `<video>` del visor de animación). El diálogo de información, en su caso, usa `touch-manipulation` para que el doble toque no haga zoom de la página.
- **UUIDs**: el formato de id que se valida en el servidor es **8-4-4-4-12** (`/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`). Hay una copia local de esa expresión en cada módulo que la usa (`src/server/images/service.ts`, `src/server/storage/user-files.ts`, `src/server/animaciones/service.ts`, `src/app/api/finanzas/gastos/[id]/route.ts`, `db/sweep-attachments.mjs`, `db/ensure-user-storage.mjs`): **un grupo `{4}` de más hace que la expresión no case con ningún UUID real**, y el síntoma es un 422 o un 404 en rutas que sí manejan ids válidos. Si se edita una de ellas, hay que comprobar que acepta un UUID de muestra.

## Deployment

Este proyecto **siempre se publica en el subdominio**: https://distribuidor-tvbox.people-ia.com/ (Caddy reverse-proxy al puerto 3010).

Servidor Node con build de producción, gestionado por **PM2**:

```bash
npm run build                    # eve build (runtime del agente, .output/) + next build
pm2 restart distribuidor-tvbox   # o pm2 start npm --name distribuidor-tvbox -- start
```

- La app corre como `next start` (servicio PM2 `distribuidor-tvbox`) en el **puerto 3010**; PM2 reinicia el proceso automáticamente si muere. Tras cualquier cambio de código hay que ejecutar `npm run build` y luego `pm2 restart distribuidor-tvbox` (`next start` sirve el build de `.next`, no el código fuente).
- Con `withEve()` en `next.config.ts`, `next start` también levanta el runtime compilado del agente EVE en loopback (puerto 4274) y proxya `/eve/v1/*` por el mismo origen. `npm run build` compila primero el agente (`eve build`) porque `next start` **falla si `.output/server/index.mjs` no existe**. Las instrucciones y las tools se congelan en ese build: tras cambiar `agent/` hay que reconstruir con `npm run build`. La lista de modelos (`ANIMATION_MODELS`) se lee al arrancar el proceso, así que cambiarla solo necesita `pm2 restart distribuidor-tvbox`. Caddy ya reenvía todas las rutas sin reescribirlas, incluidas `/eve/` y `/.well-known/workflow/`.
- El estado durable del agente vive en `.eve/.workflow-data` (disco del servidor, fuera de git): incluirlo en los backups. Variables requeridas: `AI_GATEWAY_API_KEY` y `ANIMATION_MODELS` (Vercel AI Gateway) además de `DATABASE_URL`.
- Requiere `DATABASE_URL` y `BANXICO_TOKEN` en el entorno (`.env`) y las migraciones aplicadas (paso 3). Sin `BANXICO_TOKEN` (o si Banxico no responde) la app funciona, pero los costos se muestran en USD etiquetado en lugar de pesos y los gastos en USD se reportan como *pendientes de conversión*.

El espejo de costos de imágenes históricos se importa una sola vez con `node db/backfill-image-expenses.mjs`.
