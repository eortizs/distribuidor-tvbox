## Despliegue (obligatorio)

Este proyecto **siempre se publica en el subdominio**: https://distribuidor-tvbox.people-ia.com/

### Arquitectura de publicación

- El sitio **se sirve desde esta misma máquina**: pm2 ejecuta la app `distribuidor-tvbox` (`npm start` → `next start`) sobre este directorio, escuchando en el puerto **3010**.
- Caddy (contenedor `agente-caddy-1`, config en `/root/agente/Caddyfile`) resuelve el subdominio con `reverse_proxy 172.18.0.1:3010`; Cloudflare va por delante.
- **Hacer push a GitHub NO despliega nada.** El remoto (`github.com/eortizs/distribuidor-tvbox`) es solo respaldo del código.

### Procedimiento de despliegue (obligatorio tras cada cambio)

```bash
node db/apply-mp-orders-cupon.mjs && node db/apply-mp-orders-transfer.mjs && node db/apply-mp-orders-renewal-verify.mjs && node db/apply-mp-refunds.mjs && node db/apply-shopping-list.mjs && node db/apply-coupon-limit.mjs && node db/apply-coupon-monthly-limit.mjs && node db/apply-tickets.mjs && node db/apply-paquetes.mjs && node db/apply-transfer-receipt-scan.mjs && node db/apply-transfer-concept.mjs && node db/apply-notifications.mjs && node db/apply-saldo.mjs && node db/apply-saldo-tipos.mjs && node db/apply-auth-google.mjs && node db/apply-renewal-attempts.mjs && node db/apply-mp-renewal-retries.mjs && node db/apply-conectores.mjs && node db/apply-client-filters.mjs && node db/apply-client-chip-layout.mjs && node db/apply-flujotv-app.mjs && node db/apply-modulos-permisos.mjs && node db/apply-alertas.mjs && node db/apply-order-events.mjs && node db/apply-whatsapp.mjs
npm run build && pm2 reload distribuidor-tvbox
```

1. **Migraciones de `db/` primero**: los scripts `apply-*.mjs` aplican su SQL de forma idempotente (`IF NOT EXISTS`) y son seguros de re-ejecutar. El código nuevo puede consultar columnas que solo existen tras correrlos; si se despliega sin migrar, las rutas de compra responden 500 (`SQL 42703`). Ante un cambio de esquema nuevo, crear su par `db/<tema>-schema.sql` + `db/apply-<tema>.mjs` y añadirlo aquí.
2. `npm run build` (equivale a `eve build && next build`): genera el build en `.next`/`.output`.
3. `pm2 reload distribuidor-tvbox`: reinicia el servidor para que cargue el manifiesto del build nuevo.

### Variables de entorno relevantes (`.env`)

- `MERCADOPAGO_ACCESS_TOKEN`, `LICENSE_PRICE_MXN`, `SITE_URL`: motor de pagos (sin ellas no hay checkout ni precio).
- `TRANSFER_BANK_NAME`, `TRANSFER_ACCOUNT`, `TRANSFER_HOLDER`: datos bancarios de la transferencia; sin las tres, el método se oculta.
- `RECEIPT_SCAN_MODEL` (con `AI_GATEWAY_API_KEY`): modelo de visión que revisa los comprobantes de transferencia del carrito de renovación (`POST /api/transferencias/orders`, módulo `src/server/transferencias/scan.ts`). Extrae fecha/hora, concepto, importe y beneficiario del ticket y verifica contra la orden. **Estrictos solo tres puntos**: fecha dentro del mes actual, concepto con el **código de pago de 4 caracteres** entregado al comprador en el paso 1 (el comprador escribe SOLO el código como concepto; la orden ya lo liga internamente al usuario renovado; flujo de dos pasos: primero el concepto vía `POST /api/transferencias/concepto`, después el comprobante; migración `db/apply-transfer-concept.mjs`, tablas `transfer_concepts` + columnas `mp_orders.concept_id/concept_code`) e importe ≥ orden. El beneficiario es tolerante: acepta iniciales («E. Ortiz», «Enrique O»), origen/destino implícito sin la palabra «beneficiario» y nombres con palabras extra; un nombre ajeno completo sí rechaza; sin beneficiario legible no bloquea. Todo pasa → orden `paid` y renovación automática; algo falla → orden `pending` para revisión manual y aviso al comprador de contactar al admin; sin modelo configurado o con el escaneo caído → revisión manual como siempre. La UI bloquea la app por etapas (validación → renovación → resultado) hasta el 100%: el overlay sondea `GET /api/mercadopago/orders/{id}` cada 3 s (la lectura concilia órdenes varadas), se restaura desde localStorage si el comprador recarga, y solo el panel final libera. Dedup por sha256 (`mp_orders.ticket_sha256`): el mismo comprobante re-subido por el mismo comprador nunca auto-aprueba otra orden (va a revisión manual). Escaneos con tope de 3/min por comprador (bucket en memoria) y timeout de 25 s para caber en el presupuesto de Cloudflare. El resultado queda en `mp_orders.scan_status/scan_result/scan_model/scan_at` (migración `db/apply-transfer-receipt-scan.mjs`) y lo ve el admin en «Transferencias por revisar». El concepto de pago es idempotente por comprador + usuario + mes (cancelar y volver entrega el mismo código) y se anula (`status='consumed'`) cuando la orden se aprueba o rechaza; al vencer el mes vence el código.
- `COUPON_QA_ENABLED=1`: activa el cupón de QA `0000` (pago con cupón). **Desactivado por defecto**: un cupón siempre activo permitiría renovaciones gratis sin límite. Con `COUPON_QA_DAILY_LIMIT` (default 3) se topea los canjes por comprador en 24 h y con `COUPON_QA_MONTHLY_LIMIT` (default 10) el acumulado en 30 días; ambos con override por usuario desde `/users` (icono de permisos → `users.coupon_daily_limit` / `users.coupon_monthly_limit`). El canje es idempotente por `request_id` (`mp_orders.coupon_request_id`, índice único parcial). **Todo pago con cupón (`0000` en `/clientes` y `1010` en paquetes) debita `users.saldo_cupones`** —la billetera exclusiva para licencias FlujoTV— en la misma transacción de la orden (`createCouponOrder`: lectura + débito + INSERT atómicos con el advisory lock por comprador que comparten los abonos; sin saldo suficiente no se crea la orden y responde `422 saldo_insuficiente`; el cargo queda en `saldo_movimientos` con `kind='cargo'`, `tipo='cupones'` y `order_id` único, y los replays del mismo `request_id` no vuelven a debitar). Las ventanas de checkout de `/clientes` y `/modulos/paquetes-flujotv` muestran el saldo vigente en el renglón «Saldo en cupones» del resumen (server-rendered con `getSaldosActual`) y bloquean el botón si no alcanza.
- `FLUJO_API_KEY` (o la clave guardada en Configuración → API de licencias): clave del panel FlujoTV.
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`: credenciales OAuth 2.0 de Google (Google Cloud Console → Credenciales → ID de cliente OAuth, tipo «Aplicación web»). Sin las dos, el botón «Continuar con Google» de `/login` y `/register` se oculta y `/api/auth/google/start` redirige a `/login?error=google_disabled`. La URI de redirección autorizada en Google debe ser `SITE_URL + /api/auth/google/callback` (usa `SITE_URL`; sin ella deduce el origen de la petición). El callback canjea el código, valida los claims del `id_token` (iss/aud/exp y correo verificado), liga la cuenta por `users.google_sub` (migración `db/apply-auth-google.mjs`, columnas `google_sub`/`google_picture` + `password_hash` nullable), o crea la cuenta como distribuidor sin contraseña local. El vínculo con una cuenta local existente **exige prueba de propiedad**: el callback deja la identidad pendiente firmada en cookie (HMAC con `GOOGLE_CLIENT_SECRET`, 10 min) y redirige a `/login?error=google_link_required`; al iniciar sesión con la contraseña correcta, `loginAction` canjea el cookie y enlaza `google_sub`. No hay vínculo automático por correo sin verificar (evita que una cuenta local autoregistrada anticipe el Google de su dueño). Las cuentas solo-Google no pueden iniciar sesión con contraseña. El nombre completo y la foto de Google (`name`/`picture` del `id_token`, con respaldo en el endpoint userinfo) llenan `fullName` de la entidad Cuenta (solo si está vacío; nunca pisa ediciones manuales) y `users.google_picture` (avatar del menú; se refresca en cada inicio). **Ojo**: con `cacheComponents` activo, `/api/auth/google/start` y `/callback` deben llamar `await connection()` — sin API de request-time se prerenderizan en el build y sirven congelada la respuesta (p. ej. `google_disabled` si las credenciales no existían al compilar); `export const dynamic` no compila en este proyecto. Origen público compartido: `publicSiteUrl()` en `src/server/site-url.ts` (lo usan OAuth y Mercado Pago; no leer `SITE_URL` crudo).
- **Trazas de renovación (`mp_order_events`)**: bitácora durable del ciclo de vida de las renovaciones (`db/apply-order-events.mjs`, tabla `mp_order_events`, módulo `src/server/telemetry/order-events.ts`). Cada intento de renovación (webhook, cupón, scheduler, conciliación, reintento del admin, transferencia) corre bajo un `transaction_id` (`txn-<12hex>`, `newTransactionId()`) y deja eventos con detalle acotado: `renewal_started` (trigger, clave de idempotencia, línea base y su latencia), `renewal_panel_ok` (duración del panel), `renewal_renewed`/`renewal_retry_scheduled`/`renewal_in_progress`/`renewal_failed`/`renewal_skipped_busy`. El mismo id viaja en el log JSON de pm2 (`transaction_id`), en la respuesta del canje de cupón (`transaction_id`, que la UI muestra como «ID de seguimiento» en el fallo) y en `GET /api/mercadopago/orders/[id]/events` (solo admin): seguir un caso es `SELECT * FROM mp_order_events WHERE order_id = '…' ORDER BY id;` o por `transaction_id`. La bitácora es best-effort y detached: nunca rompe ni frena la renovación. Los canjes de cupón (individuales y paquetes) disparan la renovación **desacoplada de la respuesta** (`createCouponOrder` devuelve `pending` + `transaction_id`; el sheet sondea `GET /api/mercadopago/orders/{id}` cada 2 s hasta 2 min y muestra «Aplicando…»): sostener la respuesta HTTP con el plan completo (línea base 45 s + panel 60 s + verificación 3×45 s) excedía el presupuesto ~100 s de Cloudflare y producía falsos negativos — «El pago no se completó» con la renovación aplicada después por el scheduler (caso real: orden `146eabec`, `retry_scheduled` a las 14:48:33 y `renewed` a las 14:50:49). Un fallo solo se muestra CONFIRMADO (`renewal_failed`, presupuesto de reintentos agotado o fallo permanente); `retry_scheduled`/`in_process` nunca se reportan como fallo. **Nota de despliegue**: las pestañas de `/clientes` cargadas ANTES de un deploy que cambie el flujo de canje conservan el bundle viejo (sin rama `pending`) y anuncian «Renovación aplicada» al instante aunque la renovación siga en vuelo — el resultado real llega igual por campana/SSE; anunciar el deploy y que los operadores recarguen `/clientes` antes de canjear.
- `LISTA_COMPRAS_MODEL`: opcional; modelo del intérprete de Lista de compras (`/api/lista-compras/interpretar`). Sin ella usa `ASISTENTE_MODEL` con la misma `OPENROUTER_API_KEY`.

- **Canal WhatsApp (Baileys)**: el número del agente IA se vincula como dispositivo enlazado y vive en el mismo proceso (`src/instrumentation.ts` → `src/server/whatsapp/`). Requiere `WHATSAPP_AGENT_NUMBER` (número del agente, solo dígitos con código de país, p. ej. `525540049353`; sin él el módulo queda deshabilitado) y `WHATSAPP_AGENT_MODEL` (modelo del agente de consultas vía AI Gateway con `AI_GATEWAY_API_KEY`, p. ej. `openai/gpt-6-luna`). Dos funciones: **espejo 1:1 de la campana** (todo `insertNotification` encola una copia en `wa_outbox` para cada destinatario con WhatsApp registrado — comprador y admins ya incluidos vía fan-out) y **agente de consultas solo lectura** por chat (saldo, clientes del alcance propio, vencimientos, órdenes; sin escritura). El número de WhatsApp registrado en `users.whatsapp_phone` (admin en `/users`, auto-servicio en `/profile`; único por cuenta) ES la identidad: mensajes de números no registrados reciben una sola respuesta de cortesía cada 24 h. Módulo admin `/modulos/whatsapp`: estado, vinculación por QR o código de 8 dígitos, números registrados, cola con reintentos y bitácora (`wa_message_log`, retención 90 días). La sesión persiste en `storage/whatsapp-session/` (gitignored, contiene llaves): cada deploy corta el socket y reconecta solo; los salientes quedan en `wa_outbox` y salen al reconectar. `loggedOut` (desvinculado desde el teléfono) queda en estado `revoked` sin reconectar: re-vincular desde el módulo («Reestablecer sesión»). El teléfono del agente debe conectar a WhatsApp al menos cada ~14 días para mantener viva la sesión. Baileys es no oficial: riesgo de ban mitigado con tráfico bajo (solo espejo + soporte, cero bulk) y número dedicado. Migración `db/apply-whatsapp.mjs` (columna `users.whatsapp_phone` con índice único parcial + tablas `wa_outbox`/`wa_message_log`).
- `CONECTORES_SECRET`: opcional; clave del cifrado AES-256-GCM de los tokens OAuth guardados por el módulo Conectores (`/modulos/conectores`, tabla `connector_connections`, migración `db/apply-conectores.mjs`). Si falta, se deriva de `GOOGLE_CLIENT_SECRET` — pero **rotar ese secret ladrilla en silencio todas las conexiones guardadas** (el descifrado GCM falla sin ruido y las conexiones pasan a `error`), así que conviene fijarla dedicada antes de la primera conexión. El flujo OAuth del conector es distinto al del login: URI de redirección autorizada `SITE_URL + /api/conectores/google/callback` (hay que darla de alta en Google Cloud Console). El scope pedido vive en el catálogo `src/lib/conectores.ts` (hoy `https://www.googleapis.com/auth/calendar.events`). Los consumidores de los tokens usan `accesoValido()` en `src/server/conectores/repository.ts` (renueva en frío; solo `google_grant_invalid` marca la conexión en error).
- `TICKET_SCAN_MODEL` (con `AI_GATEWAY_API_KEY`): modelo de visión del análisis de Alta de tickets (`/api/tickets/[id]/extraer`). Sin ninguna de las dos el endpoint responde 500 (`tickets_llm_not_configured`); el módulo se despliega, pero el análisis queda bloqueado hasta configurarlas.
- `ALERTS_MODEL` (con `GEMINI_API_KEY`) y `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`: módulo Alertas (`/modulos/alertas`, migración `db/apply-alertas.mjs`, tablas `alerts`/`alert_hits`/`push_subscriptions`, dependencia `web-push`). Interpreta la solicitud en lenguaje natural y revisa cada alerta con **Google Search grounding** por la **API directa de Google** (`@ai-sdk/google` + `google.tools.googleSearch`, patrón `src/server/images/grounding.ts`; el prefijo `google/` de la variable se quita al resolver). Scheduler en proceso (`src/instrumentation.ts` → `src/server/alertas/scheduler.ts`, tick de 60 s): catálogo fijo de frecuencias (1 h / 6 h / 12 h / diario con hora / semanal con día+hora, zona America/Mexico_City; la semanal ya reprograma al siguiente ciclo, no al día siguiente), **dos carriles por tick** —recordatorios primero (precisión de minuto) y después búsquedas vencidas con tope de 10 y concurrencia 3—, tope de 10 alertas activas por usuario **en transacción con advisory lock** (`insertAlertCapped`, patrón saldo: sin TOCTOU) y retención del historial a 30 hits por alerta (podado en ticks con actividad). El modo (`once`/`recurring`) lo decide el LLM; las recurrentes deduplican por huella sha256 del hallazgo (`alerts.last_finding_fingerprint`) y 3 fallos consecutivos del LLM pausan la alerta (`status='error'`, reactivable; un hallazgo exitoso reinicia el conteo). Cada disparo avisa por **tres canales simultáneos** y mejor esfuerzo: campana (kinds nuevos `alert_hit`/`reminder` en `notifications`, CHECK ampliado por la misma migración), **Web Push VAPID** (`src/server/push/service.ts`, `public/sw.js`: payload con `tag=alert_id` para colapsar en Android, deep link al módulo, `timeout` de 10 s por envío, suscripciones muertas borradas en 404/410 y **endpoint restringido a los push services reales** — fcm.googleapis.com / `*.push.services.mozilla.com` — para que ninguna URL arbitraria convierta los envíos en un sondeo del servidor; el upsert solo cambia de dueño con la misma cuenta, otro usuario → 409) y **tiempo real entre dispositivos**: evento `alerts` del bus SSE (solo-propietario, en `inScope` junto a prefs/notifications) publicado en cada mutación y en cada resolución del tick — el listado del módulo se suscribe con `useRealtimeEvent` y refresca en silencio con debounce, al volver del segundo plano y al entrar a la pestaña. **Gotchas**: `public/sw.js` debe seguir **excluido del matcher de `src/proxy.ts`** (con el gate activo el registro del service worker falla en todos los dispositivos), rotar las llaves VAPID invalida TODAS las suscripciones (`push_subscriptions`, nunca reintentar una muerta) y en iOS el push solo funciona con la PWA instalada (≥ 16.4; la card degrada con explicación). Sin `GEMINI_API_KEY` el módulo se despliega pero la creación queda bloqueada; sin llaves VAPID queda en modo campana-sola con el switch «Avisos en este dispositivo» deshabilitado (`pushConfigured()` compara contra `null`). Adjuntos por alerta: máximo 4 archivos (imágenes o PDF, 10 MB c/u, 20 MB total) en `user_files`, leídos del disco en cada revisión (sin copia extra del Buffer). La máquina de subida de adjuntos vive en el hook compartido `src/hooks/use-attachment-upload.ts` (también lo usa Imágenes).

### Advertencia crítica

**Nunca dejar el build sin reiniciar pm2.** Si se ejecuta `npm run build` sin `pm2 reload distribuidor-tvbox`, el servidor sigue con el manifiesto del build antiguo en memoria: sirve el HTML nuevo del disco pero responde **404** a los chunks estáticos nuevos (los nombres de archivo cambian en cada build). ## Reglas de UI: servidor MCP de ReUI (obligatorio)

Cualquier elemento o componente de la GUI debe crearse usando el servidor MCP de **ReUI**. Está prohibido escribir componentes de UI a mano cuando ReUI provee uno equivalente.

Flujo obligatorio para cualquier trabajo de UI:

1. Buscar el componente/bloque/ejemplo adecuado con `reui_search` (y `reui_search_icons` para iconos).
2. Leer la API real del componente con `reui_get_component` antes de escribir props o JSX; copiar composiciones exactas de `reui_get_examples`.

## Mejores prácticas de UX (obligatorio)

Al crear o modificar cualquier componente, se debe buscar ofrecer la **mejor UX posible** aplicando las mejores prácticas de diseño de interfaces:

- **Jerarquía y orden de componentes**: organizar los elementos según su importancia (título → descripción → contenido → acciones). Lo más importante primero y visualmente dominante; agrupar controles relacionados; mantener una sola acción principal por vista.
- **Organización de botones**: la acción primaria a la derecha (o al final del flujo), secundarias a la izquierda, destructivas separadas y con confirmación. Nunca más de una acción primaria visible por vista; usar variantes correctas (primary/secondary/outline/ghost/destructive).
- **Tamaño y escala tipográfica**: usar la escala del sistema de diseño (nothing below `text-xs`); títulos con jerarquía clara, cuerpo legible, etiquetas cortas. No usar tamaños arbitrarios.
- **Espaciado y alineación**: ritmo visual consistente con `gap-*`/márgenes del sistema; alinear a una retícula; densidad adecuada al contexto (tablas densas, formularios aireados).
- **Estados y feedback**: todo elemento interactivo debe tener estados hover/focus/active/disabled; feedback inmediato para acciones del usuario (loading, toasts, mensajes de error cerca del campo).
- **Accesibilidad**: contraste suficiente, área táctil mínima, foco visible, labels asociados a inputs, navegación por teclado.
- **Carga cognitiva**: formularios cortos, opciones limitadas, texto de ayuda solo donde haga falta, iconos con etiqueta de texto cuando el significado no es universal.

### Directrices de tamaños: botones, iconos y tipografía (obligatorio)

Métricas concretas de legibilidad y toque, además de las prácticas generales de arriba. Referencia aplicada: `src/components/herramientas/actualizacion-flujotv/actualizacion-flujotv-view.tsx`.

**Áreas táctiles y botones:**

- **Área táctil mínima (hit target)**: 44×44 px (estándar Apple; 48 dp Google) en todo elemento interactivo. Los botones de solo icono pequeños NO se agrandan visualmente: se extiende su zona de toque con un margen invisible por pseudo-elemento, p. ej. botón `size="icon-sm"` (28 px) + `className="relative after:content-[''] after:absolute after:-inset-2"` → 44×44 px sin cambiar el aspecto.
- **Botones estándar con texto**: altura entre 36 y 48 px (p. ej. `size="lg"`, 36 px) con relleno lateral de 12 a 16 px (p. ej. `px-4`).
- **Separación entre elementos clicables**: mínimo 8 px de espacio libre entre dos controles adyacentes (filas con enlace + botón de copia, chips, iconos de acción): usar `gap-2` como mínimo en esos contenedores.

**Tipografía:**

- **Títulos de tarjeta o sección**: 18–20 px (`text-lg`–`text-xl`) con peso SemiBold o Medium para fijar jerarquía.
- **Texto principal y datos**: 16 px (`text-base`) como base ideal en móviles (valores, cifras, enlaces).
- **Etiquetas secundarias**: nunca bajar de 14 px (`text-sm`).
- **Texto de botones**: 14 px con peso Medium (el estándar de `Button` ya lo cumple).

**Iconos informativos y enlaces largos:**

- Iconos informativos (no de acción) a 20×20 px (`size-5`) o 24×24 px (`size-6`), con `aria-hidden="true"`.
- Enlaces largos (URLs): mostrar un texto claro como «Enlace directo» en vez de truncar con puntos suspensivos; el `href` real va en el anchor y el botón de copia de la fila manda al portapapeles el renglón completo (etiqueta + URL).

Antes de entregar UI, verificar que el resultado cumple estas prácticas (usar `reui_get_audit_checklist` y el skill de ReUI como referencia de calidad).
